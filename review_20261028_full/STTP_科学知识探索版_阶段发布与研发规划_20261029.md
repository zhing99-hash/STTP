# STTP 科学知识探索版：阶段成果、发布与研发规划

日期：2026-10-29；状态：建议方案，尚未开发、验收、发布或进行用户研究。面向项目负责人和 WorkBuddy。本方案基于 [2026-10-29 全面测试评估](STTP_全面测试评估与发布整改报告_20261029.md)，不是对新版本已完成的声明。

## 一、如果由我负责，现在做什么决定

将当前第一产品调整为「科学知识探索版」：帮助具有高中基础的成年科学爱好者，从一个感兴趣的问题出发，看懂数学、物理和化学之间的一条可解释联系，逐步追溯到公式、概念、元素和可靠来源。优先中文，支持中英文关键词。

原有「科学家研究辅助系统」保留为长期可选方向，不作为本阶段交付承诺。其需要专家工作流、可复核来源、条件、数据权利和独立评测，不能因为科普版能用就认为研究版成熟。商业方向和目标客群调整是**待市场验证的假设**；若真实用户更需要科研场景，或对科普图谱没有持续兴趣，应调整或撤销这一决定。

核心取舍：一期只做 **3 个有完整讲解的主题路径**，而非承诺覆盖全部科学公式。以现有局部查询和图谱能力为底座，建立经过核对、可公开的策展内容层。模型训练、全图开放、复杂账户、自动发现、付费系统均不进入第一版。没有独立审查通过的内容不进入公开集。

预期阶段成果：用户无需了解技术术语，在 5–10 分钟内完成一条路径，能够说出一条跨学科关系、查看其条件和来源，并用反馈告诉我们哪里有帮助或看不懂。上述时间是设计目标，不是实测结论。

## 二、版本与交付对象

建议产品名暂用「STTP 科学知识探索」；对外版本拟定 **`v0.66.1-beta.1`，邀请制体验版**。先核对开发仓库中 0.66.0 的真实标签和是否已公开；若候选名已用，顺延至未使用版本，绝不覆盖已发布资产。Git 标签、页面、发布说明、manifest 使用同一个产品标识；Python packaging 可使用兼容 PEP 440 的 `0.66.1b1`，须注明二者对应，产品版本、数据集版本与数据快照哈希各自记录，不混为一谈。

| 阶段 | 成果 | 对象与条件 |
|---|---|---|
| P0 内部候选 | 能从本机打开的三个主题、已策展内容及测试记录 | 团队和审稿人；不得声称已公开 |
| P1 邀请制 Beta | 只读体验链接或可复现离线包，反馈渠道，版本说明与可追溯来源 | 约 5–10 名成年人；关键科学、许可、安全、体验门槛通过后开放 |
| P2 公开 Beta | 基于邀请反馈修复后，扩大访问范围 | 满足公开部署、内容和运营条件；另行冻结版本并按渠道实际状态发布 |

推荐先做静态只读体验站：经审查的主题内容、按主题预构建的小图 JSON 和本地前端资源构建为静态文件，避免为探索版先建设公网数据库和动态查询服务。如果部署方案不支持静态只读站，退回受控离线包/现场陪同，公网地址及托管渠道在实际选择后确定；不要把现有 `viz_server.py` 直接暴露公网。可访问的网站与可下载离线包是不同交付物，应各自验收。无需为第一版引入 AI 对话；搜索表单足够。

## 三、首版用户与三条主题

**主用户**：18 岁及以上、对自然科学感兴趣、具有高中基础的非专业人士；**次用户**：大学低年级自主学习者。先不以未成年人为首发招募对象；若以后面向学校和未成年人，再根据实际地区及平台要求设计监护、数据和合规流程。用户基础、语言和场景均是待验证假设。

| 主题 | 用户的问题 | 一条建议的知识路径 | 具体边界 |
|---|---|---|---|
| 水与物质的量 | 一杯水中为什么有这么多分子？ | 水的分子式 H₂O → 摩尔质量 → 物质的量 n=m/M → 分子数 N=nNₐ → 阿伏伽德罗常数 | 数值示例明确质量、单位及纯净水假设；元素组成不等于空间构型或分子性质 |
| 气体与温度 | 气体受热为什么会膨胀？ | 理想气体 pV=nRT → 恒压等物质的量时 V∝T → 微观粒子与温度的解释 → R=NₐkB | T 使用开尔文；理想气体、恒压、固定 n 等前提不可省；非所有真实气体和条件都适用 |
| 能量与化学变化 | 化学反应为什么有能量变化？ | 配平后的反应式 → 反应物与产物 → 反应焓 ΔH → 反应吉布斯能 ΔG=ΔH−TΔS → 讨论条件和方向 | 区分标准态与实际条件；固定温压及所用近似须说明，ΔG°=−RT ln K 使用无量纲平衡常数；反应速率与自发方向不是同一概念 |

第三个主题仅在物理化学顾问审核并核对具体例子后进入 Beta。如果短期找不到审稿人，用「元素周期与原子结构」替换该主题，仍需核对元素、同位素和原始引用。ATP 当前已知字段冲突，**首版先排除其节点、边、图、搜索、导出及截图**；也可在修复并独立复核后再纳入，但排除不意味着完整图的 ATP 问题已修好。

以上是策展内容提案，并非声称当前样例已具备这三条完整路径。必须先逐条清点已有节点、关系和来源，缺项人工补充或缩小讲解，不为凑连通路径创建没有事实依据的边。面向普通用户应解释「概念相关」「公式定义」「条件下推导」「反应参与」等不同关系，不能把所有路径都描述为证明或因果链。

## 四、实际用户流程与界面

1. 首页一句话说明用途，展示 3 张问题卡和一个搜索框；每卡说明预计学习时间与所需基础。
2. 用户选择「一杯水中为什么有这么多分子」，先看日常问题和 2–3 句说明。
3. 点击「开始探索」，依次看到问题 → 水 → 摩尔质量 → n=m/M → N=nNₐ。当前节点与前后关系高亮，一次显示少量节点；可返回上一步，不默认加载全图。
4. 点击公式显示：含义、变量、单位、使用前提、一步数值例子、相关原始出处及更新时间；显示「适用范围未核对」的内容不进入公开主题。
5. 用户可以按「为什么相关」看边说明，切换入门/进阶说明，并查看来源；找不到内容时诚实给出「本版本暂无」，不生成未经核验的答案。
6. 可选完成一个简单自检题，显示解释而非评分排名；用户主动提交「看懂了／不清楚／发现错误」及可选文本。

一期页面最少 4 类：首页、主题路径页、节点/公式详情、来源与反馈页。图谱可在详情中一跳展开，增加文本列表替代视图；支持键盘、基本无障碍和手机窄屏。颜色不作为唯一关系标识；文字优先、移动端可滚动。排除上一轮发现的布局偏出视口问题，切换主题时重置跳数和过滤器。面向小白隐藏 stale、phase、pipeline 等工程术语，保留可以展开的来源和限制。

搜索优先匹配人工维护的中文别名、英文别名、常见符号和主题标题；`乙醇/ethanol` 属于上轮发现的回归案例，但只有通过许可及数据审查后才能纳入公开内容。非唯一结果必须让用户选择，显示实体类型及上下文，不因为同名自动合并。

## 五、内容与数据建设：可执行的数据契约

用独立策展包承载公开内容，不直接公开完整图。建立可机读清单，每项至少包含以下字段（可 JSON/YAML，最终格式由 WorkBuddy 在现有仓库中选）：

| 对象 | 必填字段 | 公开规则 |
|---|---|---|
| 主题 | 稳定 ID、标题、问题、读者水平、步骤顺序、版本 | 每步可定位到已发布对象；缺项必须失败 |
| 节点 | ID、类型、中文名、英文/别名、解释、学科、来源、审查状态 | 未审或不允许展示的不进入公开包；同名不自动当同实体 |
| 公式 | LaTeX、变量释义与单位、定义域、适用条件、示例与依据、来源 | 条件未知不得包装为普遍规律；单位解析和计算代码必须通过相关反例 |
| 边 | 起点、终点、关系类型、方向、解释、条件、证据定位、是否推断 | 不同关系语义分开；不把同量纲、共现、图路径当作数学证明或因果 |
| 证据 | 原始来源标题、作者/机构、日期/版本、URL 或页码、授权及核验人、核验日期 | 可逐条追溯；上游转载链和共享来源要记录；许可不清不能公开内容或导出 |

优先从权威标准、原始文献、可合法引用的教材或权利人明确允许的资料入手。公式等事实能否复用、文本/图片/数据许可和数据库权利需分开核查；自写讲解也要保留事实依据。已有内部来源登记可作为工作线索，但「审计 0 违规」只证明符合登记表本身，不能替代核验权利。公开资源涉及共享、演绎或数据库时，具体情况和适用条款需要核实：[Creative Commons BY-SA 4.0 原文](https://creativecommons.org/licenses/by-sa/4.0/legalcode.en)。

人工策展建议起始目标：每条路径 6–12 个节点、5–12 条关系，每条 1 个完整解释和 1 个核对过的例子；三个主题分别有可检查的出处和审查记录。这是工作量上限建议，不是已有数据规模、外部认可或发布质量证明。

## 六、WorkBuddy 实施任务与验收

**T0 冻结基线与数据范围。** 从完整开发 Git 仓库确认真实 HEAD、tag、工作区状态；保留上一版结果。建立白名单策展包与排除表，记录产品版本、数据包版本、输入哈希和构建环境。验收：每条页面内容均能映射到同一冻结清单；不存在受限数据混入；复跑结果及跳过项有日志。

**T1 关闭本版会触达的科学缺陷。** ATP 全入口排除或修复；`m/s`、`J/mol/K`、`mol/mol`、`x/x` 在零处、NaN/Inf、标准态与实际 ΔG 反例形成回归。若首版不调用原评测运行器/符号验证器，仍需确认搜索、演示、导出无法触发；修复可分支推进，不能把屏蔽视为修复。验收：公开包和 UI 搜索无未审 ATP 内容，已启用的计算项有输入范围及测试；未启用功能不对外宣传。

**T2 核验来源与内容。** 逐一核对三条路径，至少 1 位相关学科人士审每条涉及的公式与关系；跨学科路径覆盖其相关学科，必要时由多位审查。记录每项意见、修订和未决问题；角色互相独立，审查不等同于实际教学有效性验证。验收：每条对外节点/边的来源、许可、条件、审稿记录完整，无未关闭的严重错误。

**T3 做体验与基本功能。** 使用既有前端实现问题卡、步骤式图、详情、来源、列表、反馈和中文搜索；采用静态策展包，或确认只读接口严格限定数据范围。验收：桌面和手机各至少一款主流浏览器，新用户独立完成三个主题入口、至少一个完整路径、查看引用和反馈；返回、空结果和错误提示有效；不存在自动拉取完整 48,813 边或暴露内部图的接口。若设计稿与实现脱节，以实际用户行为结果为准。

**T4 构建与部署。** 与开发者核对上轮 `dataset_v1.1.1` 的版本失败是否适用于新策展包：沿用现有生成器时先依据版本规则修正并重建；另做静态策展包也必须有自己的版本、散列、许可清单和验收，不得声称原数据集构建已修复。测试静态文件的来源访问及无敏感文件、第三方依赖许可、HTTPS 和安全响应头、备份与故障回退；动态服务一旦开放，再补身份、授权、速率限制与安全评估。验收：干净环境构建成功、固定输入重建输出一致或解释可接受的非确定性；验证发布包完整性和渠道权限。

**T5 复核和封版。** 本轮评估报告里的门禁退出码、全部跳过返回 0、版本不一致，以及完整 Git 历史缺失均要在开发仓复核；发布路径涉及的检查必须 fail-closed，保留具体日志。区分与发布路径无关的内部慢任务，但不得以「科普版」消除科学和许可要求。两位未参与实现的人分别完成一次安装/访问和一次用户流程；形成发布说明、已知问题、维护人及撤下错误内容流程。只有满足清单才发布。

## 七、时间、人力和决策点

以下为条件性估算，不是实际承诺：1 位熟悉现有代码的全栈工程师、1 位负责内容/运营的人，以及可及时到位的数理化审稿支持，预计 **2–4 周**形成邀请制 Beta。若只有一人兼任全部工作，或授权、审稿、托管无法及时完成，周期可能更长；如先仅发布 1 条经审查路径，可更早做小规模陪同测试。具体费用取决于是否有现成员工、顾问报酬、服务区域和托管选型，暂不编造报价。

## 八、市场试用与商业路径

第一轮找 5–10 位符合目标画像的成年人，通过科学社区、朋友介绍、大学社团和科普作者邀请；必须标明他们是方便样本，不代表整体市场。提供真实公开材料而非要求用户上传未发表研究或个人敏感信息。

建议先记录：成功进入人数/邀请人数、完成第一条路径人数/进入人数、能正确解释关键关系的人数/完成题目人数、主动打开来源人数/进入人数、7 天后再次访问人数/首次访问人数、有效反馈数及严重内容错误数。记录每个事件定义、去重方式和统计周期，低样本同时列分子/分母和原始访谈；取得知情同意，尽可能匿名，不采集多余信息。

试验前建议目标：5–10 人中至少 5 人独立完成一条路径；完成者多数能够用自己的话解释关系；至少 3 人表达愿意继续尝试，并观察实际二次访问。阈值是团队用于决定下一轮的初始约定，不是统计显著性或市场规模证明。若反复出现科学错误、看不懂、打开来源成本高或无人再访，优先纠正内容、定位或受众，不直接归因于宣传不足；保留原始任务与访谈记录，允许结果推翻方向。

商业顺序：先免费验证兴趣和理解价值，再探索科普机构/教育内容合作、主题策展授权或面向个人的增值内容；各项均需验证付费主体、版权、获客和维护成本，不预设用户会付费。不在初期做投资回报、市场份额或收入承诺。可以和投资人、科普机构及潜在合作伙伴进行非融资式交流；以真实复用、付费和内容审核能力为后续正式融资依据，实际签约或对外联系由负责人决定。

## 九、发布清单与版本说明草案

邀请制 Beta 的硬门槛：

1. 三个主题逐项科学审查与出处/许可复核通过，或按计划缩小为经审查的更少主题；不隐瞒未覆盖。
2. ATP 缺陷已修复并复核，或在本版所有公开路径彻底隔离；启用的单位/数学/数值功能覆盖已发现反例。
3. 代码与内容版本、构建清单、真实 Git 身份、关键文件哈希一致；发布流程中失败和跳过不可冒充通过。
4. 新用户能访问、操作主题、查看来源并反馈；桌面/手机的实际测试记录完整，图谱不被遮挡。
5. 部署与数据分享范围有明确许可和安全措施；现有单机 HTTP 服务不得直接开放公网。
6. 有反馈接收者、严重科学错误处置和撤下内容的办法；版本说明写清具体限制。

拟用文案：「STTP 科学知识探索 Beta 是一个帮助你从问题出发了解科学概念和公式之间联系的交互式工具。当前版本聚焦少量已注明来源的主题，内容仍在完善。请查看每条公式的适用条件与原始来源，并告诉我们发现的问题。」最终宣传文字须与**实际完成的审查和功能**一致。
