## §1 现场与证据（逐条实测，非推断）

### 1.1 现场 A：服务已停 ⇒ `Failed to fetch`

```
$ curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/     → 000（连接被拒）
$ netstat -ano | grep 8765                                          → 无监听
$ ls .runlog/                                                       → （进程已消失，日志停在 16:19）
```

**真实原因**：上一轮的常驻 viz 进程**随启动它的那个 shell / 会话结束被回收**（不是崩溃：日志无 traceback，末尾是正常 `200` 记录）。
⇒ 浏览器侧表现为 `TypeError: Failed to fetch` ⇒ 前端把它记成「后端执行异常」。

★ 这一条**不是产品缺陷**，但它暴露了**缺陷②**：错误归类把「服务没开」说成了「后端执行出错」。

### 1.2 现场 B：搜索框从未工作（旧实例日志）

对旧实例日志做**请求去重统计**（`grep -o 'GET /api/search[^"]*' | sort | uniq -c`）：

```
     26 GET /api/search?limit=20&mode=ego HTTP/1.1   ← 全部 400
```

即：**26 次搜索请求，26 次全是 400**，且请求串里**没有任何 `q`**。后端原始应答：

```json
{ "status": "error", "reason": "缺少参数 q", "error_code": "BAD_REQUEST",
  "snapshot_id": "sha256:7d4f66bca0dc" }        HTTP 400
```

### 1.3 根因定位（一次 node 实证）

```js
buildParams({ q: "F=ma", subject: "物理", limit: 20 })
  ⇒ {"limit":"20","mode":"ego","subject":"物理"}      // ★ q 不见了
toQueryString(…) ⇒ limit=20&mode=ego&subject=%E7%89%A9%E7%90%86
"q" in p ⇒ false
```

`06_PoC/js/core.js` 的 `buildParams()` 逐一 `put()` 了 22 个键，**唯独没有 `put("q", …)`**。
而 `06_PoC/js/panels.js` 的 `bindSearch` 是**唯一**的搜索调用方，其调用形态正是
`api.search(q.trim(), { limit: 20 })` ⇒ `buildParams({ q, types, subject, limit })` ⇒ **q 在这一步蒸发**。

## §2 根因链（两链，逐环）

### 2.1 链 A：搜索词丢失（P0）

```
① UI 键入 "F=ma" ⇒ bindSearch 防抖 180 ms ⇒ api.search("F=ma", {limit:20})
      ↓
② Api.search ⇒ buildParams({ q:"F=ma", …, limit:20 })
      ↓
③ buildParams 的 put 列表**没有 q** ⇒ 参数对象里 q 缺席（不报错、不告警）
      ↓
④ toQueryString ⇒ "./api/search?limit=20&mode=ego"
      ↓
⑤ 后端 _api_search：q = "" ⇒ raise ValueError("缺少参数 q")
      ↓
⑥ _guard ⇒ HTTP 400 + BAD_REQUEST
      ↓
⑦ 前端 normalizeEnvelope ⇒ status="error" ⇒ 状态行红「错误」+ error_code BAD_REQUEST
      ↓
⑧ 用户观感：**"搜索框没有反应"**（且连带把五态里的 error 态顶到台面）
```

### 2.2 链 B：断连误诊（P1）

```
① viz_server 未在运行（端口无监听）
      ↓
② 浏览器 fetch ⇒ 抛出 TypeError: Failed to fetch（网络层失败，**HTTP 状态码不存在**）
      ↓
③ api.js 的**唯一** catch 分支 ⇒ 非 abort ⇒ 一律 TOOL_EXECUTION_ERROR
      ↓
④ UI 显示「error_code TOOL_EXECUTION_ERROR（后端执行异常（非空结果，属失败））」
      ↓
⑤ 排查方向被引向「后端内部执行出错」——而后端**当次根本未被调用**
```

★ 这与铁律候选 **#84「判别依据缺字段 ⇒ 不得回落成失败态」** 是同一族：这里是
**判别依据过宽 ⇒ 错误归类**（把两类本质不同的失败压成同一个码）。

## §3 ★ 覆盖缺口（本文最值得评审注意的部分）

### 3.1 为什么「全绿而搜索框是坏的」

| 既有断言 | 它断言了什么 | 为什么抓不到本缺陷 |
|---|---|---|
| `F11 buildParams 确定性` | 同输入两次序列化**相同** | **形状**断言：只比"两次是否一样"，从不检查"里面有没有 `q`"。且其 `sample` **恰好不含 `q`** ⇒ 漏字段永远处于测试盲区 |
| `F12 空值剔除、数组以逗号连接` | 空值是否被剔除 | 恰恰把"`q` 缺席"解释成**正确行为**（它就是被剔除逻辑吞掉的） |
| `X6 error_code 文案表覆盖…` | 前端文案表 ⊇ **后端源码里出现过**的码 | 用"后端已有"作参照 ⇒ **捕不出"应该有而没写"**；且 needle 列表**硬编码**（#71 白名单永远漏） |
| `H6a–H6g 字段齐备` | `subgraph` 响应的字段齐全 | 覆盖的是**响应**侧；**请求**侧（参数是否发出去）**无人防守** |
| `H7a`（本轮新增） | 前端生成的查询串 ⇒ 真实后端 200 | — |

⇒ 一句话：**此前没有任何断言看过「真正发出去的 URL 里有什么」**。
这正是 #83（**形状断言 ≠ 行为断言**）在**参数序列化**上的又一次现身 ——
**序列化漏字段不会自己报错，只在"对端"表现为"参数非法"**。

### 3.2 同类风险的剩余面（→ D31）

`buildParams` 的键集合**没有任何"与契约求差"的断言**：本轮只把 `q` 钉住。
`/api/subgraph` 的参数（`seeds/src/dst/types/kinds/subject/trust/max_*/deadline_ms/max_paths/…`）
依旧只靠"人记得写"。契约 `contracts/*.schema.json` 描述的是**响应**，没有 query 参数清单
⇒ 无从派生。**建议**：新增 `contracts/endpoints.schema.json`（每个端点的 query 参数名 + 必填性），
让 `buildParams` 的键集合与之**双向求差**。

## §4 修复（均在源头，不打下游补丁）

| 层 | 改动 | 位置 |
|---|---|---|
| ① **参数序列化（P0 根因）** | `buildParams` 补 `put("q", o.q)`，并在注释里写明"漏字段不会报错、只在对端表现为参数非法" | `06_PoC/js/core.js` |
| ② 无效参数抑制 | `mode: null` ⇒ **显式抑制**默认 `mode=ego`；`Api.search` 传 `mode: null`（该端点不认 `mode`，发出去只是噪声，也曾在日志里误导定位） | `06_PoC/js/core.js` / `api.js` |
| ③ **错误分类（P1 根因）** | `_get` 拆成**两个阶段**：**只**包住 `fetch` 调用本身 ⇒ 传输层失败记 `BACKEND_UNREACHABLE`（带可操作提示）；响应处理阶段异常仍是 `TOOL_EXECUTION_ERROR` | `06_PoC/js/api.js` |
| ④ 契约（唯一真值源） | `contracts/error.schema.json` 的 `enum` 增至 **9 个**（+`BACKEND_UNREACHABLE`），并在 `description` 里**声明产生侧**："只由前端合成，后端永不产生" | `contracts/error.schema.json` |
| ⑤ 文案与分级 | `ERROR_CODE_TEXT` 增 1 条；新增 `ERROR_CODE_SEVERITY`（**显式归类，不设"其它一律"回落**）+ `errorCodeSeverity()`（未登记 ⇒ `err`，**往响处失败**） | `06_PoC/js/core.js` |
| ⑥ 药丸分级去硬编码 | `panels.js` 原来内联正则 `/^(BAD_REQUEST\|TOOL_EXECUTION_ERROR\|SNAPSHOT_MISMATCH)$/` ⇒ 改用 `errorCodeSeverity()` | `06_PoC/js/panels.js` |
| ⑦ **约束同源（问题的第三个入口）** | 后端 `queries.MIN_QUERY_LEN = 2`（**单点定义**，`search()` 用它报错）；前端 `core.js::MIN_QUERY_LEN` **镜像**（跨层等式 **X5b**）；`bindSearch` 单字符 ⇒ **如实提示「至少输入 2 个字符」且不发请求** | `03_知识层/queries.py` / `core.js` / `panels.js` |
| ⑧ 空/失败分列（#67） | 下拉遇到 `status="error"` ⇒ 显示「**查询失败**（`error_code`）：原因」，**不得**渲染成「没有匹配」 | `06_PoC/js/panels.js` |
| ⑨ **截断披露（#66/#67）** | `api.js::normalizeEnvelope` 补搬 `total_matches`/`truncated`（`search.schema.json` 已声明，此前被丢）；下拉据此写「**显示前 20 条 / 共 81 条（已截断）**」 | `06_PoC/js/api.js` / `panels.js` |

**为什么③要拆两个阶段**：若把「响应处理」也罩进同一个 `catch`，**我们自己的 TypeError**
（例如 `res.headers.get` 上的实现瑕疵）也会被标成「后端连不上」——那是**判别依据过宽**，与本次要修的缺陷同族。
拆开后：**只有异常确实来自 `fetch` 才允许判传输层失败**。

## §7 本轮新登记：测量器/方法学踩坑（E）

### E31 测量器比被测对象更脆（与 #76 同族）

`X6c` 首轮 **FAIL**（"未归类: GRAPH_QUERY_TIMEOUT, MISSING_CONDITION, SNAPSHOT_MISMATCH, …"），
而 `core.js` 里这些码**明明都写了**。原因：python 侧解析用 `^\s*([A-Z_]+)\s*:`（**只认行首**），
而我把 `ERROR_CODE_SEVERITY` 写成了**一行多对** ⇒ 每行只有第一个键被认出
⇒ **"漏项"被误报成"未归类"**。
**处方**：解析**不得依赖换行**（改为 `([A-Z_][A-Z0-9_]*)\s*:\s*["']`），`ERROR_CODE_TEXT`/`ERROR_CODE_SEVERITY` 两处同改。
★ 教训与 #76 一致：**先怀疑测量器，再怀疑被测对象**。

### E32 负对照脚本的"还原"必须校验字节（否则会留下已注入的仓库）

第一版负对照脚本用 `shutil.copy2(p, "/tmp/x.bak")` 备份、`Path("/tmp/x.bak")` 还原 ——
**Python 的 `/tmp` 是 `C:\tmp`**，而 Git Bash 的 `/tmp` 是另一处；且我在还原处写错了文件名
⇒ **首次还原静默失败**，`core.js` 一度**停在"已注入"状态**（后被基线 sha256 比对发现并复原）。
**处方**：备份/还原一律**绝对路径**＋**还原后断言 sha256 相等**（本轮已执行：`core.js 6a41fce8…`、`api.js 08caa0cd…`、`viz_server.py 8b757754…`、`error.schema.json 6dc6ab53…` 全部 `True`）。

### E33 ★ 断言被静默删除，而**总数是净增的**

为新增 `F35f`–`F35h` 而编辑 `frontend_core_check.mjs` 时，`old_string` 恰好覆盖了 `F35e` 整块 ⇒
**F35e（竞态：过期响应不得覆盖较新结果）被删掉**，而断言总数从 **109 → 111**（实为"**加 2 删 1**"）。
⇒ **"总数变多"完全掩盖了删除**；若只对比 PASS/FAIL 计数，本次会**带着一个被删掉的断言**交付。
**发现方式**：按**名字** grep（`grep -E "F35"`）时发现序列里缺 `e` ⇒ 立刻补回（终值 **112/0**）。
**处方（→ 铁律候选 #87）**：改断言文件后必须核对**断言「名字集合」**（前后各导出一次名单求差），**不得只看总数**。
★ 与 **#74（断言过期须重写而非删除）** 配套：#74 管"该不该删"，#87 管"删没删掉，你怎么知道"。

## §9 一句话结论

**三个互相独立、都能单独让"搜索框没反应"的根因**：
前端**参数序列化漏 `q`**（P0，26 次 400）、**传输层失败被误标为后端异常**（P1）、
**最短长度约束两侧不一致 ⇒ 第一次按键就制造 400 且被显示成"没有匹配"**（P2）。
三者的共同点不是"代码写错"，而是**断言只覆盖了形状与响应、没有覆盖"真正发出去的请求"、"失败的归类"与"两侧约束的一致性"** ——
故修复必须同时落到**断言层**：新增 `F33/F34/F35`（行为）、`H7`（跨层端到端 + 内建负对照）、`X5b`（约束同源），
并把 `F7/X6` 的比对名**从契约派生**（唯一真值源），使"忘记归类 / 忘记声明 / 忘记发字段"变成**会红**的事。
★ 方法学收尾：本轮最后一次编辑**静默删掉了 `F35e`**，而总数是**净增**的（E33）⇒
**"断言变多了"不是安全信号；核对"断言名字集合"才是**（铁律候选 #87）。
