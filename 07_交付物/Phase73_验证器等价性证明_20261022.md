# Phase 73 · 验证器等价性证明：把「代码变了」与「判据变了」分开

> **起因**：`bash sttp.sh gatecheck` 的 `[3/3]` 正对照红了一轮没人发现（D108，Phase 72 修）；
> 修完做全面体检时发现 `subgraph` **98/2/3**、`grade` **5/1** 两处红 ——
> 根因是**同一个动作**：Phase 72 改了 `verification_model.py`，没有重验。
> **这是第二次踩**：Phase 61 踩过一次并 revert，提交 `0601408` 的信息里就写着
> 「会让 32,609 条证据全部 stale」。所以本轮不只修数据，还要修**这类失效凭什么可以不重跑就恢复**。

## 一、问题：整文件哈希当身份，改一个分支就全图失效

```
`vch`（验证器 code_hash）= sha256(整个 verification_model.py)[:12]
```

Phase 72 对这个文件做了 **105 行插入、0 行删除**：只给 `mentioned_in` 这类新边加分支，
既有语句一条没动。但 `vch` 变了 ⇒ 32,609 条证据的记录值与当前值对不上
⇒ A04 判 `stale`（=「已变更」）⇒ 两个后果：

| 后果 | 读数 |
|---|---|
| `subgraph` V18h | 47,055 条 `not_in_repo` 边里 **32,254 条被判 stale**（未入库 ≠ 变更） |
| `subgraph` V16c | 假红（见 §二） |
| `exclude_stale` | 打开即排除全图 **66.7%** 的边 —— 典型自毁开关 |
| `grade` G5 | 103 条落盘评分与现算不符（Phase 72 改的那批） |

**「已变更」这个判词是错的**：这 32,609 条边的数据一个字节没动。

## 二、先说两个**仪器**缺陷（与数据无关，但让问题看不见）

**V16c · 两侧不是同一命题**（D109）
旧写法 `reg0 = V.stale_registry()`（服务端 registry，**含** A04 证据层）对比
`reg1 = Q.build_stale_registry()`（本地构造，**不含** A04）。于是：
A04 判出 0 条时两边恒等 ⇒ **判据恒真**，什么都不守；A04 一判出 stale ⇒ 左大右小 ⇒ **假红**。
这与 **D72**（V18h 旧版）是同一个模子 —— Phase 57 修 V18h 时**漏修了同函数的 V16c**。
修法：两侧走同一条构造路径，**只让哈希图这一个变量不同**。

**interpcheck 漏扫 122 个文件**（D110）
`iter_py()` 用 `git ls-files "*.py"`，而 git 默认把非 ASCII 路径输出成 `"11_\347\234\237..."`，
`os.path.join` 打不开 ⇒ 被 `except OSError: pass` **静默跳过**。
后果不是"少扫一个文件"，而是 **`11_真实数据/`、`03_知识层/` 整片目录从未被扫过**，
而 Q3/Q5 照样绿（它们只看扫到的那些）。全仓 212 个 `.py` 里有 **122 个**属此列。
这个坑本项目已经踩过一次（`phase43_subgraph_selfcheck` 的 V16f 就为此显式加了
`-c core.quotepath=false`）—— **同一条命令的默认值，换个仪器就再坑一次**。
修法：开关写在取文件的那一处，并加自检 **S9**（集合含非 ASCII 路径且逐条可打开）。

## 三、处置：可重算的等价性证明，而不是重写哈希

两条错路：

- **重写哈希**：把 `vch` 改成当前值 ⇒ 状态直接变 valid，但**没有任何证据**说明语义没变。
  这正是 `evidence_deps` 里 `hash_rewritten_without_reverify` 要堵的假象。
- **重跑 3.2 万次判定**：多数判定的输入（PhysicsBabel / ChEBI / Rhea 原文）**不在仓库里**，
  重跑只能重跑一个读不到输入的空壳 —— 假动作（铁律 #30）。

走第三条：**把「语义没变」做成可机械复算的命题**。

`11_真实数据/reverify_attest.py` 对着 git 历史里的**真 blob** 做结构证明，七条断言：

| # | 断言 | 拒什么 |
|---|---|---|
| P1 | 顶层定义一个不少 | 删掉分支函数 |
| P2 | 保留函数的 `args`/装饰器逐字相同 | 改默认参数 |
| P3 | 保留函数的语句序列是「旧 ⊆ 新」（插入-only） | 改一行既有语句 |
| P4 | 每处插入的形状 ∈ 白名单（import / 新定义 / 守卫式控制流 / 文档串） | 插入 `return`、无条件赋值 |
| P5 | 控制流插入的守卫**正向点名**被排除的边类型（不许 `!=`、不许子串匹配） | 无守卫的 `if`、`if t != "x"`、`if kind == "zz_kind"`（子串冒充） |
| P6 | 模块级字典常量：老键逐键保同值，只允许加新键 | 偷偷改掉某个老档位的取值 |
| P7 | 新增顶层名不覆盖既有名 | 用同名函数劫持旧实现 |

**本轮真实证明（`rva:9302106b0f54`，`100148c147cb → e45c23ba2993`，排除 `mentioned_in`）**：

```
changed_defs   SCOPE_KIND / classify / _CLAIM_TEMPLATES / build_ctx   （4 个，全部插入-only）
added_defs     name_mention_in_text                                   （1 个新函数）
added_consts   MENTION_VERIFIER / MENTION_RULE                        （2 个新常量）
dict_extensions  SCOPE_KIND +3 键、_CLAIM_TEMPLATES +1 键、build_ctx 的 ctx 字典 +mention_ok
guards          classify:1393 guarded_if ｜ build_ctx:1666 guarded_for
module_insertions  import(76) / newconst(1119,1120) / newdef(1123)
```

⇒ **被排除的边类型之外，验证器行为不变** —— 这是能被人拿 git 历史重算一遍的命题，
不是"我看着像纯新增"。

### 落图：只加一个键，`vch` 一个字不改

```
rva  <attestation id>     # 指回上面那条证明
```

**第一版是错的，被 E6 当场抓出来**：我先把 `vch` 改成当前值，结果「记录值 == 当前值」
⇒ 证据凭哈希相等就算 valid，`rva` **形同虚设**（验证器以后再改一百次也照样 valid）。
这正是本项目一直在堵的那个假象。E6（伪造证明的 `to` ⇒ 必须回落 stale）把它变成红的，
改成「只加 `rva`」之后 E6 才绿。

现在 `evidence_status` 的判定多一步：

1. 记录 `vch` ≠ 当前 `vch` ⇒ 原因 `verifier_changed`（**照常**）
2. 若证据带 `rva`，且 `att.from == 记录 vch` **且** `att.to == 当前 vch` **且** 验证器同名
   ⇒ 把 `verifier_changed` 换成 `reverified:code_equivalent`
3. 只抵这一条原因；`src_changed` / `ref_changed` / `dep_version_changed` **一概不动**
   —— 证明的是「代码没变」，不是「数据没变」

缺 `rva`、`rva` 指向不存在的条目、或 `to` 已过期（验证器又改了）⇒ 一律回落 `stale`。
**缺省即不认**（`attestations=None` 时更严，绝不会把 stale 说成 valid）。

## 四、结果

| 指标 | 处置前 | 处置后 |
|---|---|---|
| A04 `stale`（已变更） | **32,609** | **0** |
| A04 `valid` | 750 | 1,100 |
| A04 `needs_review`（不可复算，如实保留） | 2,310 | 34,569 |
| 图规模 | 9,750 / 48,813 | **9,750 / 48,813**（不变） |
| 改动 | — | 32,583 条边、32,609 条证据，**只多一个 `rva` 键**（条数以下方核对表为准） |
| `subgraph` | 98 / 2 / 3 | **100 / 0 / 3**（RC=0） |
| `subgraph` V16c | 假红 | stale 224 → 922（changed 698） |
| `subgraph` V18h | 47,055 条中 32,254 条 stale | 47,055 条中 **0 条** stale |
| `grade` | 5 / 1 | **6 / 0**（G5 不一致 0 条） |

`needs_review` 从 2,310 涨到 34,569 **不是恶化**：这 32,259 条原本被判 `stale`（"已变更"），
现在如实变成「来源不在仓库里，本机无法复算」—— 判词从**错**的「变了」改成**对**的「测不到」
（铁律 #70：不可复算 ≠ 已变更，两者混一起会让 `exclude_stale` 退化成清空全图）。

### 现算核对（`06_PoC/report_number_check.py` 每次重算；**当前值以本表为准**）

上表「处置前」列是历史值、不可复算，只作叙述。下面四行是**当前态**，
每行都由 `report_number_check.py` 从图里现算（`byte_source=repo` + 同一份 current 快照）
并与本表逐字比对，不一致即 RC=1：

| 量 | 现算值 |
|---|---|
| A04 `valid` / `stale` | 1,100 / 0 |
| A04 `needs_review` / `rejected` | 34,569 / 0 |
| 带 `rva` 的证据 / 全部 A04 证据 | 32,609 / 35,669 |
| 带 `rva` 的边 / 全部边 | 32,583 / 48,813 |

★ 为什么「带 `rva` 的证据数」要单独咬：把 `vch` 改成当前值**也能**让 `stale` 归零，
`subgraph` V18h 照样全绿 —— **只有 rva 覆盖率**能把「重验过」与「重写哈希」分开。
这一对有判据，是 D110 在数据侧的落地；没有它，本轮的正确处置可以被下一轮用错误方式"复现"。

★ 本表**不**登记 `subgraph` 100/0/3、`grade` 6/0、V18h 47,055/0：它们是**仪器自己的输出**，
由 `gatecheck` 直接跑那台仪器来判。再登记一遍等于"仪器跑仪器"，两处判据必然漂移（#88）。

## 五、判据与探针

**`reverify_attest.py --selfcheck` 8/8**，其中 6 条是负对照：
删定义、改一行既有语句、无守卫插入、改老档位取值、同名覆盖、不给排除范围 —— 每条都必须拒。

**`phase73_reverify_delta.py` 判据 E1–E7 8/8**（含 E4b）：

| 判据 | 守什么 |
|---|---|
| E1 | 记录侧 `vch` 单值且等于证明的 `from`，当前值等于 `to` |
| E2 | **重算**证明（拿 git 历史真 blob，不信表里的结论） |
| E3 | 被改的证据都不在排除类型上（`mentioned_in` 上一条未改） |
| E4 | 只加 `rva` 一个键（`vch`/`evd`/`src_hash`/`refs`/`dvs`/`impl` 逐字不变） |
| E5 | 合并态 `stale` 归零，其余分档如实保留 |
| E6 | **反作弊**：证明的 `to` 改坏 ⇒ 同一条证据回落 stale |
| E7 | 幂等：合并态再跑 ⇒ 0 变更 |

**自检 6/6**（含 3 个负对照）：版本不同才处置、排除类型上不许借用证明、
有 `src_changed` 时不处置、无证明时不处置、`evidence_id` 不含 `vch`（身份稳定）。

**新探针 R43 / R44**（`redprobe` 47 → **49**，都验证过真会红）：
- R43：`_attestation_ok` 不再核对 `to_code_hash` ⇒ **E6 必须红**（证明退化成永久通行证）
- R44：守卫不再点名排除类型 ⇒ **S4 必须变红**（任何改动都能自证无害）

**把新机制挂上门禁，而不是挂在记性上**（`gatecheck` 六步 → **七步**，`RC=0`）：

| 新步骤 | 防的是什么 |
|---|---|
| `[3/7]` `reverify_attest.py --check` | 证明表**入库**，若无人复核，把 `to_code_hash` 改成当前值即可伪造一份永久通行证 —— 证据照样 valid、V18h 照样绿。本步每次拿 git 历史重算 AST 证明 |
| `[7/7]` `report_number_check.py` | 本轮登记的 4 条当前态数字（含「带 `rva` 的证据 / 全部」）与图里现算逐字比对 |

★ 为什么 `[3/7]` 必须常驻：**D110 说"凭证要能被改坏后仍通过测试"**，而这条要求有个
日常版本 —— **凭证必须每天被复核**。只在"生成证明表的那一次"跑过 `--check`，
下一轮有人改了表就没人看得见。

**`docnums` 新增 4 条声明 + 自检 S4**（14 条声明，`--selfcheck` **5/5**）：
S4 是**新判据的负对照** —— 把「带 `rva` 的证据数」改小 1 ⇒ 那一条必须判不一致、
同表其余 3 条必须仍一致。新判据第一次就绿，恰恰是最该反问的时刻（D110）。
刻意**不**登记 `subgraph` 100/0/3、`grade` 6/0、V18h 47,055/0：它们是仪器自己的输出，
由 `gatecheck` 直接跑那台仪器来判，再登记一遍就是"仪器跑仪器"，两处必然漂移（#88）。

## 六、三条学费

**D109 · 「验证器版本变了」≠「判据语义变了」，但整文件哈希把它们当成一件事。**
代价不是数据错，是**判词错**：32,583 条边被盖上「已变更」的章，而它们一个字节没动。
错判词会**自我加固**：`exclude_stale` 一开就等于删掉三分之二的图，于是没人敢开，
这个开关形同报废。识别它的唯一办法是**去看 diff 到底改了什么**，而不是看"哈希不同"。
> Phase 61 踩过一次并 revert；第二次踩说明「记住」不是机制。
> 现在的机制：`--check` 每次拿 git 历史重算证明；证明过期 ⇒ 整条不成立。

**D110 · 我的第一版把 `vch` 改成当前值 —— 是 E6 抓出来的。**
如果只写 E1–E5（正向判据），第一版会**全绿通过**：状态确实 valid 了、规模确实没变、
幂等也成立。只有「伪造证明必须回落」这条**反作弊判据**能发现 `rva` 是装饰品。
> 教训：凡是引入「凭证 / 证明 / 白名单」的机制，**必须同时给一条"把它改坏仍能通过吗"的判据**。
> 正向判据证明机制能工作，反向判据证明机制**在起作用**。

**D110b · 一个静默漏扫能让整片目录从未被检查，而所有判据都是绿的。**
`git ls-files` 的默认 quotepath 引号 ⇒ 122/212 个文件被静默跳过。
**「全绿」在测量器有洞时是最危险的读数**（铁律 #90 的正向版本：
不仅要问"判据会不会红"，还要问"它到底看了多少"）。
> 处置：S9 直接咬住**取集合**这一步，而不是咬下游判据。

**另外一条流程教训（非代码）**：本轮第一次跑 `gatecheck` 时我在**同时改源码**，
`red_probe` 的 RR（还原自检）因此报红 —— 探测器的前提是"事实源在它跑的时候不许变"。
这不是代码缺陷，但会浪费一次全量运行：**门禁在跑时不要动它要突变的文件**。

## 七、剩余边界（如实登记）

1. **证明粒度仍是整文件**。本轮没有把 `vch` 改成"每函数指纹"：跨函数依赖（模块级常量、
   共享 ctx）无法可靠切分，做错比不做更危险。**未来若要根治，方向是给每个 impl 登记
   "它真正读哪些函数/常量"，而不是按文件哈希。** 本轮把「插入-only + 守卫点名」做成了
   可复算的证明，是这条路的**保守版本**。
2. **P5 只检查守卫里出现被排除类型的字面量，不检查守卫的语义是否充分**。
   `if t == "mentioned_in" or True:` 这种写法能过 P5。当前代码没有这种形状（已人工核对），
   但证明机制本身挡不住 —— 这是已知的强度上限，写在 `ast_proof` 的文档里。
3. **`dvs` 未扩容**：新导入的 `phase68_paper_fetch.py` 没有记进这 32,609 条的 `dvs`。
   这是**有意**的（它只被新分支用到），代价是将来该文件变更时这 3.2 万条不会自动失效。
   若哪天它真的影响老判据，靠 P 系列证明会拒（因为 diff 不再插入-only）。
4. **`needs_review` 34,569 条仍然测不到**。PhysicalBabel / ChEBI / Rhea 原文不在仓库里，
   这是数据可得性问题，不是本轮能修的。

## 八、复现

```bash
bash sttp.sh reverify --check      # 复算证明（不信表里的结论；算不出 ⇒ RC=2）
bash sttp.sh reverify --dry        # 只跑判据 E1–E7，不落盘
bash sttp.sh reverify --apply      # 生成 + 应用 delta（幂等）
python 11_真实数据/reverify_attest.py --selfcheck        # 8/8（6 个负对照）
python 11_真实数据/phase73_reverify_delta.py --selfcheck # 6/6（3 个负对照）
python 06_PoC/report_number_check.py --selfcheck          # 5/5（S3/S4 两个负对照）
bash sttp.sh gatecheck             # 七步（Phase 73 起并入 subgraph / grade / 证明复核 / 报告数字）
```

★ 证明表 `11_真实数据/reverify_attestations.json` **必须入库**（2 KB）。
不入库的话，干净检出里「重验过」与「偷偷重写哈希」**无法区分** ——
这正是 Phase 45 重验账本（逐证据 10 MB、只能 gitignore）留下的缺口。
