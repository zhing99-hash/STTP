## 3. `pyproject.toml` 的设计口径

### 3.1 与 §0.1「拒构建链」的关系（**先讲清，避免被当成违约**）

1. ❌ 明确不做：产品化 / 补无证据边 / 新学科大规模摄入 / GNN 大规模调参 / 3D 全图重写 / 以演示为评价标准；

## 4. `sttp_cli`：为什么是「薄封装」而不是第二套实现

三条约束（都有断言）：

1. **无机器绝对路径**（A05c 的入口侧根治）：不读任何硬编码路径；解释器用 `sys.executable`
   （= 「运行本命令的那一个」）；根目录三路探测 `$STTP_ROOT` → 从 cwd 逐级上溯 → 从包安装位置上溯
   （判定标记是 `sttp.sh` / `06_PoC/release/verify_release.py` / `contracts/subgraph.schema.json` 三个**相对**路径）。
2. **不复制逻辑**：所有子命令 `subprocess` 转发到既有脚本。自检 A05-12a 做**构造性**验证——
   在**临时 cwd**、且**剥掉 `PYTHONPATH`/`STTP_ROOT`/`STTP_PYTHON`** 的环境里按文件路径导入
   `sttp_cli/cli.py` ⇒ 必须成功（若它偷偷 `import queries`，此断言必红）。
3. **两级可复现等级可判定**（A05 要点的显式要求）：

| 等级 | 内容 | 前置 | 联网 |
|---|---|---|---|
| **L1 · 随包成品样例重放** | 校验**已入库**的发布包（`--release`，28 条断言） | 无 | 否 |
| **L2 · 原始源 → 规范图重建** | `export` → `release`（重建样例与清单） | ★ 需**不入库**的 `06_PoC/etl/normalized.json` | 是 |

★ 自检把这件事**结构化**而不是写在散文里：`L1.needs_authority_graph=False` 而
`L2.needs_authority_graph=True`（A05-12b 断死），并**构造性**地在一个「缺 manifest」的临时根上
断言 `L1.ok=False`（A05-12c）——**缺产物绝不被判成可用**。

## 5. 解释器约束与 pip 依赖分离（A05b 的根因）

原状：

```
# 解释器
python==3.11.9          ← 与下方 pip 分发**同列**
# 验证闭环
rdkit==2026.09.1
```

★ **为什么这不只是「不优雅」**：`pip install -r requirements.lock` 会把这行当
**PEP 508 依赖**解析 ⇒ 去找一个名为 `python` 的**分发**（PyPI 上确有一个长期无人维护的同名包）
⇒ **装错东西或直接失败**。这是「配置写错但看起来像对的」——最贵的一类错。

处置（**分两步、分两个文件**）：

- **解释器**（机器可读）→ `pyproject.toml` 的 `requires-python = ">=3.11,<3.12"`
  （由自检 A05-3 用版本比较器**实际求值**：`3.11.9` 通过、`3.13.12` **必须不通过**）；
- **pip 分发** → `requirements.lock` / `requirements.txt`，**不含**任何解释器伪包
  （自检 A05-6a 断死；并带反例 6b：塞回 `python==3.11.9` **必红**）；
- `requirements.lock` 里给出分两步的复现命令（先备 3.11 解释器，再 `pip install -r`）。

### 5.2 ★ 拆分的**代价**与回程（E27，本轮踩到并已修）

动手前先查「谁在读那一行」——结果 **`make_manifest.py:85` 的注释明写「（含 python）」**：
`read_lock()` 会把 `python==3.11.9` 解析为 `dependencies.target["python"]`。
⇒ 直接删掉它，会让发布清单**丢掉「目标解释器」这一信息**，并让 `drift` 不再报告解释器不符。
**这是「改了一个文件、悄悄弄丢另一处信息」的典型**（与 E10 同族：口径一致但**搬运漏了一格**）。

**处置（回程，而不是放弃修复）**：

- `make_manifest.py` 新增 `read_requires_python()`：用 `tomllib` 读 `pyproject.toml` 的
  `project.requires-python`，写入

  ```json
  "interpreter": {
    "constraint": ">=3.11,<3.12",
    "constraint_source": "pyproject.toml:project.requires-python",
    "running": "3.11.9",
    "note": "约束的权威在 pyproject.toml 的 requires-python（**不在** requirements.lock）；…"
  }
  ```

- 同时确认 **`installed_versions()` 本来就硬编码** `{"python": platform.python_version()}`
  ⇒ 「**运行**的解释器」一路不缺；缺的只是「**目标**」，现由 `requires-python` 补回。
- **`verify_release.py` 不读 `dependencies.target`**（它独立 `importlib.import_module` 判 G1/G2）
  ⇒ 拆分**不**影响发布门禁口径（已核对，实测 `release` 仍 **28/0/0**）。
- 新增断言 **A05-14**：`manifest.dependencies.interpreter.constraint == pyproject.requires-python`
  **且** `target` 不含解释器伪包 —— 保证「**只有一个权威**」不会随重构漂移。
  ★ 在**干净检出**里也成立（`manifest.json` 已入库）。

### 7.2 为什么「仪器自证」排在最前（铁律 #76 的镜像）

实测：把 `_vt()` 故意打坏（恒返回 `(0,0,0)`）后：

```

  ⛔ **仪器自证失败** ⇒ 后续「全红」可能是测量器坏了，而不是被测对象坏了。
     退出码 **3**（与「有 FAIL」的 1 分开；铁律 #76）。      → RC=3 ✓
```

### E23（**测量器陷阱 · 本轮踩到**）`grep -c $'\r'` 在本环境**恒等于总行数**

**现场**：本报告初稿曾据此判定「新文件全是 CRLF」，与 `od` 结果矛盾。

**实测**（同一文件 `pyproject.toml`，`od -c` 已证为**纯 LF**）：

| 写法 | 结果 |
|---|---|
| `grep -c $'\r'` | **102**（= 文件总行数）|
| `awk '/\r/{n++} END{print n+0}'` | **0** |
| `tr -cd '\r' < f \| wc -c` | **0** |
| 三口径哈希（raw / `--path` 过滤后 / LF 归一化） | **三者完全相等** |

**根因**：`$'\r'` 传进 `grep` 时该构建下**退化为空模式** ⇒ `grep -c ''` 匹配**每一行**
⇒ 恒返回总行数 ⇒ 制造「**全 CRLF**」的假象。

**性质**：与铁律 **#38（PASS ≠ 无红）/ #76（全红也可能是测量器坏了）同源** ——
这次是「**全非零也可能是测量器坏了**」。**它已经成功误导过本轮的判断一次。**

**处方（新增铁律候选 #81）**：
> **行尾一律用 `od -c` / `tr -cd '\r' | wc -c` / `awk '/\r/'` 判定；`grep -c $'\r'` 在本项目环境不可用。**
> 更一般地：**任何「计数型」探针，先在一个已知答案的样本上自证**。

★ **连带复核建议**：D24/D26 里出现的 CRLF 计数（如「`git checkout -- 06_PoC/js` 写入 2446 处 CRLF」）
若当时是用 `grep -c $'\r'` 得出的，**该数字需用上述三种方法之一重测**。本报告不做断言（无法回溯当时的命令）。

### E28（**仪器自指 · 已修**）扫描器会把**探针自己**算进去 ⇒「提交前绿、提交后红」

**现场**：`bash sttp.sh install` 在 `phase45_install_selfcheck.py` **未跟踪**时跑 = **24/0/0（绿）**；


**根因（两段，缺一不可）**：
1. 我在本轮新写的 `wheel_probe()` 里有 `import setuptools`（用来判断能否离线构建）。
2. 文件枚举用 `git ls-files`（**只含已入库**）⇒ 该文件**未跟踪时根本不在扫描范围**，

### E30（**`finally` 保护不了强杀 · 已识别未修 · P2**）SIGTERM ⇒ 临时目录残留（**#78 的残余路径**）

**现场**（本轮收官清扫时实测）：`%TEMP%` 里残留 **4 个**本轮工具链的临时目录：

```
sttp_manifest_6rmkezhl      14:59   1 文件   4 KB
sttp_manifest_dj07l2s5      14:26   1 文件   4 KB
sttp_lineage_sc3_bkai9fsm   14:27   39 文件/24 目录  315 KB
sttp_lineage_sc3_lbq3bb3n   15:00   39 文件/24 目录  315 KB
```

**先排除误判**：两处创建点（`make_manifest.py:301`、`lineage_invalidation.py:688`）**都已经**有
`try/finally: sr.rmtree_force(tmp)`（Phase 44 的 E9 修复）⇒ **不是「忘了写 finally」**。
且 `sttp.sh` **全文无** `timeout`/`kill`/`trap`（410 行，实测）⇒ **不是工具链自己杀进程**。

**构造性验证（铁律 #75）** —— 同一段带 `try/finally` 的探针，两种信号对比：

| 信号 | 探针输出 | 临时目录 |
|---|---|---|
| **SIGTERM**（`kill -TERM`） | 只有路径，**没有** `FINALLY-RAN` | ★ **残留** |
| **SIGINT**（模拟 Ctrl-C） | 路径 + `FINALLY-RAN` | 已清理 |

⇒ **根因**：Python **默认不捕获 SIGTERM**，进程**立即终止、不展开栈** ⇒ `finally` **不执行**
（`TemporaryDirectory` / `__del__` 同理，都救不了）。时间戳与被强杀的那几次运行吻合
（14:59/15:00 ≈ 本轮前台跑 `release` 被工具超时 SIGTERM 的那次；14:26/14:27 ≈ 更早一次同样被杀的运行——
★ 逐个归属无法确证，**可确证的是机制**）。

**为什么值得登记（而不是「环境噪音」）**：本工具链的仪器**动辄 8–10 分钟**（`lineage` ≈8 min、`release-full` ≈2 min），

```bash
node 06_PoC/tests/frontend_core_check.mjs
```
