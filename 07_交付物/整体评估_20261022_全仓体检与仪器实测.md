## 一、项目是什么（定位，先说清，避免评估错位）

指南 §0.1 已裁决：**A 研究原型（收敛版）—— 不做产品化**。
主目标 = 「跨学科公式知识图谱的构建方法论 + 可审计验证纪律」，**不是**做一个可交付的产品或专题助手。

明确**不做**（除非另行裁决）：产品化收敛、为提连通率补无证据的边、新学科大规模摄入、GNN 大规模调参、3D 全图重写。
**唯一例外**：与定位无关的工程纪律类缺陷（发布链、判分器、许可、可安装性）一律照修。

> 这一条决定了下面「下一步规划」的排序逻辑：**不是按「功能价值」排，是按「是否补齐已有纪律」排**。

## 四、本轮实测抓到的两处破口（都是 Phase 72 的收尾遗漏）

### 4.1 🔴 `subgraph` V18h：32,583 条证据被判 `verifier_changed`

实测输出：
```
[FAIL] V18h [构造性] unverifiable_not_in_repo 的边不被判 stale（未入库 ≠ 变更）
       样本 47055 条中判 stale 32254 条｜not_in_repo=47055（占 96.4%）
[FAIL] V16c 判据非真空：翻转已登记来源的当前哈希 ⇒ 相关边翻成 changed
       stale 32802 → 922（changed=698，来源 Phase13.Gate.B5，引用 734 条）
```

**根因链（已逐环验证）**

1. 现算 A04 状态：`stale 32,583` / `needs_review 2,600`；stale 的原因**逐条都是两个**：
   `unverifiable_source:<src>`（已知边界）+ **`verifier_changed:verification_model`**。
2. 证据里记的验证器哈希是 `100148c147cb`；当前 `verification_model.py` 的 blob 哈希是 `e45c23ba2993`。
3. 用 git 逐提交验算 blob：
   ```
   0f462fb (Phase 72) : e45c23ba2993   ← 当前
   0601408 (Phase 72 前): 100148c147cb ← 证据里记的值
   ```
   ⇒ **Phase 72 新增 A11 分支 + import `phase68_paper_fetch`，把验证器实现改了，但没有执行重验。**

**这件事在本仓库有前科，而且是我自己记下的：**
> 指南 §0.3.18 / 规划 §6.1：「曾试图在 `verification_model.declared_symbols()` 加护闸 ——
> 那会让 A04 判据把 **32,609 条证据全部判 stale**，必须整体重验才能恢复。
> **改判级模型的代价必须先算清再动手**（已 revert，commit `0601408`）。」

Phase 61 踩过一次、revert 了；**Phase 72 又踩了一次，这次带着正确的功能目标，但同样没有配套重验。**
数字也对得上（32,609 → 32,583，差 26 条 = 图规模从 48,712 涨到 48,813 后又撤回的边）。

**影响面（要如实说，不夸大也不缩小）**

- `exclude_stale` **默认 False** ⇒ 前端（121/0/2）与对外数据集**当前不受影响**。
- 但这是一个**自毁开关**：一旦有人开 `exclude_stale=true`，会**排除全图 66.7% 的边**（32,583/48,813）。
  铁律 #70 当初就是为这个风险写的。
- 按 A04 契约，「**单纯重写哈希不能恢复 valid**」——必须实质重验。

### 4.2 🔴 `subgraph` V16c：两侧口径不一致（与 D72 同族，Phase 57 修 V18h 时漏了它）

```python
reg0 = V.stale_registry()                              # ← 含 A04 status（第 4 参）
n0   = sum(1 for e in all_e if Q.edge_is_stale(e, reg0))   # 32802
reg1 = Q.build_stale_registry(sr.ids(), hm2, rsm)      # ← 只有 3 参，无 A04
n1   = sum(1 for e in all_e if Q.edge_is_stale(e, reg1))   # 922
rep.add(n1 > n0 and n_ch > 0, ...)                     # 方向反了 ⇒ 红
```

正对照**含** A04 层、变异态**不含** ⇒ 两边不是同一个命题。
**A04 层贡献为 0 时它恒绿（什么都不守），A04 一有 stale 就假红** —— 这正是 D72（`V18h` 旧版）的原形状。
Phase 57 把 `V18h` 改成构造性判据时，**没有顺手检查同函数的 `V16c`**。

### 4.3 🔴 `grade` G5：103 条落盘评分未刷新

Phase 72 改了 **103 条**边的档位/证据 ⇒ 派生的 1—5 分随之变化，而落盘值还停在 `bbfb406`。
仪器自带提示已指明出路：**`bash sttp.sh gradepersist --apply`**。属**预期内的收尾遗漏**，不是新缺陷。

### 4.4 ★ 共同形状：又一次 D108

**D108：判据的价值 = 它被跑到的次数。**

- `subgraph` 在 Phase 63 之后**再没进过任何一轮的收尾清单**（指南里最后一次记录是 100/0/3）。
- Phase 72 的收尾跑了 `gatecheck / redprobe / evdeps / docnums / interpcheck / frontend / licence / dataset / release`，
  **唯独漏了 `subgraph` 与 `grade`** —— 而踩的坑恰好只有这两台能看见。
- 对照上一轮刚总结的 D107（「最易漏的入口是自己新加的出口」）：
  这次是 **「最易漏的仪器是上一次没跑的那台」**。

## 六、下一步规划（三选一，需你拍板）

> 按记忆规则：每个选项给「好处 / 未来的问题 / 我的选择 + 原因」。
> **未选之前不动工新阶段**；以下 A 是**修已有破口**，不是新阶段。

### A（推荐）· 先补纪律：重验 + 修 V16c + 刷新评分 · 约 1 天

1. 跑 `phase45_evidence_deps_delta` 重验，用当前验证器身份重算全部证据依赖，**生成新证据并保留旧证据**（A04 契约要求）；
2. 修 `V16c`：变异态也注入 A04 status（两侧同口径），并配红探针证明「不注入就红」；
3. `gradepersist --apply` 刷新 103 条落盘评分；
4. 把 `subgraph` + `grade` 补进**收尾必跑清单**（这是防止 D108 复发的唯一办法——加一条 `sttp.sh` 级别的守卫）。

- **好处**：把 32,583 条从 stale 清回 `needs_review`/valid（它们本来就不是"已变更"，是"验证器实现升级了"）；
  拆掉 `exclude_stale` 的自毁开关；14 台仪器真正全绿；**后续所有开发都有干净基线**。
- **未来的问题**：全图回写一次（35.5 MB 量级流程），需重跑全部仪器，发布样例/数据集数字可能随之变（要重出清单）；
  且每次改 `verification_model.py` 都要再走一遍 —— 除非把「改判级模型 ⇒ 必须重验」做成门禁断言（建议一并做）。
- **为什么选它**：**这两条红不是"数据错了"，是"该做的收尾没做"**。红着继续开发，等于让后面每一个 Phase 的
  「全绿」都带星号。而且 Phase 61 已经为同一件事 revert 过一次 —— 不修，第三次踩只是时间问题。

### B · 直接开新功能（F13 学科导航 + F12 空结果解释）· 约 3—5 天

- **好处**：**用户可见价值最直接**。F2 数据侧（`domain_tags` 跨域 84.3%）早已就绪，只差前端；
  F12 是外部评审最在意的一条（RC1-10）。做完原型才算真正兑现 M1 的成果。
- **未来的问题**：**建在红的基线上**。且前端每动一次要重跑 `frontend`(121) + `taskflow`，
  与 A 的全图回写撞车时会有一次返工（前端读的是图快照，重验后快照会变）。
- 不推荐作为第一顺位，但**可作为 A 之后的紧接着一项**。

### C · 开对外接口（F6 公式详情查询 + F8 子集导出 + F9 版本化）· 约 1—2 周

- **好处**：把「能被 `wget` 的数据集」推进成「能被查询的数据集」，是规划里"为未来训练模型/数据接口做准备"的正路；
  F5 已有 2,963/12,301 的底子，manifest 与 sha256 体系齐全。
- **未来的问题**：**F6 的"适用条件"栏只有 30 条有内容**（Phase 63 实测），接口契约会暴露这个空；
  而且接口一旦对外，就是**对外口径承诺**——重验后数字变动会变成破坏性变更，需要版本化配套（F9 得先做）。
- 不推荐现在做：**先有稳定基线，再谈对外承诺**。

### 我的排序建议

**A（1 天）→ B（3—5 天）→ C（1—2 周）**，另把 **F15/F16 工程治理（半天，低风险）** 插在 A 之后顺手清掉
（36 个 `_*.py` 归档 + 1.9 GB 本地冗余清单，**先出清单再删**）。
