**我的结论是：这轮调整有实质进步，项目值得继续作为收敛的研究原型推进；但还不能认定“可信性已经验收完成”。Apache 2.0 适合当前路线，建议保留，并补齐迁移和数据许可管理。**

最明显的进步，是从追求跨域边数，转向识别错误断言、划分验证范围、保留反例和披露指标分母。最大的剩余问题，则是部分验证仍把“文字出现、字段标记、同源数据的一致性”提升为更强的科学断言。它们会影响新的可信性指标，不能只靠增加测试数量解决。

我也修正上一轮规划的适用前提：项目文档已选择“路线 A：研究原型（收敛版）”。在这个定位下，下一阶段应以可复现研究、真实跨学科任务和方法比较为验收标准。付费客户、企业权限、SaaS 运维可作为后续选项，不应成为当前研发价值的必要条件。

**可信性方面，下一步需要修正的是验证语义，而不只是扩大案例数量。** 下列反例均为独立合成输入，用于证明当前函数允许错误或不足的证据通过；除明确引用 delta 的地方外，不代表已经证实完整主图含有同样数量的错误。

1. **化学门禁混用了 reaction SMILES 和 reaction SMARTS。**

   `gate_chem` 接受 `smiles` 或 `smarts` 字段，却统一调用默认 SMARTS 模式的 `ReactionFromSmarts`。在本机 RDKit 中，`CO` 被计成只有 C/O、没有 H；`[Na]` 还出现了不符合该 SMILES 含义的氢计数。于是旧反例虽然被拒绝，不能证明计数已经正确。

   两个已配平的 reaction SMILES：`CO>>C=O.[H][H]` 对应 CH₄O→CH₂O+H₂，`C=C.[H][H]>>CC` 对应 C₂H₄+H₂→C₂H₆，**都被当前门禁拒绝**。无论放入 `smiles` 还是 `smarts` 字段，结果相同。显式写氢的 `[CH3][OH]>>[CH2]=O.[H][H]` 则通过。这说明结果依赖输入写法，而不是稳定的计量判断。

   修复方向：明确输入格式；具体 SMILES 使用相应解析模式和分子校验，查询型 SMARTS 若无法确定完整计数则返回不可判定；不要把氢计数异常吞掉后按 0 继续证明。补充“同一反应的不同合法写法应同判”的测试，并同步修正 scope 文案。这里验证的是计量守恒，不是反应能否发生。[当前实现](F:/codex/sttp/STTP-review/04_验证闭环/verification_loop.py:96)；[RDKit 官方示例](https://www.rdkit.org/docs/GettingStartedInPython.html)展示了 reaction SMILES 的 `useSmiles=True` 用法。

2. **摩尔质量→能量的旧问题在另一入口仍存在。**

   `gnn_infer.py` 的 `gate_check` 仍匹配 `("mass", "weight", "energy")`。本次给出一个分子、一个名为 energy 的物理量，以及 18.015 g/mol 的计算结果，仍得到 `has_quantity / R-PHY / VERIFIED`。Part B 的修复没有覆盖 Part A。

   应把目标限定为语义明确的摩尔质量量类，并核对单位、数值和实体；不能只删除 energy 后保留任意 mass/weight 子串。所有生成入口都应调用同一个校验器，且落库前重验。[源码](F:/codex/sttp/STTP-review/09_科研扩展/9_inference/gnn_infer.py:635)

3. **“不同数据库”被当成了“独立证据”。**

   Phase 33/34 用 Rhea 方程与 ChEBI 名称、分子式、同义词匹配，将结果升为 `cross_source`，自动生成 `indep=True`。但 Rhea 官方明确说明，其参与物由 ChEBI 描述；Rhea 使用的名称还可能作为 UniProt 来源同义词进入 ChEBI。对于“该物质位于这条反应的哪一侧”这个断言，这条链可能是共享词典、甚至回流引用，不能仅按数据库名称不同认定独立。[Rhea 官方参与物说明](https://www.rhea-db.org/help/reaction-participant)

   这项匹配仍有价值：它可以检查实体映射、别名解析和方程侧别是否一致。但应标为相应的数据一致性检查；反应角色这一事实仍保留其原始文献/数据库依据。只有确认支持同一断言的另一证据不沿用该上游，才能进一步计为事实层面的独立支持。

   本地 delta 可确认 Phase 33 有 **2,773** 条、Phase 34 有 **1,218** 条 `equation_species_cross_source` 更新记录。这 3,991 条升级记录值得专项复审，**不能据此说它们都是错反应**。缺主图、完整血缘与独立标注时，我不直接给出“修正后的 T9-i”。[判定位置](F:/codex/sttp/STTP-review/11_真实数据/verification_model.py:1256)

4. **同分子式不足以确定具体反应参与物，旧风险换了位置。**

   `reaction_side_cross_check` 在名称未命中时，允许通过分子式单侧命中升级。本次用 dimethyl ether、分子式 C₂H₆O 去匹配只有 `C2H6O = acetaldehyde + H2` 的方程，仍获得 `cross_source / indep=True`。该式没有排除乙醇等同分子式异构体；“同侧只出现一次”也不能排除这种歧义。

   应优先使用 Rhea 的具体参与物标识及 ChEBI ID 对齐；结构键比较须处理立体化学、质子化态和泛称类。仅分子式命中应保留为候选，不能证明指定实体参与该反应。[源码](F:/codex/sttp/STTP-review/11_真实数据/verification_model.py:577)

5. **数学算子出现，被提升成了推导关系。**

   本次构造 `y=\log(x)+7` → `MA:fo:log_product` 的 `derived_from` 边，模型因看见 `\log` 而判 `rule_checked / log_rule_usage`，并附独立复算证据。看见对数只能说明使用了对数算子，不能证明该式由对数乘积公式推导而来。

   可把这种边改为 `uses_operator` 或更准确的概念使用关系；`derived_from` 要求显式变形步骤、前提条件及可重放的推导检查。类似地，出现微分符号不等于使用了幂函数求导法则。这些桥改名后仍有检索价值，无需为了保留边数而维持更强的关系名。[规则表](F:/codex/sttp/STTP-review/11_真实数据/verification_model.py:880)、[升级分支](F:/codex/sttp/STTP-review/11_真实数据/verification_model.py:1223)

6. **部分“复核器”仍信任上游标签或汇总字段。**

   两个不同 InChIKey 的节点，只要边带 `kind=pubchem_bridge`，当前分类器就可返回 `cross_source / inchikey_exact_match`；该分支没有重做键比较。另一项测试给出正确量纲、任意数值 `999999999`、`n_references=2`，没有提供两篇文献及各自测量记录，仍得到 `webbook_multi_reference_agreement`。

   WebBook 的摄入脚本确实包含文献值比较逻辑，这应肯定；问题是下游重新分类只信汇总标记，无法抓住落库后数值被破坏、文献缺失或依赖关系未证明的情况。把它称为“可独立重算”仍不充分。应在验证记录中引用不可变的输入记录及哈希，重新计算比较结果，或明确这只是沿用先前验证结果，并检查原验证记录未失效。[身份分支](F:/codex/sttp/STTP-review/11_真实数据/verification_model.py:1348)、[WebBook 分支](F:/codex/sttp/STTP-review/11_真实数据/verification_model.py:1176)

7. **量纲表修复了具体错误，但“真值表”来源仍需更扎实。**

   当前表主要从 PhysicsBabel 方程指数反解，基本量为边界条件。源码是逐个求解“恰有一个未知量”的传播过程，并未实现一般线性方程组的完整一致性检验；某个量一旦求出，其他已知量方程不会自动反证它。用这张表再核验同一批方程，包含同源自洽成分。

   建议以独立 SI/标准量定义建立小型权威基表，保留反解表作为待比较结果；每个量记录来源、维度约定和适用范围。当前 PB 节点仍写 `dimension=exp.get(k)`，应改为 `exponent_in_term`，真实量纲用独立字段，避免新旧语义混杂。[量纲构建](F:/codex/sttp/STTP-review/11_真实数据/dimension_table.py:60)、[遗留字段](F:/codex/sttp/STTP-review/11_真实数据/physicsbabel_ingest.py:95)

这些问题共同说明：**确定性程序也可能确定性地验证错了命题。** 更稳妥的设计是把“原子守恒通过”“表达式出现某算子”“实体键一致”“外部来源支持”“人工复核”分开存储，然后按发布断言的要求组合使用。七级标签有展示价值，但不宜成为所有事实类型通用的正确性排序。

证据“独立”至少要区分三件事：计算实现独立、数据来源独立、原始实验/文献独立。不同程序读取同一条记录可以交叉检查实现，但不会自动增加一份独立事实证据。建议记录来源之间的 `derived_from`、`imports_from`、共同文献 ID 和版本，而不是只保留一个布尔值。

还应把“95.8% 已到天花板”“数学桥约 40 条，不再投”“现有候选中不存在第二源”收窄为**当前样本、当前访问路径及当前规则下的负结果**。20 个访问探测、少量文献或一批映射未命中，能帮助停止低收益接入工作，不能证明科学空间或外部数据源已经穷尽。

**GNN 评测已经向前走了一步，但尚不能证明模型发现了有用的新知识。**

直接从训练集中再次抽测试样本的问题已经改掉；训练邻接、结构特征、关系类型掩码改为来自训练边，也是正确做法。

但切分在每种关系内部独立进行。对包含两种关系的同一批实体对，本次运行真实切分代码，得到三元组交集为 0，却有 **20/20 个测试实体对仍通过另一种关系出现在训练邻接中**。这是合成数据的可复现结果，不是完整 STTP 图上的泄漏比例。

**Apache 2.0 是合适的选择，但它帮助的是开放采用，不负责形成排他商业壁垒。**

MIT 和 Apache 2.0 都允许广泛使用、修改与商业分发。Apache 2.0 比 MIT 更明确地规定贡献者专利许可及相关终止条件，也要求分发时保留相应许可和署名。这适合希望科研团队、开发者和企业采用 STTP 的路线；这里的专利授权有范围限制，并非替你清除所有专利风险。[Apache 2.0 正文](https://www.apache.org/licenses/LICENSE-2.0)、[MIT 正文](https://opensource.org/license/mit)

使用者可以在遵守条件下做闭源衍生或商业服务，通常无须回馈修改；所以它不会阻止别人部署竞争服务。若你的目标是开放核心、研究合作、托管服务或企业集成，选择合理。若目标是强制所有改动公开、禁止竞争者商用，Apache 2.0 不满足这个目标。[Apache 官方 FAQ](https://www.apache.org/foundation/license-faq.html)

| 你的可能目标 | Apache 2.0 的适配判断 |
|---|---|
| 让高校、研究者复现和扩展方法 | 合适，重点补数据和评测可复现性 |
| 让企业集成验证器或知识接口 | 合适，许可范围较明确；数据权利仍单独核验 |
| 保留收费服务、支持和私有部署业务 | 可以，收入依赖服务能力和持续价值 |
| 靠禁止复制或强制付费授权保护核心代码 | 不合适，不能把已给出的宽松权限当收费门槛 |
| 防止别人使用 STTP 品牌冒充官方服务 | 需要品牌与商标治理；开源许可不是完整品牌策略 |

**当前迁移已完成基础声明，但还没有完成一个可靠发布包的许可整理。** 根目录已有 Apache 正文、NOTICE，README 徽标和自有源码 SPDX 头已更新；批量脚本明确跳过 vendor，且 vendor 文件相对旧版忽略行尾后的 diff 为空，没有发现把它们改标为 Apache 的情况。这些是正确方向。

**更新后的商业价值主要来自可信工作流和可复用验证能力，而不是现有图的规模。**

项目现在具备可发展成研究基础设施的几个积累：跨源适配器、量纲与组成检查、保留已知错误的回归机制、验证范围表达、证据展示。将这些能力做成可复用库和可复现实验，比直接宣称“自动发现数理化新知识”更容易获得研究合作和实际使用。

| 发展方向 | 当前适合程度 | 下一份应取得的证据 |
|---|---|---|
| 研究合作、课程项目、开放基准 | 最匹配当前路线 | 外部人员按文档复现实验；专家接受任务定义与判分 |
| 科学知识工程/数据核验工具 | 有潜力 | 同一验证接口接入第二个独立项目，减少人工核查时间 |
| 专题教学或科研资料助手 | 可做有限试点 | 在完整任务上比普通检索更快且可追溯 |
| 企业托管、集成、私有部署 | 可作为后续业务 | 有明确采购方、持续使用场景及交付成本记录 |
| 自动科学发现、药物研发结论系统 | 当前证据不足 | 独立基准、专家盲评、条件/不确定性建模及前瞻验证 |

尚未获得用户访谈、使用数据或付费意愿，不能据代码规模给出可靠收入或估值。建议商业验证先测三个量：一个真实任务节省多少时间、错误或遗漏是否减少、维护一个数据源需要多少工时。即使科学任务正确率较高，如果源维护成本超过用户节省的工作量，也未必形成可持续业务。

Apache 2.0 有利于别人试用和集成，但竞争者也可以复用代码。未来更可积累的优势是：高质量专家案例、版本化证据血缘、可复现评测、稳定更新流程和深入用户工作流的能力。当前建议优先建立这些资产，不把“改许可证”本身当作商业壁垒。
