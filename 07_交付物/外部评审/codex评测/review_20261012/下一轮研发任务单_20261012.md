**A01｜修复顶层发布入口的失败传播**

修改范围：`sttp.sh`、`06_PoC/release/verify_release.py`、`make_manifest.py`；尽量先用小改动完成。

任务：

- 对 `release-full / dimaudit / lineage` 每一步保留非零退出状态，失败停止后续发布步骤。
- 完整模式逐个检查规范图、展示投影、依赖与必要报告；核对各自哈希、路径和计数。
- 子进程非零、必需产物缺失、未执行的关键检查都必须阻断。
- 双投影用规范图哈希与转换器版本绑定；验证关系类型、关键属性和 evidence 引用的投影一致性。
- 构建清单与验证清单分离。验证不得改写 manifest 或数据。

验收：在隔离副本中分别注入缺规范图、缺展示图、坏哈希、子进程返回 1、必要依赖缺失、关键 SKIP、同 ID 错关系；从用户顶层命令执行，全部非零退出。正常样例和完整研究副本仍通过。日志明确指出第一处失败及所用版本。

**A02｜补齐判分器与工具的输入域**

修改范围：`12_评测/eval_runner.py`，后续抽取共享数值验证模块。

任务：统一拒绝 NaN、Infinity、错误数值类型；结构化答案逐字段验证有限性。按具体工具检查 T>0、K>0、Q>0、比值>0，校验单位和适用条件；把异常转换成可识别的工具错误，不能伪装成科学拒答。

验收：本次 DV-09、NM-05 NaN 反例不再判对；零/负温度不被普通平衡工具接受；缺条件与无效值分别返回原因；40 条旧题继续通过。增加有效边界附近的正例，避免“一律拒绝”导致假通过。

**A03｜让数据许可政策进入打包程序**

修改范围：`DATA_LICENSES.md`、机器可读的来源许可表、`make_sample.py`、manifest。

任务：为每个来源登记 `redistribution_status / license_id / attribution / field_scope / decision_source`；未决来源默认不进入公开包，派生记录递归检查上游。明确 `internal_research` 与 `public_demo` 两种 profile；公开包附实际来源清单。

验收：当前待核对来源及其受限派生项不会被公开 profile 选入；故意加入一条未决来源记录后构建失败；公开样例能够运行现有查询和适用回归。不得通过删除来源字段规避检查。

**A04｜从“来源绑定”升级到“验证依赖绑定”**

修改范围：`source_registry.py`、`phase41_lineage_delta.py`、`lineage_invalidation.py`、`verification_model.py`，增加版本化证据契约。

最小字段建议：

```text
claim_id + claim_version
conditions + conditions_schema_version
input_refs[] = source_id / record_id / content_hash
reference_refs[] = table_or_rule_id / version / content_hash
verifier_id + code_hash + dependency_versions
result + verification_scope + checked_at
status = valid | stale | needs_review | rejected
supersedes_evidence_id
```

任务：先允许按整个输入文件保守失效，再逐步细化到记录；输入、参考表或验证器更新都能传播。`--reverify` 需明确是摄入后的新规范图还是旧图，重验成功生成新证据并保留旧证据；单纯重写哈希不能恢复 valid。查询和答案默认排除 stale。

验收：分别变异原始数据、量纲表、元素表、验证器与依赖版本，能够定位所有登记的受影响证据；未受影响项保持原状态。旧实现版本反例失效。重验前答案停止引用旧证据；重验后可追溯新旧记录和判定变化。116 条历史模型血缘缺口继续显式展示，不伪造历史信息。

**A05｜形成第三人能安装的发布入口**

任务：解释器约束与 pip 依赖分离；核心依赖和 GNN/在线摄入等可选依赖分组。入口区分 `sample verify / sample serve / sample build / release verify --full`。从原开发仓库生成明确版本的包，记录源码、图、任务、验证器哈希；旧脚本保留薄包装兼容。

验收：干净 Windows 和 Linux 环境只按 README 能安装并运行随包公开样例；不依赖管理员目录、已有 `.env` 或 Aura。完整重建另有原始输入清单及命令。实际依赖漂移能被报告。此任务完成前不宣称已实现全流程干净重建。

**A06｜限制查询成本并保护关系语义**

修改范围：`03_知识层/queries.py`、`06_PoC/viz_server.py`。

任务：加入 max_paths、max_hops、max_expansions、deadline；返回每一步 edge ID 和 evidence ID，显式输出截断/超时状态；过滤 stale 和不适用关系。建立专题允许的关系组合，区分“存在关联路径”与“有依据的推理路径”。

验收：密集子图和多重边构造下不出现无界枚举；错误、超时、无路径可区分；最少一条错误关系被插入的路径能被拒绝。缓存以 snapshot_id 绑定，页面与 API 报同一版本。

**B01｜交付一个完整专题任务服务**

输入：问题文本或表单、数值和单位、物质/物相、温度与标准态。输出：answer / needs_input / refuse / error，加公式、步骤、单位、条件和来源。

第一批工具：K↔ΔG°；ΔG=ΔH−TΔS；ΔG=ΔG°+RT ln Q；必要的量纲/单位检查。将 method 视为系统选择结果，不能由盲测数据暗中提供。规则/表单即可完成初版，语言模型作为可选解析器。

验收：至少 10 个真实措辞场景全过程演示；包括三类条件缺失、同量纲异义和来源过期。用户更改关键条件后，方法、数值或拒答结果相应改变；导出可复核执行记录。

**B02｜建立独立评测与图谱增量证据**

立即启动独立出题和审核：建议 80 个新任务，20 开发、60 盲测，按公式模板/实体家族分组；原 40 题保留为单元回归。盲测隐藏 method、expected、拒答原因标签。

公平对照：规则＋表格/文本检索；规则＋图谱；可选 LLM＋工具＋图谱。数据来源与预算一致。记录任务正确性、证据支持、拒答、耗时、调用成本，增加无边图、错误关键边和过期证据对照。

验收：报告题集、来源、审题记录、切分哈希、软件/图版本、逐题结果和区间。若看过测试结果后修改规则，后续成绩标为回归结果，另换未见测试集。没有增量时允许结论为“当前场景用规则检索更合适”。

**B03｜实现以任务为入口的局部图谱界面**

页面布局：任务输入与条件；结果与计算步骤；证据卡片；局部关联图。节点卡包含量类、单位、条件、来源和状态，边标关系语义；支持只显示本次使用的证据链。原全图浏览保留作辅助视图。

验收：用户能定位答案中的每个关键数字和公式来源；能看懂为何拒答或要求补条件；版本和 stale 状态一致；不需要在数千节点中手工找入口。

**C01｜用真实任务决定是否继续产品化**

由项目负责人邀请 5—10 名同一类目标用户，完成难度配对的真实任务；邀请和外部沟通由负责人执行，本报告未发送任何消息。

记录：当前工作方法、任务频率、耗时、错误、是否点开证据、是否重复使用、愿意付费解决哪一段工作。建议累计约 100 次真实任务尝试，失败也计入。初步目标是中位耗时降低 30%，同时不增加关键错误。

决策：有持续价值再投入协作和私有部署；使用少但审计价值明确，可收敛为知识治理工具；若没有明确收益，重选用户或任务，不以扩图和换模型代替验证。
