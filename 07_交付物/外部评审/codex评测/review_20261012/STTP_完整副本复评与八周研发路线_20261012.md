**三、此次新发现的关键问题**

**1. 发布失败仍可能被总命令吞掉，应优先修复。**

[sttp.sh](F:/codex/sttp/STTP-review/sttp.sh:254) 的 `release-full`、`dimaudit`、`lineage` 分支没有像 `release`、`eval` 那样启用错误立即退出，也没有逐项传递退出码。例如发布校验失败后，如果最后的冻结门禁成功，Shell 最终仍可能返回 0。`lineage` 也可能在实际失效检查失败后，被最后一次自检成功覆盖。这里是静态代码确认，未执行 Shell 故障注入。

[verify_release.py](F:/codex/sttp/STTP-review/06_PoC/release/verify_release.py:276) 自身还有三处缺口：完整快照缺失只记 WARN；现算审计没有产出也只记 WARN；只核对展示快照哈希，没有逐一核对 manifest 中规范图的哈希。本次在内存中把完整快照路径改为不存在，`check_full` 返回 FAIL 0、WARN 1。

**处理方式：**把样例验证与完整发布分成明确模式；完整模式的必需文件缺失、哈希不符、子进程失败或关键检查跳过都必须非零退出。故障注入需要打到最外层用户命令，不能只证明底层函数会报错。构建与验收分离，验收时不能重建清单把错误数据“登记成正确”。

**2. 40 题是规则模块回归集，尚不是端到端能力测试。**

[eval_runner.py](F:/codex/sttp/STTP-review/12_评测/eval_runner.py:189) 直接读取任务内的 `method`，再把已结构化的 `inputs` 交给对应求解器。它没有从问题文本识别任务、抽取条件、选择方法的过程。

本次内存实验结果如下；原图与原题均未修改：

| 实验 | 判对数 | 说明 |
|---|---:|---|
| 正常规则基线 | 40/40 | 与项目报告一致 |
| 删除全部边，保留节点和参考表 | 37/40 | 只有 MS-03、MS-04、MS-06 失败；当前评测对关系结构不敏感 |
| 再删除全部节点，保留程序和参考表 | 25/40 | 仍能靠规则、参考表和预先指定的方法完成多数题 |
| 把全部问题文字替换成无意义句子，保留 method/inputs | 40/40 | 当前题目文本不参与求解 |

这不是“图谱无用”的证明。它说明这套题主要覆盖规则工具，不能验证系统自动选方法、组合证据或跨域推理的能力。现有 40 题应继续保留作回归集；新增的盲测题应经独立学科人员出题或审核，被测系统不能收到参考答案、解题方法标签和拒答类别。

评估还应增加公平对照：相同来源、相同信息预算下，比较“规则＋表格/文本检索”与“规则＋图谱”，衡量正确完成率、有效证据、时间和维护成本。不能把信息更多的系统与信息更少的基线比较，再把差异都归于图结构。

**3. 判分器与数值工具存在新的边界漏洞。**

[结构化数值判分](F:/codex/sttp/STTP-review/12_评测/eval_runner.py:519) 使用 `abs(got - expected) > tolerance` 判错。NaN 的比较不会进入该判错分支。本次把 DV-09、NM-05 的全部数值字段替换为 NaN，两题都被判为 `correct`。

[K 转 ΔG 的计算](F:/codex/sttp/STTP-review/12_评测/eval_runner.py:303) 只检测温度缺失，没有检测温度是否在该工具适用域内。本次输入 K=10、T=0 K 或 −298.15 K，程序都返回数值。对于当前普通化学平衡工具，应要求有限数值、T>0，并按具体工具约束 K、Q、单位与物相。

标准平衡常数关系中的量是标准反应 Gibbs 能和热力学温度；产品中还需要区分 ΔG° 与实际组成下的 ΔG、K 与 Q，不能仅靠字段名称里的简写承担这些语义。[IUPAC 标准平衡常数定义](https://goldbook.iupac.org/terms/view/S05915)

**处理方式：**求解入口和判分入口都验证类型、有限性、取值域和单位；NaN/Infinity 不能成为有效答案。把“条件不足”“无适用规则”“数值错误”分开。当前自检能识别普通扰动，但不涵盖这次发现的特殊数值漏洞。

**4. 证据已经有版本字段，但还没有完整的失效生命周期。**

[血缘分析器](F:/codex/sttp/STTP-review/11_真实数据/lineage_invalidation.py:72) 比对 `src_hash`，没有比对 `impl_ver`。本次把一条真实边的验证器版本标为过期，受影响断言数仍为 0。

更深的问题是，[Phase 41 绑定器](F:/codex/sttp/STTP-review/11_真实数据/phase41_lineage_delta.py:125) 给一条边的所有 evidence 绑定相同的“断言提出者来源”。例如某条 NIST 数据还经量纲表检查，证据源只记 NIST，量纲表没有作为该次验证的机器可读依赖登记。内存中模拟量纲表来源哈希变化时，当前失效器只定位 28 条边；另有 evidence 的 `impl` 明确提到量纲表的 NIST、种子等记录没有被这个依赖关系覆盖。这里证明的是依赖登记不完整，不能据此断言所有这些科学结论都已错误。

此外，`--reverify` 重验的是当前规范图上的判级并报告变化；没有自动把更新后的原始来源重新摄入，也没有把过期状态贯通到查询和答案。绑定器复跑会写当前哈希，因此它不应成为“刷新旧证据有效期”的替代手段。

**处理方式：**每次验证记录分别保存 claim、实际输入记录及其哈希、参考表及哈希、验证器和依赖版本、条件、检查结果。增加 `valid / stale / needs_review / rejected` 状态。输入或程序变化先标 stale，重新摄入和验证成功后追加新记录；默认查询和答案不使用 stale 证据。旧证据保留以便追溯。

**5. 演示数据打包与项目自己的许可政策不一致。**

[DATA_LICENSES.md](F:/codex/sttp/STTP-review/DATA_LICENSES.md) 明确把 PhysicsBabel、ElementKG、MathXiv 等列为待核对、暂不对外打包来源。实际演示样例的节点来源中包含 PhysicsBabel 4 个、ElementKG2.0 14 个、mathxiv 17 个、PubChem 7 个；边来源也包含相关数据。

[样例抽取器](F:/codex/sttp/STTP-review/06_PoC/release/make_sample.py:136) 依据学科和关系采样，没有调用机器可读的许可白名单。因此，“有数据许可说明”还没有变成“发布包遵守该说明”。这是一项可验证的内部政策执行缺口；本报告不据此认定这些来源实际禁止使用。

**处理方式：**先按当前政策排除待核对来源，或逐字段完成授权核对后更新政策；许可选择应追溯派生数据的上游，不能仅筛 `props.source` 表面名称。内部研究快照与公开样例分别构建，产物附自己的来源、许可与修改说明清单。

**6. 可运行副本与可独立重建的软件包之间仍有距离。**

README 的“无需完整数据”入口是 `bash sttp.sh release`，但它先运行 `make_sample.py`，后者默认依赖被 Git 忽略的 `normalized.json`。干净获取者应该先运行随包成品样例的校验和启动；“从全图重建样例”需要另一个命令。

完整数据获取说明中的 `sttp.sh export` 实际调用 Aura 导出器，生成的是展示格式，不能自动恢复规范图。[导出器格式说明](F:/codex/sttp/STTP-review/09_科研扩展/9_inference/export_aura.py:11)

`requirements.lock` 当前更像依赖版本清单：它包含 `python==3.11.9`，但 pip requirements 的每行描述的是待安装项目，不能用这个条目安装解释器；也未完整锁定传递依赖和所需安装源。本机 `.env` 的 Python 路径仍指向另一个 Windows 用户目录。发布检查器只检查关键包能否导入，并没有按文档承诺报告实际版本与锁的漂移。[pip requirements 格式](https://pip.pypa.io/en/stable/reference/requirements-file-format/)

**处理方式：**建立跨平台 Python CLI、解释器版本声明、核心依赖与研究扩展分组；给出能实际安装的锁和无原机器路径的配置模板。先验收成品快照重放，再独立验收“原始源→规范图”的重建；二者不要混为一个可复现等级。

**7. 查询层还需要转向“有限、带语义的证据路径”。**

[queries.py](F:/codex/sttp/STTP-review/03_知识层/queries.py:169) 仍将 `all_simple_paths(..., cutoff=5)` 完整转成列表。跳数上限不能保证路径数量有界；异常又统一变成空列表，会混淆“无路径”和“查询失败”。

目前返回节点路径，也不能单凭连通性证明每一步都是允许的科学推导。`uses_operator`、`same_as`、`cites`、`derived_from` 不应在解释里视为同一种关系。

**处理方式：**增加路径数、扩展节点数、跳数和执行时间预算；显式返回 `ok / no_path / truncated / timeout / error`。每步携带 edge ID、关系语义、适用条件和 evidence ID。先为专题规定允许组合的关系，保留拓扑浏览作为浏览功能。

**四、项目结构与发展方向的判断**

当前目录按 Phase、工作层和交付历史组织，适合探索和留痕。问题在于可运行产品、一次性修复、历史快照和实验报告混杂；一个新贡献者难以快速知道哪个模块是当前权威入口。188 个 Python 文件和约 5.39 GB 本地内容已经超过“靠目录记忆维护”的舒适范围。

对规划目标应分层判断：有限专题的可审计查询与计算，在现有基础上具备较高可行性；通用跨学科科学推理尚无充分证据；自动发现有价值的新科学关系仍属于研究问题。图中按当前学科分类，物理 5,247 节点、化学 4,108、数学 277、跨学科 25，也还不是覆盖均衡的数理化知识体系。量纲相容、原子守恒和拓扑连通都是特定检查，不能单独推出公式、反应或推导在现实条件下成立。

建议渐进整理，先抽核心，不进行全库重写：

```text
src/sttp/
  schema/         实体、断言、条件、证据契约
  ingest/         当前支持的数据源适配器
  verification/   数学、化学、量纲与失效管理
  query/          有限检索与证据路径
  tasks/          任务解析、条件检查、方法选择、工具执行
  release/        打包、许可筛选、清单与验收
  cli.py          统一命令入口
data/
  sources/        版本化输入记录与来源清单
  releases/       不可变规范图与专题发布物
benchmarks/       模块回归、公开开发题、独立盲测协议
experiments/      GNN、候选生成和探索脚本
docs/archive/    Phase 历史报告与迁移记录
```

这是建议结构，不是本次已经实施的改动。第一阶段只抽取 schema、release 和 verification；旧脚本做兼容入口。每迁移一组模块，对相同输入核对图、证据和输出指纹，防止目录整理改变语义。

第一版产品建议定位为：**“帮助物理化学学习者、教师或研究助理完成有限的公式选择、条件核对、计算和证据追溯。”** 先选择其中一种主要用户，通过试用确认任务频率。

首批用户流程应包含：

1. 输入问题或使用结构化任务表单，识别目标量、物质、物相、温度、单位和标准态。
2. 列出已知条件与缺失条件，必要时请求补充；缺证据时明确拒答。
3. 选取允许的公式或计算工具，展示选择理由和适用范围。
4. 返回数值、单位、步骤、来源定位、数据版本以及证据有效状态。
5. 在局部图中查看所用公式、参与量和证据关系，并导出可复核的任务记录。

建议先交付三个场景：K 与 ΔG° 换算及边界检查；由 ΔH°、ΔS°、T 或 Q 判断相应 Gibbs 能；追溯某个常量、公式或实体映射的依据。酸碱多物种、活度模型和复杂平衡系统留待条件模型成熟后增加。

polytech-tree 可借鉴的唯一事实源、数据/视图分离和来源治理，在新版本里已经开始落地。下一步把这些机制用于“问题—条件—方法—证据—答案”的局部导航即可；3D 全图效果不应占据本轮关键路径。

**五、未来八周怎么做**

以下为建议排期，假设有 1 名主要研发人员、每周固定的学科审查时间，以及必要的兼职前端支持。若只有一人并且缺少学科评审资源，按相同依赖顺序拉长到约 10—12 周更稳妥；外部评审不能由增加自动化次数替代。

前两周是容量目标，任务单中的工时上界可能超过两周：若证据迁移或干净安装耗时超出预期，延后界面工作，不以跳过验收维持日历日期。

| 阶段 | 目标与具体交付 | 退出条件 |
|---|---|---|
| 第 1 周：发布基线可靠 | 修退出码链、完整清单验证、NaN/数值域；区分样例运行与重建；建立许可白名单；冻结当前研究副本 | 顶层命令的缺文件、坏哈希、失败子进程和 NaN 注入均能阻断；原 108 条回归保持通过 |
| 第 2 周：证据可失效 | 证据登记真实输入与程序依赖；过期状态贯通查询；完成可安装核心依赖与跨平台入口 | 修改原始记录、参考表、验证器分别定位受影响断言；过期证据不进入默认答案；干净机器可以运行公开样例 |
| 第 3—4 周：完成一条用户任务链 | 建条件模型、结构化任务入口、方法选择器、受控计算工具、证据路径和结果卡片；同步准备独立评测 | 从用户输入到答案全过程无需评测文件提供 method；可作答、需补条件、拒答三类流程完整；查询有预算 |
| 第 5—6 周：验证增量价值 | 独立人员审核盲测；比较表格/检索、规则、规则＋图谱；逐题记录失败原因；形成可复核报告 | 达到下述独立任务目标；图谱的优势或无优势均如实报告；不根据盲测结果修改后再沿用同一测试集声称泛化 |
| 第 7—8 周：小范围用户试用 | 5—10 名目标用户试用；记录真实任务、耗时、错误、证据使用和回访；准备可复用专题包 | 至少一个明确用户群愿意持续使用；确认节省的是哪一段工作，以及用户能否接受维护/服务模式 |

第 1 周不要同时安排新数据源、GNN 调参和全图界面重写。每个研发任务都应具备输入、输出、失败模式和验收数据，并能直接关联一个用户场景或发布风险。

**建议冻结三个里程碑：**

- `v0.2.0-reviewable`：发布、许可、依赖与证据失效机制闭合；第三人可安装和运行。
- `v0.3.0-thermo`：三个专题场景端到端可用，能够解释条件、方法和证据。
- `v0.4.0-pilot`：独立评测与用户试用形成报告，再决定扩学科、训练模型或产品化。

版本号是建议命名，尚未创建任何 tag 或发布。

**六、知识库如何扩建，以及怎样证明扩建有效**

知识库增长应由任务缺口驱动。先把能够回答三个场景的最小专题包做好，逐条登记公式条件、量类、量纲、单位、来源与冲突。遇到解不出的真实任务，再判断缺的是事实、条件、映射、验证器还是方法，最后决定是否增加数据源。

每周维护一个“失败任务→所缺知识→新增记录→验证结果→重新完成任务”的闭环。不要把节点总数、连通率或新增来源数量设为研发主指标。旧的 99.65% 可继续作为数据治理健康指标，与用户任务效果分栏展示。

独立任务集建议保留现有 40 题作开发回归，另准备 80 题新任务：20 题用于新场景开发，60 题按问题家族、实体和公式模板分组后盲测。由独立学科人员审核答案、条件和证据；不能把同一题仅换数字后分到两边。60 题仍是早期样本，需要同时报告置信区间和分类型结果。

新增任务至少包括：跨实体别名定位；两个同量纲但意义不同的候选；需要两步以上受约束关系才能选择方法的任务；证据冲突；来源过期；参数或标准态缺失；替换错误关系后应拒答的任务。为每个正例配一个只改变关键条件的反例。

| 指标 | 建议试点门槛 | 测量方式 |
|---|---|---|
| 独立专题任务正确完成率 | ≥90% | 固定测试版本、经审核答案、逐题核查；不是现有 40 题分数 |
| 作答中的证据支持率 | ≥95% | 人工核查证据是否支持实际结论与条件，而非仅检查是否存在引用 |
| 已知关键反例误答 | 0 | 纳入发布门禁；同时披露独立未知反例中的错误率 |
| 对应输入/证据/程序版本绑定 | 100% | 每个可发布答案有 snapshot、input、verifier、evidence 标识 |
| 有效证据筛选 | stale 证据默认使用数为 0 | 对真实路径做更新与失效注入 |
| 交互性能 | 本地已缓存查询 p95 ≤2 秒 | 固定机器、图版本和至少 100 次代表性请求；模型/网络等待另报 |
| 用户效率 | 完成同类任务的中位耗时降低 ≥30% | 难度配对、顺序交叉、记录失败任务；这是待验证目标 |

这些数字是建议验收目标，不是项目已经达到的结论。如果图谱没有提高正确率，但显著降低证据追溯或维护时间，也可以保留其价值定位；需用相应实验说明。

LLM 第一阶段可以协助理解输入、提取条件、提出方法候选和生成解释，但答案中的计算、引用和验证状态由受控工具及证据记录决定。评测应分别计量解析、选法、检索、计算和解释错误，避免一个总分掩盖根因。

商业上，项目目前具有潜在的基础软件和知识治理价值，但没有看到付费、留存、节省工时或采购记录，不能据代码和图规模判断市场已成立。比较适合先验证的价值主张，是“缩短专题公式查证与证据整理时间”“减少单位、条件和版本错误”“让团队维护可复核的专题知识包”。

建议优先接触一个小型教学或研究团队，以专题工具、证据审计和知识包维护服务获得使用反馈。教育场景可降低首次试用门槛，科研场景更可能重视来源和版本；哪一方愿意付费，必须通过真实任务和访谈决定。先不设市场规模、收入预测或未经验证的价格。

如果 5—10 名试用者完成真实任务后仍没有持续使用理由，优先调整产品入口或问题范围；不要用更多图数据替代需求验证。如果有持续需求，再考虑团队协作、私有数据导入、部署支持和维护服务。
