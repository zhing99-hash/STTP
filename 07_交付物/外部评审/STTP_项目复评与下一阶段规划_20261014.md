## 1. 结论

项目已经从“知识图谱资料集合”进化为一个具有明确数据契约、来源登记、验证状态、局部图查询、离线样例和评测框架的**可审计跨学科公式知识图谱研究原型**。这次版本最明显的进步是：大图不再要求浏览器一次性加载；发布样例可独立验证；查询设置了节点、边、跳数、时间和会话预算；证据新鲜度与验证依赖开始进入数据模型。

当前版本还不适合直接面向普通用户公开推广。阻塞推广的主要原因不是图谱规模，而是发布基线和前后端集成：工作目录相对当前 Git HEAD 有 272 个已修改文件和 128 个未跟踪文件；全图证据状态因此出现 35,018 条 `stale`；浏览器实测发现冷启动误判离线、搜索参数丢失、路径查询契约不一致。这些问题会让首次体验者误以为“系统没有数据或不能工作”。

建议将下一阶段定义为 **RC1 可演示版本收敛**，先用 3—5 个研发日关闭 P0，再开展推广。完成 RC1 门禁后，项目可以用于科研展示、教学演示、方法论交流和合作方评审。若要发展成面向普通用户的产品，还需要继续实现任务式工作台，把“看图”转为“提交问题—返回结论、证据和局部图”。

## 5. 关键问题

### P0-1：发布版本没有形成干净、可追溯的 Git 基线

当前工作目录存在 400 项变更，其中 272 项已修改、128 项未跟踪。`contracts/`、`pyproject.toml`、`sttp_cli/`、验证依赖表和大量评测资产都没有进入当前 HEAD。项目的证据忠实度策略明确以 `git cat-file HEAD:<path>` 读取权威字节，因此“代码和数据已经在目录中”并不等于“验证系统认可它们”。

实际后果：48,712 条边中仅 234 条显示 `verified`，1,274 条显示 `changed`，121 条无来源，47,083 条来源未入库；A04 状态为 0 条 `valid`、35,018 条 `stale`、165 条 `needs_review`、13,529 条无记录。

**处理：** 建立 `release/rc1` 或同等候选分支；只提交要发布的源代码、契约和可合法分发数据；清理生成物与临时文件；在该提交上重新生成注册表、A04 记录、样例、清单和哈希。所有门禁必须在干净克隆中执行。

### P0-2：首次加载可能被误判为离线

前端探活对 `/api/stats` 使用 2 秒预算并在 250 ms 后中止连接。全图首次统计需要加载和聚合数据，浏览器会先中止请求，然后进入离线降级；服务端日志出现客户端断开。第二次刷新因后端已预热才恢复正常。

**处理：** 新增只返回进程、快照和后端状态的轻量 `/api/healthz`；启动时异步预热统计缓存；前端把“后端启动中”作为独立状态，允许 10—15 秒渐进等待，不立即尝试下载大于 8 MB 的全量图。

### P0-3：搜索框没有发送 `q`

`api.js` 将 `q` 传给 `buildParams()`，但 `core.js` 的 `buildParams()` 没有写入 `q`，并自动补入 `mode=ego`。真实请求成为 `/api/search?limit=20&mode=ego`，服务端返回 400。界面又把错误和空命中统一显示成“没有匹配”，进一步掩盖故障。直接调用 `/api/search?q=manifold&limit=5` 可得到 2 条命中，说明数据和后端搜索正常。

**处理：** 在参数构造器中显式支持 `q`，并允许端点声明自己的参数白名单；搜索组件分别呈现 `error`、`timeout`、`no_result`。新增浏览器级断言：输入 `manifold` 必须发出含 `q` 的请求并显示至少一条结果。

### P0-4：路径查询前后端契约不一致

前端调用统一 `/api/subgraph`，传入 `mode=path&src=...&dst=...`；该端点只读取 `seeds`，因此两端点始终缺少种子。服务端已经有 `/api/path?src=...&dst=...`，直接调用示例两点返回 `truncated` 和 3 条路径，证明后端算法可用。

**处理：** 二选一并写入契约：A）前端改调 `/api/path`，在 API 适配层把 legacy 返回映射为统一信封；B）`/api/subgraph` 在 path 模式读取 `src/dst` 并在响应中加入 `paths`。推荐 B，减少两套路径协议长期漂移。新增端到端路径测试。

### P0-5：验证脚本对未入库依赖缺少稳健处理

验证依赖自检发现 4 个参考依赖无法取得仓库哈希；谱系自检随后把 `None` 当作字节串使用并抛出 `TypeError`。即使未入库本身应导致门禁失败，自检也应输出结构化失败原因而不是崩溃。

**处理：** 先把合法且必要的依赖文件纳入 RC1；同时为 `repo_blob()` 返回 `None` 增加显式分支，输出 `dependency_not_in_repo`。

## 6. 其他重要改进

1. 默认筛选预算从 500 节点/2,000 边降到 40/70，最大首屏不超过 60/100，默认超时提高到 5—10 秒。当前默认请求在真实浏览器中超时，而 50/100/10 秒可在约 63 ms 返回 50 个节点和 72 条边。
2. 成功请求必须清除上一个错误横幅。当前一次预算失败后，后续成功结果仍可能残留 `SUBGRAPH_LIMIT_REACHED` 提示。
3. 增加 Playwright 或等价真实浏览器冒烟测试，覆盖冷启动、搜索、筛选、路径、导出、返回上一步和重置。纯函数测试不能代替协议集成测试。
4. 在 Windows 启动脚本中固定 UTF-8，避免中文输出触发 GBK 编码异常。
5. 在 Python 3.11 的干净环境执行 editable install、wheel 构建、命令行入口和离线样例验证；不要使用当前已经失效的 `.env` 解释器路径。
6. 项目指南应区分“研究原型能力”“演示能力”“产品能力”，避免把计划中的任务工作台写成已经实现。

- 交付可解压运行的样例包、标准用户流程和 5 分钟演示脚本。

**退出条件：** Git 工作目录干净；发布样例、来源注册、验证依赖、谱系、子图、安装和浏览器测试全部 0 失败；首次打开无需刷新；搜索和路径均可用。

### 阶段 B：可推广演示版（1 周）

- 首页只提供三个入口：按问题开始、浏览示例、查看方法与数据边界。
- 预置 6—10 个跨域任务卡，优先展示“量纲检查”“公式解释”“两个概念的关系”“证据追溯”。
- 结果页固定为：结论、依据、局部图、限制与拒答原因、导出。
- 样例模式作为公开默认入口；全图模式面向研究者并明确加载与验证边界。
- 制作截图、短视频、FAQ、版本说明和可复现声明。

### 阶段 C：任务式工作台 MVP（2—4 周）

现有前端仍以图浏览器为中心，尚未实现此前规划的 `TaskDraft`、任务 API 和工作台流程。建议先实现三类确定性任务：

1. **量纲/单位一致性检查**：用户粘贴公式或选择图中公式，返回通过、冲突或证据不足。
2. **概念/公式证据查询**：用户输入自然语言关键词，返回最多 5 个候选、一个结论和不超过 40 节点的局部图。
3. **两点关系路径**：用户选择起点和终点，返回有限条路径及每条边的来源和状态。

后台为每个任务提供版本化 JSON Schema；前端不直接拼接任意图查询参数。这样 WorkBuddy 可以围绕稳定契约生成页面，避免再次出现搜索和路径参数漂移。

### 阶段 D：科学证据增强（并行 2—6 周）

- 将 40 项同源规则回归集拆成开发集、冻结测试集和外部专家集。
- 引入至少一名独立学科专家复核，记录分歧、修订和不可判定案例。
- 增加图结构消融：删除关键证据边后任务应明确降级，避免“删掉全部图边仍有 37/40 通过”的弱依赖现象。
- 报告 Wilson 区间、任务覆盖、失败分类和版本哈希，不把 40/40 表述为普遍科学推理正确率。

## 8. 对外定位与商业价值

短期最有价值的定位是“可审计、可复现、能拒答的跨学科公式知识图谱研究基础设施”，可服务高校课程、科研数据治理、公式与量纲审计、知识库建设咨询和行业 PoC。它的差异化来自来源链、验证状态、边界表达和离线可复现，而不是节点数量。

中期可形成三类产品能力：面向教师和学生的公式关系学习工具；面向科研团队的证据追踪与公式一致性工作台；面向企业知识工程团队的图谱构建、验证和发布工具链。商业化前必须补齐用户任务闭环、权限与项目隔离、持续更新、质量 SLA、独立评测和第三方数据授权。

推广用语建议固定为：

> STTP 是一个可审计的跨学科公式知识图谱研究原型。它通过有界局部查询展示公式、概念、量纲、单位、化学实体和文献之间的关系，并明确给出来源、验证状态与拒答边界。

不要宣称“已经实现通用科学推理”“所有边都经过权威验证”或“40/40 等于真实场景 100% 正确率”。
