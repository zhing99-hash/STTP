## 0. 一句话结论

**D1 的根因不是「某个文件的字节不对」，而是「判据读错了字节源」**：`stale` 原先拿
**工作区（worktree）文件字节**当证据字节，而本机 `core.autocrlf=true` 会在检出时把 LF 改写成 CRLF，
于是**干净检出下哈希必然对不上** —— 判据的有效性依赖于「文件是怎么被 checkout 出来的」。
本轮把权威字节源改为 **`git cat-file blob HEAD:<path>`**（与检出/行尾无关），并同时把
「不可判定」从一句话拆成**可加总回边总数的四分类**。

实测：**`changed` 760 → 0**；干净 clone 与主工作区**逐值相同**；
`stale` 口径**保持不变**（= `changed` + `unverifiable_no_source` = **121**）。

## 1. D1 的本体与真实量级（先测量，再修）

### 1.1 判据原文（修复前）

```
stale ⇔ ∃ 证据 ev: ev.src_hash ≠ 当前内容哈希(ev.src)
当前内容哈希(sid) ← sha256( worktree 上该来源 locator 的文件字节 )      ← ★ 就是这里
```

`ev.src_hash` 是**生成时刻**记下并入库的存档值；判据把「此刻磁盘上的字节」当成「此刻的真相」。
问题在于：**磁盘上的字节由 checkout 决定，不由仓库决定**。

### 1.2 实测（本机 · 修复前）

| 项 | 实测 |
|---|---|
| 登记来源 | 31 |
| `locator` 文件（去重） | 34（21 已入库 / 13 未入库，后者被 `.gitignore` 的 `*_raw.json` / `*_cache.json` 挡掉） |
| 已入库 locator 中 **worktree ≠ blob** | **7/21**（`06_PoC/sample_mathxiv.json`、`10_种子数据/seed_{biochem,inorganic,math_calculus,math_numbertheory,organic_chem}.json`、`11_真实数据/seed_papers_openalex.json`）—— 差异**纯为行尾**（worktree CRLF / blob LF） |
| 受影响来源（旧口径下假阳） | 4：`cross_source_alignment`、`curated_seed`、`mathxiv`、`openalex-topic-align` |
| 旧四态 | `verified 776 ｜ changed 760 ｜ unverifiable_no_source 121 ｜ unverifiable_not_in_repo 47 055`（Σ = 48 712 ✓） |

## 2. 方案取舍（为什么这样修，以及不这样修的理由）

### 2.1 三个候选

| 方案 | 做法 | 裁决 |
|---|---|---|
| **A（采用）** | 权威字节源改为**仓库 blob**；`git` 不可用 ⇒ **`None`（fail-closed）**，绝不退化为空字节 | ✅ |
| B | 只把 `.gitattributes` 补齐（让 worktree 字节 ≡ blob） | ❌ 作为**根因修法**不成立：判据仍然依赖「用户怎么 checkout」（`-text` 是仓库属性，但 `--no-filters`、`core.autocrlf`、外部工具改写都不受它约束）。**已在 §5 作为附带项做了**，但它是**卫生**，不是**根因** |
| C | 把存档 `src_hash` 全部重算成 worktree 口径 | ❌ 方向反了：干净 clone 上根本没有那些字节（13/34 locator 未入库），只会把不可判定伪装成可判定 |

### 2.2 ★ 为什么 `unverifiable_not_in_repo` **不计入 `stale`**（本设计最关键的一处判断）

12 个来源的 locator 是**未入库的大体积拉取缓存**（约 20 MB，按「大体积派生对象不入库」有意排除），
牵连 **47 055 / 48 712 = 96.6%** 的边。**`stale` 若把它们并进来**：

- `stale` 会从 121 变成 47 176 ⇒ **信号被淹没**；
- `exclude_stale=true` 会变成「几乎什么都别显示」——**一个开关如果它的效果是"清空"，那它就不是开关，是自毁**；
- 而且它们在语义上**并未变更**：判据能说的最多是「我读不到它」，**不等于**「它变了」（铁律 #30 的反面）。

故：**静态分列**（`repo_status` 是来源的**固有属性**，不随此刻字节变化），
`stale` 只收 `changed`（真变了）+ `unverifiable_no_source`（连 locator 都没有 ⇒ 无从复核，fail-closed）。

**但绝不静默**（否则「stale≈0」会被读成「证据都可字节复算」）。四分类在以下位置**始终可见**：

- `/api/stats`：`evidence_fidelity` + `source_repo_status` + `evidence_byte_source`；
- `/api/subgraph`：`stats.evidence_fidelity`（本次）与 `stats.evidence_fidelity_global`（全图），
  且**每条边**都带 `fidelity` / `fidelity_reasons`；
- 前端：状态行四分类 pill、证据卡横幅、图例（并明确标注「需上游」**不**着色）。

### 2.3 回填策略（`phase41_lineage_delta.py`）

| 来源类别 | `src_hash` 处置 | 条数 |
|---|---|---|
| **已入库**（`in_repo`，10 个来源） | 用**仓库字节摘要覆盖**旧值 | 改动 **760** 条 |
| **未入库**（`not_in_repo`，12 个来源） | **保留**生成时刻的存档值（**不覆盖成 `None`**） | 保留 **47 655** 条 |

为什么保留而不清空：那个值是 R10 在**有缓存的环境**里**唯一**的复核依据；
且它的裁决由 `repo_status` **静态分列**（`unverifiable_not_in_repo`），那个值**从不参与比较**
⇒ 保留它**没有任何**假阳风险，反而保住了能力。

### 4.3 ★ 负对照：怎么证明「判据确实能动」而不只是"恒绿"

这是本轮**最花功夫**的一处，也是原来那条断言**必须改写**的原因。

**(a) 旧的 V16 断言过期了。** 旧形式是「改一个被登记的文件 ⇒ `stale` 增加」。修复后
**worktree 变异不再影响裁决**（这正是 D1 要的性质）⇒ 旧断言**测的是旧缺陷**，修好之后**必红**。
—— 一个断言在缺陷修好后变红，**不是回归**，是断言过期。**必须改写，不能保留**。

**(b) 拆成两件互不替代的事：**

| 断言 | 内容 | 实测 |
|---|---|---|
| V16b | **D1 性质**：向 `06_PoC/sample_mathxiv.json` 追加字节 ⇒ 服务端 `stale` **不变**（走真 HTTP 路径） | 2 → 2 |
| V16c | **非真空**：把某个已登记来源的**当前哈希**翻成 `0×64`（等价于"该来源文件真的变了"）⇒ 相关边必须由 `verified` 翻成 `changed` | `stale 121 → 819`，`changed = 698`（来源 `Phase13.Gate.B5`，被 734 条边引用） |
| V16d | **缓存键敏感性**：键 = `(HEAD sha, …)`；monkeypatch `_head_sha` ⇒ 键必变（且键里不含 `mtime/size`） | 键已变 = True |
| V16g | **两口径可构造差异**：临时仓库里造「blob=LF / worktree=CRLF」⇒ 两种 `byte_source` **必须**给出不同哈希，还原后**必须**重新相等 | differ=True / restored_equal=True |

**(c) 为什么 V16g 必须是"构造"而不是"观测本机"。** `byte_source_divergence()` 读的是**本机工作区**；
干净 clone 下工作区字节 ≡ blob（`.gitattributes` 保证）⇒ 该函数**必然**返回空。
若把「差异非空」当作口径有意义的**唯一**证据，那这条论证在任何干净环境里都会退化成 SKIP ——
**等于在最需要它的地方失效**（铁律 #65：结论必须有消融对照）。
故 `source_registry.divergence_probe()` 在临时仓库里把差异**造出来**，
使 ⑭ / ⑤ / V16g 在**任何机器**上都能给出 PASS/FAIL，而不是 SKIP。

### 4.4 差分口径（自检 ①）：一个真实踩到的坑

同一个文件**被两个来源以不同字节源记录**是允许的：`11_真实数据/seed_papers_openalex.json`
同时是 `openalex`（**未入库** ⇒ 记录的是**工作区**字节）与 `openalex-topic-align`（**已入库** ⇒ 记录的是**仓库**字节）
的 locator。单个临时仓库**无法同时复现**两种字节 ⇒ 直接断言「工具判定 == 独立期望」会**多报 `openalex`**。

处置：**差分口径** —— 先取未变异基线，再断言**新增**的变更集合相等。
结果：**期望 7 797 / 命中 7 797，差 0**，并透明打印「镜像固有基线（非变异）: ['openalex']」。

另外两个坑（都已修，都写进注释）：
- 临时仓库 `git add` 必须带 `-c core.autocrlf=false -c core.safecrlf=false`
  —— 否则 add 时归一化行尾，把"字节源差异"误报成"来源已变更"（第一版就是这里假红 13 个来源）；
- 提交后必须 `source_registry.clear_git_cache()`
  —— `_GIT_CACHE` 的键是 `(base, git args)`，**不含 HEAD sha**，HEAD 变了还在读旧 blob ⇒
  失效检测**静默失灵**（铁律 #38 的反面：PASS 掩盖了"根本没测到"）。

### 5.3 D26：行尾策略从「逐路径白名单」改为「兜底 + 例外」（已修）

**问题**：`.gitattributes` 原来只锁 `*.json` / `11_真实数据/*.py` / `06_PoC/js/*.js` / `graph_view.html`。
**白名单的失效方式是必然的**：干净 clone 里其余文本被写成 CRLF，而 blob 是 LF
⇒ `sha256(clone 文件) ≠ sha256(blob)` —— 铁律 #61「字节可复现」在这些文件上**不成立**。
实测漏网 **17 个文件**：`.gitignore`、`LICENSE`、`NOTICE`、`env.ps1`、`*.env.example`×2、`*.cjs`、
`06_PoC/vendor/*.js`×4、`*.bak`，以及 `03_知识层/queries.py`、`06_PoC/viz_server.py`、
`06_PoC/tests/phase43_*.py`×2、`sttp.sh`。

**修法**：置顶兜底 `* text=auto eol=lf`；例外（`*.json -text`、`*.lock -text`、

## 10. 收尾补记（同一轮内追加；终测 HEAD `f173eae`）

### 10.1 ★ 新发现问题 **E8**：测量口径陷阱 —— `--path` 与 `--no-filters` **互斥**

收尾复测「工作区字节 == 仓库 blob」时，脚本写成
`git hash-object --no-filters --path=<f> <f>`，结果**446 个入库文件全部判为「不一致」**。

**根因**：本机 Git 明确拒绝这两者同时出现 ——

```
error: Can't use --path with --no-filters
usage: git hash-object [-t <type>] [-w] [--path=<file> | --no-filters] ...
```

且该次调用**stdout 为空**。脚本只读 stdout、不查退出码 ⇒ 拿到**空哈希**，
与 `git rev-parse HEAD:<f>` 必然不等 ⇒ **全红**。改用正确写法后：**446 / 446 一致，RC=0**。

**两个命令回答两个不同问题（必须分清）**：

| 问题 | 命令 | 用途 |
|---|---|---|
| **工作区原始字节** == 仓库 blob？ | `git hash-object --no-filters <f>` vs `git rev-parse HEAD:<f>` | **D1 / D26 要的就是这个** |
| **`git add` 会存成什么** == 仓库 blob？ | `git hash-object --path=<f> <f>`（过滤后） | 判断「索引是否会脏」，**不是**字节忠实性 |

**教训（计入文档）**：这是铁律 **#38「PASS ≠ 无红」的镜像 —— 全红也可能是测量器坏了**。
凡「全量比对」类脚本必须先跑一个**已知一致的样本**自证测量器可用（本项目已有的同类纪律：`F29d` 的误命中、
`gatecheck` 的「正对照 PASS + 注入缺陷 FAIL」双断言、`source_registry` ⑭ 的构造性对照）。
本轮把它升格为铁律 **#76**。

### 10.6 ★ 收尾自身踩坑：**改写入库文件时引入 CRLF**（新铁律 #77）
