## 0. 摘要

**本轮本来只做一件事**：把交付给用户的《STTP 测试清单》§3/§4/§5 的期望值按 Phase 49 的新默认值同步。
按"用户可见期望值必须实测、不得照抄"的纪律逐条重测时，撞到一个**用户可见的事实性错误**：

> 路径条 / 状态栏显示的 **「已隐藏 N 条低可信度边」** 里，N 是**遍历过程中的判定次数**，
> 不是被排除的**不同边数**。实测 N 可以达到 **62,640**，而全图**总共只有 48,712 条边** ——
> 一个"条数"比"全部条数"还大，是可判定的假。

**影响面**：`mode=path`（页面底部路径条）与 `mode=ego`（点进子图）的 `stats.hidden_by_trust`；
`filter` 模式不受影响（它单遍扫描 `idx["edges"]`，本来就天然去重）。前端把该字段渲染成
「已隐藏 N 条」并直接用作文案断言（`main.js` 的 `no_result` 分支、`panels.js` 的状态行）。

**修法**：把计数变量从 `int` 计数器换成**边 id 的 `set`**，对外一律发布 `len(set)`。
另附 5 条断言（V20a–V20e），其中 V20c 是**负对照**（证明"用计数器必然虚高"，防止将来回退）。

**性质**：本项目对外口径的**事实性**缺陷（不是风格问题、不是已知边界）。计为 **P1**：
它不改变返回的图（nodes/edges/paths 都对），但它**对用户说了一个假数**，而且这个假数
恰好是用户用来判断"我的通路是不是被过滤掉了"的依据 —— 正是本项目最反对的那类结论。

## 1. 发现路径（为什么会在"同步文档"时发现代码缺陷）

按纪律，交付文档里的期望值必须**实测**。测到 §5 路径查询时，我用的是页面路径条的真实参数
（`mode=path`、`max_paths=5`、`max_hops=5`、`deadline_ms=10000`、`trust=verified`），
`MX:chem:co2 → MX:chem:combustion` 的输出是：

```
status=no_result  0 节点 / 0 边  paths=0  hidden_by_trust=72333  11507 ms
```

**`hidden_by_trust = 72333`，而全图只有 48,712 条边。** 一个"被隐藏的边数"不可能超过"边的总数"。
这一条就够了 —— 不需要任何内部知识就能判定它是错的。

进一步实测（同一查询连跑两次）：**72,333 / 62,640 / 66,319**，幅度差 ~15%。
一个"条数"随 deadline 抖动 ⇒ 它根本不可能是集合基数。

## 2. 机制（读码 + 探针实测）

`03_知识层/queries.py`：

```python
def _count_hidden(e) -> int:          # ← 旧实现
    nonlocal hidden_by_trust
    hidden_by_trust += 1              # ← 每被调用一次就 +1
    return 0

if mode == "path":
    def path_edge_ok(e) -> bool:
        ...
        if not self._trust_ok(e, trust):
            _count_hidden(e)          # ← 判定点
            return False
        return True
    pr = self._find_paths(a, b, max_paths, hops, deadline_ms, edge_ok=path_edge_ok, t0=t0)
```

而 `_find_paths` 是**路径 BFS**（不是节点 BFS）：队列元素是 `(当前节点, 节点路径, 边路径, 已访问集合)`，
`edge_ok(e)` 在**每条部分路径的每一次邻接枚举**上都会被调用：

```python
q = deque([(a, [a], [], {a})])
while q:
    node, npath, epath, seen = q.popleft()
    for e, other, _direction in idx["adj"].get(node, []):
        if other in seen: continue
        if edge_ok is not None and not edge_ok(e):   # ← 同一被拒边被反复判定
            continue
        ...
        q.append((other, npath2, epath2, seen | {other}))
```

⇒ 同一条被 trust 拒绝的边，会在**所有经过它的部分路径**上各被判定一次。在度数 2000 的
`EK:el:C` 附近，这个重复次数是**几百倍**。

**探针实测**（给真实 `subgraph(mode="path")` 调用装上 `edge_ok` 探针，同一次遍历里既数
"判定次数"、也用 `set` 记"被拒的不同边"）：

| 查询（`trust=verified`, `max_hops=5`, `deadline=10 s`） | 判定次数 | **不同**被拒边 | 单边最多重复 | 报告值 / 不同 | 该次报告值 |
|---|---|---|---|---|---|
| `CE:pq:gibbs_energy → PB:pq:entropy`（早停：5 条就够） | 2,807 | **28** | 3 | 1.1× | 31 |
| `MX:phy:newton2 → EK:el:C` | 5 | **3** | 1 | 1.0× | 3 |
| `MX:chem:co2 → MX:chem:combustion`（撞 deadline） | 1,979,241 | **11,660** | **601** | **169.7×** | 62,640 |

> 全图 `trust=verified` 通过 34,780 条 ⇒ 非 verified 共 **13,932** 条。
> 也就是说：被拒的**不同**边最多 13,932 条，而旧实现能报出 62,640。

★ 这张表同时说明**为什么这个缺陷危险**：第 1、2 行里报告值**恰好**接近正确值（1.1×、1.0×）——
早停的小查询"看起来完全正常"。只有撞 deadline、探索范围大的查询才暴露。⇒ 用户会先建立
"这个数字是对的"的信心，然后在大查询上被它骗。

## 3. 为什么定性为缺陷（而不是"字段含义没写清"）

1. **可判定的假**：N > 全图边数。任何读者都能一眼判定不可能，无需内部知识（§1）。
2. **跨查询不可比**（铁律 #12 计数≠内容 / #52 命题须一致）：同一字段在不同查询里
   有时≈不同边数、有时 170×，**两个查询的"已隐藏"根本不能放一起比较** ——
   而前端的用法正是让用户比较（"切到 all 多了几条"）。
3. **它是文案里的断言，不是内部指标**：`main.js` 的 `no_result` 分支直接把它写进
   「本次已隐藏 **N** 条低可信度边；通路可能正被它们连接」。这句是**给用户的结论**，
   数字错 ⇒ 结论的强度错。
4. **数值不稳定**：同一查询两次 72,333 / 62,640 ⇒ 任何"复现"承诺（本项目核心主张之一，
   `query_hash` + `snapshot_id`）都被这个字段破坏。

## 4. 修法

`03_知识层/queries.py`：计数变量由 `int` 改为**边 id 的 `set`**，对外只发布基数。

```python
hidden_edges: set = set()                 # ★ 去重：对外计数必须是"被排除对象集合"的基数

def _mark_hidden(e) -> int:
    """记下被可信档位排除的边（按边 id 去重）；返回值恒 0 以适配 edge_ok 协议。"""
    hidden_edges.add(e["id"])
    return 0
```

三处判定点统一改为 `hidden_edges.add(e["id"])`（`path` / `filter` / `ego` 各一处），
四处使用点统一改为 `len(hidden_edges)`。

**顺带订正一处陈旧 docstring**：`_find_paths` 的返回值里从来没有 `hidden_by_trust`
（旧文档一直写着有）——这正是"去重计数不该住在 BFS 里"的书面证据，已改写为
`{paths, truncated, timed_out, pending, missing, elapsed_ms}` 并说明**为什么**不返回它。

**前端文案**（随口径一起改，避免"代码改了、话说错了"）：
- `main.js`：`已隐藏 ${hid} 条低可信度边（按边 id 去重、已探索范围内）`
- `panels.js`：状态行 `title` 改为「本次查询中被可信范围排除的**不同**边数（按边 id 去重；不是遍历判定次数）」

## 7. 本轮登记（编号延续）

### 缺陷

- **D45**｜`mode=path` / `mode=ego` 的 `hidden_by_trust` 是**遍历判定次数**而非**不同边数**；
  实测可 **> 全图边数**（62,640 > 48,712）、随 deadline 抖动（72,333 / 62,640 / 66,319）、
  且在小查询上"恰好接近正确值"从而掩盖问题。**已修**（§4），已加断言（§5）。
  ⇒ 与 **#12（计数≠内容）**、**#52（发布命题须＝被验证命题）**同族。

### 教训（E）

- **E41**｜**核对/计数类仪器必须先自证"探针有效"**。本轮我第一次写的探针把 `f["types"]`
  传成**空 `set`**（正确应为 `None`），`_edge_ok()` 对每条边都返回 `False` ⇒ 探针计数
  **全为 0**，看上去"一切正常、没有隐藏边"。发现方式是它与 HTTP 实测值（72,333）
  **量级差 4 个数量级**，逼我回头查探针而不是查被测对象。
  ⇒ 铁律 **#76（"全红"也可能是测量器坏了）** 的反面同族：**"全绿"也可能是测量器坏了**。
  这就是 `V20c` 存在的理由 —— 每次运行都先证明"这个探针真的会数到东西"。
- **E42**｜"探索过程中的计数"必须显式区分三种口径：**①判定/访问次数 ②不同对象数
  ③全量实有**。三者可以相差几个数量级；字段名与文档必须写明是哪一种。本字段的正确口径是
  **②（不同边数，且只在已探索范围内）**，UI 文案已按此改写（§4）。
- **E43**｜**"上一轮记下的数字"不得直接落进交付文档，必须重测**。本轮我在同步测试清单前，
  中间记录里写着"理想气体组应改为 15/20、all 40/59"；实测是 **6/5、13/14**，而文档里
  **原本就是 6/5、13/14（正确的）**。若照抄记录，会把**正确的文档改错**。
  （同批核对中确实需要改的是 §4 的 `500/499` → `40/39`：那是 Phase 49 改默认预算后遗留的旧值。）

### 铁律候选（待外部评审转正）

- **#89**｜**探索型算法（BFS/DFS/回溯）内部的计数不得直接对外发布为"集合大小"。**
  对外计数必须来自**对象集合的基数**（按稳定主键去重）。同一字段在同一接口的不同查询之间
  **必须含义稳定**，否则跨查询不可比，用户据此做的比较全部无效。
  （编号说明：#87 = 断言名字集合，#88 = 白名单必须派生自事实源，均已由 E33/E34 占用。）
- **#90**｜**"全绿也可能是测量器坏了"**：凡是"用探针/仪器去核对被测对象"的断言，
  必须**在同一次运行内**证明探针确实数到了东西（构造性负对照），否则"0 差异"可能只是
  探针永远返回 0。（与 **#76** 互为反面；两者共同点：先证仪器，再证对象。本条由 E41 得出。）

### 顺带发现的核对陷阱（**不是**缺陷，记录以免下轮再查一遍）

- **`mode=path` 只接受 2 个种子**。用 `seeds=<单个 id>&mode=path` 会得到
  `no_result` + 「path 模式需要 2 个存在的种子（起点/终点）」。
  §3「点进子图」用的是 **`mode=ego`**（默认预算 40/70/2/10 s），不要拿 `mode=path` 去核。
  本轮我先踩了一次，属"用错端点"而非产品缺陷。
- **页面路径条 ≠ legacy `/api/path`**。前者走 `/api/subgraph?mode=path` 并**应用** trust；
  后者**不做** trust 过滤（D9/D43）。同一对节点两个答案：`MX:phy:newton2→EK:el:C`
  在 legacy 上 24 ms 返回 5 条链路，在页面（`verified`）上是 `no_result`、切 `all` 才在
  0.4 s 内返回 5 条。这条差异已在测试清单 §5/§8 中明写。

## 8. 遗留

1. `hidden_by_trust` 现在的语义是「**已探索范围内**被排除的不同边数」，仍然**不是**
   "全图被隐藏的总数"。这是刻意的（探索型查询给不出全量），但 UI 文案必须带上限定语 —— 已加。
   若将来要在概览里给"全图隐藏总数"，应另开字段（可全量扫描的 `filter` 模式本来就给得出）。
2. `ego` 模式的 BFS 里，未被接受的边不会被记入 `why_edges`，因此仍可能从**两端各被枚举一次**；
   现在用 `set` 去重后**不影响对外数值**，只是多做一次判定（性能，不是正确性）。
   —— 若将来出现"子图查询明显变慢"的报障，这是可优化的点（记于此处，暂不动）。
3. 同族排查（方法：逐一定位**赋值点**并确认它是否来自"对互异对象的单遍扫描"）：
   现有对外计数字段中，`n_nodes` / `n_edges` / `paths` 长度 / `total_matches` / `count` /
   `pre_truncation` / `n_edges_total` / 各 A04 与字节忠实度分列 / 概览元图 `n_nodes`·`weight`
   **全部**为 `len(集合)` 或对 `idx["nodes"]`/`idx["edges"]` 的**单遍**累加
   （每次迭代对象互异 ⇒ 天然等于集合基数）；`elapsed_ms` 是耗时不是计数。
   ✅ **未再发现"用过程次数充集合大小"的字段**。⇒ D45 是这类问题的**孤例**（因为只有它住在
   一个会重复枚举同一对象的搜索循环里）。
