## 2. B1 · 底部路径栏「指引指向代码做不到的动作」

### 2.1 缺陷

`06_PoC/js/main.js` 的 `runPath()` 自组请求参数：

```js
const env = await state.api.subgraph({
  mode: "path", seeds: `${src},${dst}`,
  max_paths: BUDGET.paths, max_hops: HARD.hops, deadline_ms: BUDGET.deadline_ms,
});
```

- 不发 `trust` ⇒ 后端（`viz_server.py`）**默认 `verified`**；
- `max_hops` 写死 `HARD.hops`(=5) ⇒ 不读左侧面板的跳数设置。

而紧挨着的 `pathOutcomeText()` 在 `no_result` 分支里明确写着：

> 可把「可信度」切到 **all** 再试；**若切档后仍无结果，更可能是跳数不够**，可增大跳数。

**这两件事路径栏都做不到。** 用户按提示操作，请求一个字节都不会变，于是把
「**被可信度档隐藏**」读成「**图里确实没有路径**」——这在本项目是最反对的那类结论
（把「没看见」报告成「不存在」）。

与 **D64** 同族：D64 是**文案把人送进死循环**，这里是**文案让人做无效操作**。
两者共同的病根是：**判据/文案没有把自己需要的执行条件一并兑现**。

### 2.2 修法

1. `runPath()` 改走 **`taskRequest({mode:"path"}, {seed, second, scope})`** ——
   与任务卡**同一个构造器**（D48/D50 的教训：两条代码路径各写一套，迟早只修一份）。
2. `scope` 取自 `state.panel.collect()`（`trust` / `max_hops` / `max_nodes` / `max_edges` / `deadline_ms`）；
   `taskRequest` 返回 `null` 时**显式说清缺哪一端**，不发明知会被拒的请求（#34/#62）。
3. `pathOutcomeText(env, paths, ctx)` 增 `ctx`，在结论里**报出本次实际参数**：
   `（本次参数：可信档 verified ｜ 2 跳）`。

第 3 条不是装饰，是**必要的诚实性收尾**：改走界面参数后，默认跳数由写死的 **5 → 面板的 2**。
**不报出实际值，这个变化就是静默的**——用户会以为「图退化了」，而实际是「参数变严了」。

### 2.3 构造性证据

`R12`：把 `runPath` 改回自组参数（`trust` 写死 `"verified"`）⇒ **`V13` 必须变红**。实测 PASS。
`V13`：在 `runPath` 函数体内断言 ① 存在**调用形状** `= taskRequest(`；② 无内联 `.subgraph({…})`；③ 含 `trust`。
`V14`：断言 `pathOutcomeText` 带 `ctx` 且文案含「本次参数：可信档」。
`F38k`（node）：同一构造器在 `trust=all/3 跳` 与默认值下必须给出**不同**的 `trust`/`max_hops`
——**比较两个不同输入**，写死任何一个都会使两值相等而变红（只断言"等于 all"挡不住写死成 all）。

## 3. B2 · 谱系自检在「依赖未入库」时 traceback

### 3.1 缺陷

`11_真实数据/lineage_invalidation.py` 两处自检（⑥ 依赖感知失效、⑦ 未受影响项保持原状）：

```python
with open(ap, "wb") as f:
    f.write(sr.repo_blob(rel, ROOT) + b"\n# MUTATION-FOR-SELFCHECK\n")
```

`repo_blob()` 的契约明写「**不在仓库 ⇒ None**」（`source_registry.py:496-499`）。
依赖未入库时 ⇒ `None + bytes` ⇒ `TypeError`，现场**只有栈回溯、没有一句判定**。
评审那次全量冻结门禁 107/108 即由此而来。

本仓库因该参考表**已入库**而不触发 ⇒ 属**潜伏**缺陷。但「脏目录」恰恰是最需要自检说话、
最不该崩的场合——评审撞到的就是这种场合。

### 3.2 修法

新增 `_write_mutated(ap, rel) -> (ok, reason)`：`repo_blob` 为 `None` 时返回
`False, "dependency_not_in_repo: <rel> …（先提交该参考表，再跑本自检）"`，**不落盘**。
⑥⑦ 两处改为「打判定 + `return False`」（fail-closed；清理仍由 `finally` 保证）。

### 3.3 构造性证据（新增 ⑨ 段）

`_selfcheck_none_guard()`：构造一个**确定不在 HEAD 里**的路径，断言
`_write_mutated` 返回 `(False, "dependency_not_in_repo …")`、**不落盘、不抛异常**。

**为什么必须单列一条**：⑥⑦ 只有在**当场存在未入库参考表**时才走到坏分支
⇒ 拿真实数据测它等于**永远测不到**（#90 的反面：全绿可能只是没测到）。
`R13`：去掉该守卫 ⇒ **⑨ 必须变红**。实测 PASS。

新增 `--selfcheck-guard` 单跑 ⑨（**0.39 s**），而不是整套 `--selfcheck`（**3 min 15 s**）：
**一条没人愿意跑的构造性证据等于没有**。

## 4. 本轮两次「假绿」（比结论更值得记）

这两次都不是"想清楚了才写对"，而是**仪器在纠正仪器**：先有探针，才有自我发现。

| # | 假绿 | 怎么被抓住 | 教训 |
|---|---|---|---|
| 1 | `V13` 第一版判据是 `"taskRequest(" in runPath 体`。而函数体里正有一句注释写着「统一走 `taskRequest()`」⇒ 注入「回到自组参数」后**仍然 PASS** | `R12` 首跑 FAIL：*"注入缺陷后 V13 没有变红"* | **名字出现过 ≠ 真的调用了**（#83/#100）。判据须匹配**调用形状** |
| 2 | `⑨` 第一版打印成 `: FAIL`，而 `red_probe` 只认 `[FAIL] NAME` 行形状 ⇒ R13 报"没有变红"，实际 RC=1 **已经红了** | `R13` 首跑 FAIL | **判据被看见了，但探针看不见它**——两种失败都要接住 |
| 3 | 新增的 node 断言第一版叫 `F38k`，而 `F38k` **已被占用**（"任务请求序列化带 hops="）⇒ 两条断言归一化到同一 ID | `assert_name_diff` 的**族内补差**当场报出「族内新增 1」 | 改名 `F38l` 后归零。★ 这是 **D62 的工具第一次在「日常提交」里派上用场**（此前它只在自己的自检里被验证） |

第 2 条尤其值得记：它说明「探针 PASS」与「判据有效」是两件事，
只有当**探针能读到判据的输出形状**时，两者才等价。

第 3 条是 D62/D65 那族的**活体再现**：`norm()` 会把 `F38k`/`F38l` 归到同一个 `F38`，
所以「唯一 ID 数」看不出新增；若不是 D62 补了「族内按全名补差」，这条会被**静默放过**。
