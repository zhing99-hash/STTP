## 一、今天到底发生了什么

一次基础设施故障，以及我们**第一时间的错误处置**。两者都值得记录。

### 1.1 事实：OpenAlex 的免费额度是**按出口 IP 按天**结算的

第一轮抓取一切正常（拿到 447 条候选）。第二轮开始连续 HTTP 429 —— **当时没有读响应头**，
代码把 429 一律当作"稍等再试"，于是每条公式重试 3 次、每次睡 30 秒：

```text
每条公式：3 次重试 × 退避 30 秒 ≈ 90 秒 ⇒ 80 条跑满约两个多小时
结果：65 条失败 + 把第一轮的好数据覆盖掉
```

真实的响应头是这样的（2026-10-21 01:43 UTC 实测，逐字抄下）：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 80202                         ← 22.3 小时
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Limit-USD: 0.1                 ← 真正的闸门在这
X-RateLimit-Remaining-USD: 0
X-RateLimit-Cost-Required-USD: 0.001       ← 每次检索的费用
body: {"error":"Rate limit exceeded",
       "message":"Insufficient budget. This request has no API key, so it counts against
                  the free daily budget shared by everyone on your network's IP address,
                  and that budget is used up ($0 remaining; resets at midnight UTC)."}
```

三条信息缺一不可：
1. **限的不是速率，是钱**：$0.1/天 ÷ $0.001/次 ≈ **100 次检索/天**，按出口 IP 共享；
2. **重置时间是 UTC 午夜**，不是"过一会儿" —— `Retry-After` 明确给了 80202 秒；
3. 服务端明明把原因写在 body 里了，是我们的代码**没读**。

### 1.2 错误的处置：把"配额耗尽"当成"请求太快"来治

第一次修法是「看样子请求太快了，把间隔从 0.35 秒改成 1 秒、退避上限提到 30 秒」。
这是**对着错误的前提做优化** —— 一天只有 100 次额度时，慢一点只能让你**优雅地用完**，
不能让你多用一次。代价是实打实的：第二轮跑成了 65 条失败，还把第一轮的好数据覆盖掉了。

> 与 D86/D87 同族：**动手之前，先有能力把前提说出来**。
> 动手前问一句"这个 429 到底在说什么"，30 秒就能省下两小时和一轮好数据。

## 二、修了什么（D96）

### 2.1 把 429 按成因分类（`fetch_common.classify_throttle`）

| kind | 判据（三条取**或**） | 下一步动作 |
|---|---|---|
| `budget` | `Remaining-USD ≤ 0` ／ `Retry-After ≥ 600s` ／ body 含 `insufficient budget` | **抛 `BudgetExhausted`，不重试**；消息里带**绝对重置时刻**（本地 + UTC） |
| `transient` | 秒级 `Retry-After` 且额度尚余 | 退避后重试（有意义） |
| `unknown` | 没有任何配额头（可能被代理剥掉） | 保守地重试，次数由调用方限制 |

为什么要分开：同一个状态码只说明"服务端没给数据"，**成因才决定下一步**。对着"今天没钱了"
执行"稍等再试"，就是把一个 22 小时的问题当成毫秒级问题治。

### 2.2 不再用劣化数据覆盖好数据（D95 已登记，本轮才真验证）

写盘一律走 `tmp`；`n_error > 0` ⇒ 只写 `.partial.json` 且 `RC=1`，**永不**落到正式候选池。

### 2.3 失败必须落在「未知」那一态

`not_extracted`（没查到 / 查失败）和 `no_referent`（查过了，确实没有）是**两种不同的事实陈述**。
一次抓取失败若被记成 `no_referent`，5,090 个节点里的一批会被永久标成"文献中无人提及"——
而这从未被验证过。所以 delta 遇到含 error 行的候选池 ⇒ **`RC=2` 拒绝产出**；
要放行必须显式 `--allow-partial`，届时 error 行强制记 `not_extracted`，并在汇总里写明原因。

### 2.4 判据从"源码锚点"升级成"运行时验证"

上一版的守卫是**源码字符串计数**（"代码里有这段"）—— 它绿着，而真实行为照旧跑满 80 条。
源码锚点证明的是"没被删"，不是"会这样跑"。改成 **stub 掉网络后真跑一遍**，验证：

| 断言 | 验证的行为 |
|---|---|
| C5 | 第 1 条撞上配额就停 —— 发起 **1** 次请求，不是 20 次 |
| C6 | 以 `RC=1` 退出，调用方能据此中止流水线 |
| C7 | 失败只写 `.partial.json`，正式候选池一个字节都不动 |
| C8 | 已存在的好候选池，不会被后续的失败运行覆盖（85 KB 真实事故的回归测试） |
| C9 | `--estimate` 估算**真的一个请求都不发**（配额耗尽当天唯一安全的动作） |

## 六、提交前的最后一道关：RT 把自己拦下来了

今天收尾时准备提交，按惯例先跑红探针，结果是 **PASS 32 / FAIL 4**。四条失败里有三条
（R15 / RS / RT）指向同一件事：

```text
[FAIL] RT 残留自检：上次被中断的运行没有把注入留在工作树里
       ★ R15 的注入内容仍残留在 06_PoC/js/viz.js（= 上次运行被中断且未还原）
```

现场是这样的：

```diff
  // ★ Phase 58：宽 + 透明度改由**证据等级**驱动
- _width: gradeToWidth((typeof e.grade === "number") ? e.grade : null),
- _opacity: gradeToOpacity((typeof e.grade === "number") ? e.grade : null),
+ _width: 2,      // redprobe: 写死（等级编码退场）
+ _opacity: 0.6,   // redprobe: 写死
```

成因：早先在一台前台终端里跑红探针，被 120 秒超时 **SIGTERM 掐断**。探针的工作方式是
"注入缺陷 → 断言必须变红 → 还原"，还原那一步没来得及执行，缺陷就留在了工作树里。
于是下一次运行**以脏内容为基准**：R15 想注入"写死常量"，可锚点 `gradeToWidth(...)`
早就不在文件里了 ⇒ 锚点命中 0 次（RS 红）⇒ 断言根本题没被改动 ⇒ R15 红 ⇒
连"纯注释改动不得让任何断言变红"的负对照 RN 也跟着红。

**四行失败里没有一行是判据失效，全部是一个操作事故的涟漪。**

处置只有两步：`git checkout -- 06_PoC/js/viz.js` 还原，重跑 ⇒ **PASS 36 / FAIL 0**。

值得记下来的是：**这套机制今天拦住的是它自己。** 如果我们没有 RT 残留自检，
这份"被写死的边宽"会安安静静跟着提交进库，而 R15 从此以后永远绿 ——
因为基准已经是缺陷态了，注入等于没注。**判据恒绿的后果不是"没测出问题"，
是"以后再也不会有人发现它测不出来"。**

> 与 D99 同族：**基准脏了，所有结论都不可信**，而且它不会报错，只会安静地变绿。
