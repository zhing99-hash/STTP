## 一、一句话结论

侦察时以为要去「核 ElementKG 2.0 的许可」，结果发现**真正挡住 `composed_of` 的是登记口径**：
118 个元素节点的真值字段本来就来自 `element_reference`（Apache-2.0），1,734 条元素边也本来就是
我们自己用权威表算的 —— 它们被记在 ElementKG 名下，于是被许可过滤器连坐。

把这两件事拆开后，对外数据集从 **2,837 节点 / 5,417 边** 变成 **2,963 / 12,301**（边 **×2.27**），
`composed_of` 从 **0** 变成 **5,145**，包内分子组成覆盖从 **0%** 升到 **96.65%**，
且**没有引入任何新许可**。

## 二、做了三件事

### 2.1 Element 节点改由 `element_reference` 重建

| | 改造前 | 改造后 |
|---|---|---|
| 字段数 | 14 – 38（各元素不同） | **13**（116 个）/ **14**（La、Ac 多一个 `series`） |
| 真值 8 字段来源 | `element_reference`（节点自带 `periodic_source`） | 同（显式重建） |
| 物性字段 | 熔点/沸点/密度/电负性/电子构型… 直接从 ElementKG 节点上 | **已剥离**，写入 `11_真实数据/element_props_elementkg.json`（内部归档、不入库） |
| `source` | `ElementKG2.0` | `element_reference` |

共剥离 **1,752 个字段值**（118 个元素）。

> ★ 剥离的是**分发资格**，不是**数据本身**：归档文件带 `redistribution: internal_only` 标记，
> 将来若核下 ElementKG 1.0 的条款，可以逐字段回填。
> ★ 前端零影响：`06_PoC/js/*.js` 十个文件 + `graph_view.html` 对这 15 个物性字段名 **0 命中**。

### 2.2 1,734 条元素边订正来源 —— **重算，不是改标签**

这是本轮最要紧的一条。做法不是「把 `source` 字段改掉」，而是：

1. 用 `element_reference` 分组**重新生成**一份集合（完全不看 ElementKG 的 `hasPeriod*`/`hasFamily*`）；
2. 断言「生成集 == 图上现有集」，**双向差集都必须为空**；
3. 断言通过才改来源；**不过就拒绝执行**（宁可这轮什么都不做）。

| 边型 | 图上现有 | 权威表重算 | 缺口 | 多出 | 结论 |
|---|---|---|---|---|---|
| `same_period` | 1,360 条 = 1,355 对 | 1,355 对 | **0** | **0** | 逐对一致，可改 |
| `same_family` | 374 条 = 374 对 | 374 对 | **0** | **0** | 逐对一致，可改 |

依据不只是「算出来一样」——`elementkg_ingest.py:136-144` 的准入判据本来就写着
`period_of(sym) == period_of(target)` 和 `family_key(sym) == family_key(target)`，
两个函数都只读 `element_reference`。ElementKG 的 `hasPeriod*` 只提供候选对。

### 2.3 给 `apply_delta` 加 `props_drop`

upsert 的语义是 `merged.update(props)` —— **只能加改，不能删除**。要真正移除字段，
靠给 `props` 赋 `None` 不行（字段还在，只是变成 null，许可审计仍算「含上游内容」）。

新增可选的 `props_drop: [...]`，在合并后逐字段 `pop`。不给该键时行为与旧版完全一致。

## 五、四条教训

### D106 · 来源标签要按「断言由谁验证」登记，不能按「骨架从哪来」

1,734 条边的 `verifier` 明明是 `element_reference.py`、`explicit_or_inferred` 明明是 `inferred`，
却因为「候选对来自 ElementKG」就整条记成上游来源。
**后果不是数据错，是包小了一半** —— 而且是**静默的**：图能建、测试全绿、报告能写，
只是对外分发时这些数据被政策剔掉。

更糟的是，这个错误会**自我加固**：一旦记成上游来源，后续所有审计都认为它「待核对」，
没人会去翻 `verifier` 字段。识别它的唯一办法是**重算一遍看集合是否一致**。

### #113 · 口径不对，算出来的差距是假的（第三次复发）

侦察时用 `er.series` 单一口径重算 `same_family`，只命中 184/374，差点得出
「families 是 ElementKG 独有分类、不能重算」的**错误结论**。
正确的 `family_key` 是「有族号用 18 族号，f 区才用 series」，换过来后 **0 差异**。

同一个坑这周第三次（#105 两次）。规律很清楚：**先怀疑自己的口径，再怀疑数据**。

### #115 · 探针不能依赖生产数据的当前状态

R38 第一版用 `--dry` 跑、期望 E5 变红 —— 结果 FAIL（没红）。原因：**图已经重建过了**，
`build` 对 118 个元素全部走 `elem_already` 分支、产不出 delta，E5 判的是**已合规的图**。

一次成功的执行会把初始条件改掉，探针从此恒绿。修法是让判据落在**纯函数**上
（S5 用合成 props 测 `rebuild_element`），不依赖生产数据此刻长什么样。

### D107 · 最容易被漏掉的入口，是「**你自己新加的那个出口**」

收尾跑 `bash sttp.sh gatecheck` 时，`interpcheck` 的 **Q3 报红**（RC=1）：

```
❌ Q3 命中「依赖/前置缺失」措辞的文件 ⊆ 入口声明 ∪ 豁免表
   未登记：{'06_PoC/dataset/export_dataset.py': ['前置缺失'],
            '06_PoC/dataset/verify_dataset.py': ['前置缺失'],
            '06_PoC/dataset/wget_offline_e2e.py': ['前置缺失']}
```

这三个文件都是 **Phase 70** 加的。它们新增了 `[前置缺失] ⇒ RC=2` 的出口，
但当时没人想到「这就等于多了一个『非通过』入口」—— 于是它们绕过了铁律 #92
（非通过出口必须自述解释器，否则「解释器选错」与「产品缺陷」外观完全相同）。

**为什么所有测试都绿、而它一直是红的**：缺件分支在绿树上**永不执行**。
跑 `dataset`、跑 e2e、跑全部探针，都不会走到 `if not os.path.exists(src)` 里面去。
**能抓住它的只有静态扫描** —— 而扫描本身在 `gatecheck` 里，Phase 70 收尾时没跑。

处置（不是"先豁免了事"）：
- `export_dataset.py` / `wget_offline_e2e.py` ⇒ **登记为入口**（`ENTRY_POINTS` 5 → 7），
  接 `interp_note.skip_detail`；
- `verify_dataset.py` ⇒ **不能登记**：它会被复制进对外数据集、由第三方在**仓库之外**
  以 `python3 verify_dataset.py` 运行，一旦 import 仓库模块就失去「下载即可自证」（#53）。
  故列入**内联豁免** `INLINE_EXEMPT`，两处出口内联打印 `sys.executable`；
- 新增 **Q7** 咬住这份豁免：`[前置缺失]` 出口数 ≤ `sys.executable` 出现次数 ——
  **豁免的是实现方式，不是纪律本身**；删掉内联打印 ⇒ Q7 变红（负对照 S8 证明它会红）。

★ 这条与 D58「同族未改」同根，但形状更隐蔽：D58 是"**知道**该改、改了一处",
D107 是"**根本没意识到**这也算一处"。**判据能抓到的前提，是它被真的跑过。**

## 八、收尾发现：`gatecheck [3/3]` 是**红的**（与本轮无关，但必须记下来）

本轮第一次把 `bash sttp.sh gatecheck` 完整跑通（前几轮的收尾清单里**没有它**），
结果是 **RC=1**，红在 `[3/3] 门禁非真空自检` 的**正对照**（即：**未注入的原图本身就不过**）：

```
❌ baseline(q) P1-den-main-evidence-traceable        got=FAIL  want=PASS
❌ baseline(r) P1-den-main-evidence-wellformed       got=FAIL  want=PASS
❌ baseline(t) P1-den-main-level-scope-reproducible  got=FAIL  want=PASS
汇总：❌ 非真空自检未通过 3 项
```

**实测定位（用 `frozen_gate.run_case` 直接喂原图）**：

| 判据 | 红的量 | 成因 |
|---|---|---|
| (q) evidence-traceable | `level>=rule_checked` 34,870 条里 **101 条无证据链**，覆盖率 99.7% < 100% | 全部是 `mentioned_in`（Paper→Formula） |
| (r) evidence-wellformed | 证据对象覆盖 **48,712 / 48,813**（99.8% < 100%），不良构 0 条 | 同一批 101 条 |
| (t) level-scope-reproducible | **103 条**「落库档位 ≠ 重算」（如 `has_symbol\|OP:fo:mirror\|OP:sy:u` 落库 `source_asserted`、重算 `rule_checked`） | 符号派生（Phase 69）+ 上述 101 条 |

**这 101 条 `mentioned_in` 的来历是可查的**：`props.created_at = 2026-10-22T08:42:20`、
`source = openalex-mention`、`kind = openalex_name_mention`、`verification_level = rule_checked`
但**没有 `verification_evidence` 对象** —— 正是 **Phase 68** 论文线入图的那 101 条。
它们当初只带了 `evidence`（一段 snippet 字符串），没建证据对象。

**为什么说与本轮无关**：Phase 71 的 delta 只有两类东西 —— 118 个 Element 节点、
1,734 条 `ek_same_period` / `ek_same_family` 边（只改 `source` 等来源字段）。
`mentioned_in` / `has_symbol` / `defines` 一条都没碰（见
`06_PoC/etl/neo4j/phase71_element_delta.json` 的边类型分布）。

**为什么现在才发现（D108）**：`gatecheck` 不在 Phase 68/69/70 任何一轮的收尾清单里。
判据**存在**、也**能红**，但**没有人跑它** ⇒ 它对这四轮等于不存在。
这与 D107 是同一件事的两面：**判据的价值 = 它被跑到的次数**，不是它写得多好。

**未修，且不应顺手修**：修它有两条路，都是**数据决策**而不是代码修正 ——
① 给这 101 条补证据对象（等于承认「标题/摘要字符串匹配」够格当独立证据）；
② 把它们的 `verification_level` 从 `rule_checked` 降为 `unverified`/`source_asserted`
（等于承认「自动匹配不足以叫规则校验」，对外包口径会跟着变）。
两条都会改动已发布口径，需要单独决策，故本轮**只记录、不动手**。

> ★ 顺带一条口径教训：`gatecheck` 的 `[3/3]` 是**正对照 + 注入**两段。
> 注入段全绿（`inject(q)/(r)/(t)` 都能 FAIL）**不代表基线是绿的** ——
> 注入段证明「判据能红」，正对照才证明「数据是干净的」。
> 只看「注入全过」就收尾，正是这四轮漏掉它的方式。
