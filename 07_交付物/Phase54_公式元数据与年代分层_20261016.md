## 1. 需求与四项决策

用户原话（要点）：给公式加 **发现时间 / 发现人 / 公式描述 / 使用描述**；发现时间与发现人
**不可考就标「暂无」**；使用描述没有就不标记；**发现时间可作分层**（每 10 年一组）。

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 元数据来源 | **机制 + 人工策展 81 条**（curated_seed），其余显式「暂无」 |
| 2 | 年代粒度 | **1900 年前按世纪 · 1900 年起按 10 年** |
| 3 | 分组形态 | **图上展示，不做筛选** |
| 4 | 空值写法 | **数据层显式写入「暂无」** |
| ① | 公式描述无值 | 与 `usage` **同规则**（不写键、不渲染该行） |
| ② | 「暂无」哨兵 + 非法值拒绝落盘 | 认可（fail-closed） |
| ③ | 「着色：学科 / 发现年代」控件 | ★ **不放控件** —— 「发现年份……不参与筛选，只是显示分组标记，查看使用」 |

### 1.1 第 3 点结论带来的方案简化（本轮最重要的设计决定）

节点上**三个视觉通道本来都已被占用**：填充色 = 学科、描边色 + 形状 = 类型、徽标 = 验证档。
所以「按年代着色」必然与「按学科着色」**二选一** —— 这正是原规划要设切换控件的原因。
用户拍板「不放控件、只作显示标记」后，方案直接简化成：

> **年代不占用节点任何视觉通道**，只落在 (a) 图例里的「发现年代」区块、(b) 节点详情面板的一行。
> 二者都是**只读**：不可点击、不触发任何查询、不改任何请求参数。

⇒ 既**不需要**新增控件，也**不扰动**既有 48（taskflow）/ 108（门禁）/ 109（前端）条断言。

### 2.2 四个新属性键

| 键 | 有值 | 无值 |
|---|---|---|
| `discovery_time` | 年份文本（见 §2.3） | **写 `"暂无"`** |
| `discoverer` | 人名（中文常用译名） | **写 `"暂无"`** |
| `description` | 一句中文 | **不写该键** |
| `usage` | 一句中文 | **不写该键** |
| `meta_source` | 依据（文献） | **有值必有据**：前两者任一 ≠「暂无」时必须存在 |

### 2.3 ★ 起草时实测出的缺口：`discovery_time` 需要**第 4 种形态**

原规划定了 3 种（四位年份 / `公元前 N` / `暂无`），起草第一条就撞墙：
**公元 1000 年以前只有 1–3 位数字**（花拉子米《代数学》约 **820** 年）⇒ 表达不了。
故合法形态扩到 **4 种**：

`四位年份(1000–9999)` ｜ `公元 N(N 为 1–3 位)` ｜ `公元前 N(N 为 1–4 位)` ｜ `暂无`

⇒ 分桶相应补一条：`公元 820` → **`9 世纪`**。
★ 桶标签**不加「公元」前缀** —— 否则 `公元 9 世纪` 与 `9 世纪` 会成为**两个同义桶**。

### 2.4 内容质量

- 81 条中 **79 条**有明确年份（含公元前后各 5 种世纪桶）；
- **「暂无」只 2 条**：`CE:fo:ksp`（溶度积）、`OP:fo:refr_speed`（介质光速）—— 都是**纯定义式**，
  没有单一「发现」事件，标「暂无」是诚实而非偷懒；
- `discoverer` 另加 1 条「暂无」：`NT:fo:crt`（中国剩余定理，作者不详）；
- 多人渐进 / 归属有争议的（万有引力、质量作用定律、熵、光电效应、泰勒级数……）写
  **主要贡献者 + 最早年份**，并在 `meta_source` 里注明「渐进」；
- 只能定到世纪的古代结果（如《孙子算经》，约公元 3–5 世纪）**取该世纪代表年份**，
  并在 `meta_source` 里显式写「约」—— 既不丢信息，也不伪装成"确有其年"。

**年代桶分布（11 桶）**：
`公元前 6 世纪`1 ｜ `公元前 3 世纪`5 ｜ `4 世纪`1 ｜ `9 世纪`1 ｜ `13 世纪`1 ｜
`17 世纪`14 ｜ `18 世纪`11 ｜ `19 世纪`28 ｜ `1900–1909`13 ｜ `1920–1929`4 ｜ `暂无`2。

## 4. 前端（3 个文件 · **零新增控件 · 零视觉通道占用**）

| 文件 | 改动 |
|---|---|

| `main.js` | 统计当前画布上的年代桶与计数，传给图例（**不加控件**） |

### 4.1 渲染规则：**哨兵 vs 缺键必须可分辨**

- `discovery_time` / `discoverer` 在数据层**总是有值**（可能是「暂无」）⇒ 总是渲染；
  「暂无」渲染成**弱化灰 + 「不可考」小标签**，不得留空；
- `description` / `usage` 无值 ⇒ **键根本不写** ⇒ **该行不渲染**（不是渲染成空行）;
- 末行「元数据依据」是本轮**主动加的**（用户只要求 4 个字段）：项目纪律是「有值必有据」，
  把依据摆到读者面前才可核验。**不想要就删掉 `evidence.js` 里 `meta_source` 那一行。**

### 4.2 分桶口径（与 Python 侧**逐条对应**）

`1899` ⇒ `19 世纪`；`1900` ⇒ `1900–1909`（**跨过 1900 即切十年桶**）；
`公元 900` ⇒ `9 世纪`；非法值 / `null` / 空串 ⇒ `暂无`（**不得猜成年份**）。
排序键**严格单调**：`公元前 6 世纪 < 公元前 3 世纪 < 4 世纪 < 9 世纪 < 17 世纪 < 19 世纪
< 1900–1909 < 1920–1929 < 暂无`。

## 9. 本轮的方法学记录

**★ 一条自检踩到的真陷阱（写给下一个改断言的人）**：
`names` 只看"名字集合"，而**名字到 ID 的归一化本身有损**（吃掉尾随数字）。
我在本轮真的把一条断言写成 `F42b2`，采集器报"新增 ID 8 个"而实际新增 9 条 ——
**"条目数 +9 / 唯一 ID +8"这个不一致本身就是信号**，它说明有两条断言共用了一个 ID。
⇒ 以后凡看到"条目数与唯一 ID 增量不等"，先查 ID 归一化，别当成显示风格问题。

**★ 计划↔实现偏差必须当轮闭合**：规划 §4 写的是「桶 **+ 计数**」，首版实现只列了桶名。
我没有把它降级成报告里的"已知边界"（那样读者会按计划读实现），而是补了一个 `fix` 提交
把计数做出来并加断言 F42j + 探针 R9。
