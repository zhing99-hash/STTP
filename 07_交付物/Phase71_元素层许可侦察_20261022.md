# Phase 71 · 元素层许可侦察：`composed_of` 为什么是 0，以及两条路各自的代价

> 侦察日期：2026-10-22｜性质：**只读侦察**，未改动任何代码、数据、登记表
> 触发：F5 对外数据集 `composed_of` = 0 条，1,397 个分子没有组成关系
> 本文所有数字均由 `06_PoC/etl/normalized.json`（9,750 节点 / 48,813 边）现算，未引用旧报告

---

## 一、结论（先给判断，再给证据）

1. **「核 ElementKG2.0 的许可」这条路，单独走不通。** 2.0 在 OpenKG 上确实标了
   `License: Creative Commons Attribution Share-Alike`，但**不带版本号**；而图里 118 个 Element
   节点来自 **ElementKG 1.0**（`elementkg_raw.json`），1.0 页面**没有授权字段**、OWL 文件 4.07 MB 里
   `license|licence|creativecommons|rights` 命中 **0 处**。⇒ **核下 2.0 也救不了 `composed_of`。**

2. **真正挡路的不是许可，是登记口径。** 1,729 条元素间边（`same_period` 1,355 + `same_family` 374）
   的 `verifier` 全是 `element_reference.py`，准入判据就写在源码里
   （`period_of(sym) == period_of(target)` / `family_key(sym) == family_key(target)`）。
   它们**本来就是 STTP 用 Apache-2.0 的元素真值表自己算出来的**，却被登记成 `source=ElementKG2.0`，
   于是一起被许可过滤器连坐剔除。

3. **正确做法是「重建」而非「改标签」：** 118 个 Element 节点改由 `element_reference` 重建
   （剥掉 27 个 ElementKG 物性字段，前端 **0 引用**），两条元素边改为按权威字段**重算生成**。
   实测：对外包 **2,837 / 5,417 → 2,963 / 12,301**（节点 +4.4%，**边 ×2.27**），
   `composed_of` **0 → 5,145**，且**不引入任何新许可**。包内分子覆盖率
   **0% → 96.6%**（1,402 个分子里 1,355 个有组成关系；剩 47 个是图里本来就没有这份数据，
   **不是许可问题**）。

## 三、发现一：Element 节点是两个来源的**混合体**

图里 118 个 Element 节点带 40 个字段，来源可精确二分：

| 字段组 | 字段 | 来源 |
|---|---|---|
| **真值 8 个** | `atomic_number` `atomic_weight` `period` `group` `block` `series` `symbol` `name` | **`element_reference`**（节点已带 `periodic_source: element_reference_iupac` 标记） |
| **物性 27 个** | `melting_point` `boiling_point` `density` `electronegativity` `electron_config` `discovered_year` `abundance` `heat_capacity` `conductivity` `ionization_energy` `atomic_radius` `bulk_modulus` `hardness` `electron_affinity` `state` `families` … | ElementKG |
| 元数据 5 个 | `source` `id` `domain` `ntype` `periodic_source` | — |

**前端依赖实测：0 处。** `06_PoC/js/*.js` 十个文件 + `graph_view.html` 全文检索这 15 个物性字段名
⇒ **0 命中**（此前 grep 到的 `state`/`density` 命中全在 `viz_server.py`、`domain_report.py`、

⇒ 结论：**剥掉物性字段对 UI 零影响**。代价只是「元素详情少了熔点/密度这类科普信息」，
而这本来就该由 ElementKG 的许可决定要不要给。

## 四、发现二：1,729 条边被错标来源（D106）

`same_period` / `same_family` 的 `props` 里，四个字段互相印证：

| 字段 | 值 | 含义 |
|---|---|---|
| `source` | `ElementKG2.0` | ← **错在这里** |
| `verifier` | `element_reference.py` | 判定它成立的是 STTP 自己的真值表 |
| `verification_scope` | `period_authority_equal` / `family_authority_equal` | 口径 = 权威表相等 |
| `explicit_or_inferred` | `inferred` | 不是上游断言，是推导 |

源码（`11_真实数据/elementkg_ingest.py:136-144`）写得很明确：

```python
if pn.startswith("hasPeriod"):
    if period_of(sym) is not None and period_of(sym) == period_of(ln(o)):
        rel_pairs["same_period"].add(frozenset({ek_id, tgt}))
elif pn.startswith("hasFamily"):
    ku, kv = family_key(sym), family_key(ln(o))
    if ku is not None and ku == kv:
        rel_pairs["same_family"].add(frozenset({ek_id, tgt}))
```

ElementKG 的 `hasPeriod*` 只提供**候选对**，**准入判据是 `element_reference`**。

**重算验证（关键，不能只看字段就下结论）**：

| 边型 | 现有 | er 重算 | 现有 ⊆ 重算 | 缺口 | 多出 |
|---|---|---|---|---|---|
| `same_period` | 1,360 条 = **1,355 对** | 1,355 对 | ✅ | 0 | 0 |
| `same_family` | 374 条 = **374 对** | 374 对 | ✅ | 0 | 0 |

⇒ **集合完全相同，差异 0**。这 1,729 条边不是 ElementKG 的数据，是 STTP 的判据产物。

> 途中一次自我纠错：先用 `er.series` 单一口径重算 `same_family`，只命中 184/374，差点得出
> 「families 是 ElementKG 独有分类、不能重算」的错误结论。实际 `family_key` 是
> **「有族号用 18 族号，f 区才用 series」**，换成正确口径后 0 差异。
> 这是同一个坑的第三次：**口径不对，算出来的差距是假的**（#105 的第三次复发）。

### 顺带发现的第二个问题：无向关系被存成随机方向

`rel_pairs` 用 `frozenset` 去重，写边时 `a, b = tuple(pair)` —— 方向取决于 `frozenset` 的迭代序，
**实质是随机的**。所以 `same_period` 1,355 对里有 1,350 对是单向、5 对是双向（1,360 = 1,355 + 5）。
`same_period` 语义上是对称关系，存成单向且方向不确定，会让 `edge id`（`same_period:{a}::{b}`）
在不同 Python 版本/哈希种子下漂移。重建时应固定方向（按 symbol 排序，小 → 大）。

## 五、两条路的规模（现算，同一份快照）

| 场景 | 节点 | 边 | `composed_of` | 许可后果 |

| 只改一半 | 结果 | 说明 |
|---|---|---|
| 只重标 1,729 条边，不动元素节点 | **2,837 / 5,417（+0 / +0）** | 端点仍是 ElementKG 元素 ⇒ 一条也进不了包 |

⇒ 两件事**必须一起做**，缺一半收益直接归零或打八五折。

## 七、我的推荐

**做 B，不做 A，也不做 A+B。**

- **B 的收益是实打实的**：边数 ×2.27，对外数据集从「只有反应、没有组成」变成「能查反应、能算分子式」。
  且这 5,145 条 `composed_of` 的边来源是 ChEBI（CC BY 4.0）+ curated_seed，**全都可以合法外发** ——
  它们被剔除的唯一理由就是「另一端是 ElementKG 的元素节点」。把这一端换成 Apache-2.0 的元素真值表，
  等于**给已经合法可用的数据解开了一个死结**。
- **A 不划算**：多拿 1,559 节点 / 6,062 边（主要是 EK2 的官能团/反应关系），代价是整包被迫 CC BY-SA。
  ShareAlike 对**模型权重的传染边界在法律上不明确** —— 这会给下游用这份数据训模型的人埋一颗雷。
  为 6 千条边换一个「下游不敢用」的许可，不值。
- **B 的唯一实质损失**：元素详情少 27 个物性字段（熔点/沸点/密度/电负性…）。这些字段**前端 0 引用**，
  属于「有更好、没有不影响功能」。若将来真要，够胆量去核 1.0 的条款再补回来，不影响现在的路径。

## 八、仍未解决的事（如实列出）

1. **ElementKG 2.0 的 CC BY-SA 版本未确认**（页面上只写 `Creative Commons Attribution Share-Alike`）。
   CKAN API `package_show` 在本机不通（返回非 JSON），只能靠页面元数据。若将来要用 2.0，必须先问上游是 4.0 还是 3.0。
2. **ElementKG 1.0 的条款可能永久不明**（2026-01 上传，页面无授权字段，OWL 无声明）。
   ⇒ 「官能团 / 反应试剂关系」这类 1.0-2.0 独占内容，**长期不能进对外包**，除非拿到书面许可。
3. **`has_quantity`（元素→物理量）1,089 条**：端点是 ElementKG 元素 + PQ 节点。即使元素层重建，
   这条边的 `verifier` 是 `ElementKG2.0`（`source_assertion`，不是推导）⇒ 仍不可外发。这是内容损失，不是口径问题。
4. **`same_state` 边当年被判定「过密（近全连通团）」而未入边**，改为节点属性 `state`。
   路径 B 把 `state` 也剥掉了 ⇒ 这条信息在对外包里彻底消失。可接受，但要写进 boundary。
5. **残余 47 个分子没有组成关系**：B 之后包内 1,402 个分子里 1,355 个能算分子式，
   剩 47 个（3.4%）**在图里本来就没有 `composed_of` 边** —— 不是许可挡的，是源数据没有。
   要补只能回去解析更多分子的分子式（ChEBI 已有 formula 的才可能），属于数据扩展，不在本次范围。
