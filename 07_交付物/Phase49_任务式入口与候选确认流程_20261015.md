★ **与需求的一句直译对照**：需求要的不是"更聪明的自然语言解析"，而是

## §1 首屏结构与交互

### 1.1 三段式

```
┌─ #task-entry（首屏）────────────────────────────────────────────┐
│  [ 文本框：输入关键词，或点下面的示例卡 ]                        │
│  ┌──────────────┐ ┌──────────────┐                              │
│  │ 吉布斯自由能 │ │ 这个公式的量 │   ← TASK_CARDS（4 张）        │
│  │ 与熵之间有什 │ │ 纲是否一致？ │                              │
│  │ 么关系？     │ │              │                              │
│  └──────────────┘ └──────────────┘                              │
│  ┌──────────────┐ ┌──────────────┐                              │
│  │ 某个物理量有 │ │ 某个分子由哪 │                              │
│  │ 哪些单位与相 │ │ 些元素或官能 │                              │
│  │ 关公式？     │ │ 团组成？     │                              │
│  └──────────────┘ └──────────────┘                              │
│  ── 候选区（点卡或键入后出现）────────────────────────────────  │
│  · 候选 1   [物理量 · 化学]  ← 点这一行 = **确认实体**          │
│  · 候选 2   …                    （最多 5 条；截断会写明）      │
│  ── 范围（可调）────────────────  跳数/节点/边/超时/可信度      │
│  [ 生成子图 ]   ← 未确认实体时**禁用**并给出可操作原因          │
└─────────────────────────────────────────────────────────────────┘
        ↓ 生成
   画布（子图）＋ 状态行（五态）＋ 证据卡＋ 图例
        ↓ 需要调整
   [ ← 修改查询 ]  ⇒ 回到上面的面板（保留已选实体与范围）
```

### 1.2 为什么"确认"必须是**前置**条件

`taskRequest()` 在缺实体时返回 **`null`**（而不是发一个必然被拒的请求）：

```js
if (isPath) {
  if (!has(seed) || !has(second)) return null;   // ★ fail-closed：明确"还缺一端"
  return { mode:"path", seeds:`${seed},${second}`, max_hops:sc.hops, max_paths:BUDGET.paths, ...common };
}
if (!has(seed)) return null;
return { mode:"ego", seeds:String(seed).trim(), hops:sc.hops, ...common };
```
配套 `taskBlockedReason()` 给出**可操作**原因（"请先输入关键词并**确认一个候选实体**（点候选行即可）"
／"本卡查「两点之间的路径」，还需要确认**第二个**实体"），**不做"点了没反应"**。
由 `F38i`（fail-closed）与 `F38j`（原因可操作）断言。

## §2 四张卡：不是装饰，是**带边界披露的可执行查询**

每张卡都携带 `mode` / 预填搜索词 / 关系类型白名单 / **`note`（如实说明本卡能力边界）**。
`note` 会渲染在卡上 —— 因为"这张卡能做到什么、做不到什么"本身就是**结论的一部分**。

| 卡 | 模式 | 预填词 | 关系类型（白名单） | `note` 里如实披露的边界 |
|---|---|---|---|---|
| `relation` 吉布斯自由能与熵之间有什么关系？ | **path** | gibbs → entropy | （空：路径查询**不加**类型过滤，否则容易人为切断通路） | ★ 同名实体来自不同来源时结论不同：本快照下 `Gibbs free energy ↔ entropy(PB)` 可连通；而 `↔ entropy(TH)` 在 5 跳内**确实没有路径** —— 这正是"先确认实体"的意义 |
| `dimension` 这个公式的量纲是否一致？ | ego | energy | `dimensionally_consistent`, `has_unit` | ★ **本图中量纲关系挂在物理量之间，公式节点没有量纲边**；故本卡实际执行的是「与所选量量纲一致的量有哪些、它的单位是什么」，**不是**公式符号级的量纲演算 |
| `units` 某个物理量有哪些单位与相关公式？ | ego | energy | `has_unit`, `dimensionally_consistent`, `derived_from`, `same_as`, `defines` | ★ 有意**不含** `has_symbol`（全图 24 341 条，占一半）—— 带上它必然截断成一团毛线 |
| `composition` 某个分子由哪些元素或官能团组成？ | ego | ethanol | `composed_of`, `has_functionalgroup`, `has_element`, `related_to` | 1 跳即答案（本快照下 ethanol ⇒ H / C / O） |

★ 第 2 张卡与第 3 张卡**问句不同、能力也不同**，但都在 `note` 里写清了"实际执行的是什么" ——
这是把**"问题的字面意图"与"图谱的实际能力"之间的落差**摆在用户面前，而不是让 UI 假装做得到。

### 2.1 四张卡的实测结果（40/70/2/10 s，`trust` 两档）

| 卡 | `trust=verified`（默认） | `trust=all` |
|---|---|---|
| `relation`（gibbs_energy ↔ PB:entropy） | `truncated` 8 节点/11 边（隐含 31 条） | `truncated` 8/11（隐含 0） |
| `dimension`（PQ:energy） | `ok` 15/29 | `ok` 15/29 |
| `units`（PQ:energy） | `ok` 15/29（隐含 30） | `ok` 40/66 |
| `composition`（OM:mo:ethanol） | `ok` 4/3（隐含 3） | `ok` 7/6 |

★ **`relation`「必需两端」是有实测依据的**：先试过 `CE:pq:gibbs_energy ↔ TH:pq:entropy` ——
`verified` 档下 `no_result`（"在 5 跳内没有满足过滤条件的路径"），`all` 档下 `timeout`（10 s）
且 `hidden_by_trust=6250`。逐对试探后改用 `PB:pq:entropy`。**这张卡的 `end` 预填词就是实测选出来的**，
并在 `note` 里把"另一对确实不通"写清楚（避免用户以为"卡坏了"）。

★ **第 4 张卡的 `hops` 由 2 改成 1**：`composed_of` 的扇出会把 2 跳撑到截断 ⇒ 1 跳即"ok 4/3"，
正好是需求想问的"由哪些元素/官能团组成"。

## §3 范围：单一来源 + 往严处回落

```js
export const TASK_SCOPE_DEFAULT = Object.freeze({          // ★ 从 BUDGET 派生 ⇒ 两处默认同源
  hops: BUDGET.hops, max_nodes: BUDGET.nodes, max_edges: BUDGET.edges,
  deadline_ms: BUDGET.deadline_ms, trust: "verified",
});
export const TRUST_LEVELS = Object.freeze(["verified", "verified_strict", "all"]);
```

- `normalizeScope()`：数字**钳到 `HARD`** 内；`trust` 走白名单，**未知档 ⇒ 往严处回落 `verified`**
  （"不认识"时不放大范围 —— 由 `F38f` 断言）。
- 默认值 **40 节点 / 70 边 / 2 跳 / 10 000 ms / 路径上限 5**，与
  `STTP_标准用户使用与演示流程` §5 步骤 4 的推荐值**逐项一致**（该文档给"路径数 3—5"，取 5）。
- 三处同源由跨层断言保证：`X4a`（四项对称）+ `X4a-path`（前端 `paths` ≤ 库 `DEFAULT_MAX_PATHS`）+ `X4c`。

## §4 候选区：这个项目最在意的三件事

1. **失败与空必须分列**（`no_result` ≠ `error`）：
   `renderCandidatesHTML()` 对 `status==="error"` 显示 `error_code` + 原因，对"无命中"显示**放宽建议**。
   ⇒ `F39c`。这与后端五态（`ok/truncated/timeout/no_result/error`）同口径。
2. **截断必须披露**：候选超过 5 条时显式写"显示前 N 条 / 共 M 条（已截断）"，**不重排、不隐瞒**。
   ⇒ `F39d`（对应铁律 #66/#67）。
3. **确认状态双重标识**：被确认的候选行带 `sel` 类 + `aria-pressed="true"`（可视 + 无障碍）。
   ⇒ `F39e`。

另：`F39b` 断言候选行的问句**被转义**（`<img>` 不得原样进入 DOM）—— 因为候选文本来自图谱/用户输入。

## §5 「生成图后返回改查询信息」

`main.js::maybeShowReopenTask()` 在画布出现后显示 `#btn-reopen-task`（← 修改查询）；
点击 ⇒ `openTaskEntry()` 重新打开面板，**保留**已确认的实体与范围（无需从头再来）。
`runSubgraph()` 是**唯一**子图执行入口（`runEgo`/`runFilter`/`runTask` 都走它），
成功即清掉旧错误横幅 ⇒ 避免"上一次的报错挂在这一次的结果上"。

## §9 结论

1. 需求的六点**逐条落地**（§0 表），且**每一条都有一个可执行的断言**钉住
   （`F38*`/`F39*`/`S15`/`H8*`）。
2. 设计上最重要的取舍：**不使用**后端的一步直达参数 `query=`，把"实体确认"做成**前置条件**；
   并在契约里把这个"有意不发"**登记成带理由的一等公民**（`backend_params_not_emitted`）。
3. 四张卡都**公开自己的边界**（`note`）——因为在本项目里，"这条结论在什么前提下成立"
   与"结论本身"同等重要。
4. **未实测处已如实登记**（§7）：真实键入、像素级渲染、请求进行中禁用态、`snapshot_id` 未发。
