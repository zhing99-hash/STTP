## 1. A04 的本体与真实量级（先测量，再实现）

### 1.1 A04a：验证器版本**不可区分**（实测坐实）

任务单要求证据携带 `verifier_id + code_hash + dependency_versions`。修复前的现场：

```
props.verification_evidence[] 的字段       覆盖率
  kind / impl / detail / indep / src / src_ver / src_hash / impl_ver   各 100%
  impl_ver 的取值集合                      { "100148c147cb" }   ← 单值
  带 impl_ver 的证据数                     49572 / 49572
```

⇒ `impl_ver` **不携带信息**：它无法回答"这条证据是哪个版本的验证器产出的"。
更严重的是：旧 `lineage_invalidation.py` 的失效判据只比对 `src_hash` 与来源哈希，
**从不读 `impl_ver`**，也**从不读参考表** ⇒ 即使验证器被改写，所有旧证据仍判"新鲜"。

### 1.2 A04b：失效覆盖面（28 → 33238）

旧失效器的可实现动作是「变异某个来源的文件 ⇒ 把 `src` 指向该来源的边判 stale」。
对 `dimension_table`（一张**参考表**，不是任何边的 `src`）做同样动作：

| | 定位到的边数 |
|---|---|
| 旧失效器（按 `src` 匹配） | **28** |
| 依赖感知失效器（按 `reference_refs` 匹配） | **33238** |

差 **1187 倍**。根因不是"匹配写得不好"，而是**判据本身缺了一层**：
`dimension_table` 是被**验证器**读的，不是被边直接引用的 —— 只有把"验证器 → 参考表"这条边画出来，
失效才能向下传导。

### 1.3 依赖的**可证**依据（不是猜的）

`11_真实数据/verification_model.py:67-68` **代码级 import** 了：

```python
import dimension_table as dm
import element_reference as er
```

于是 `code_import` 档（"由验证器模块 AST import 推出"）在**代码层面**有据可查 —— 它不是启发式猜测，
而是对"该模块确实会用到这些表"的**保守过近似**。

### 1.4 顶分屏现状（提供基线，供后续对比）

```
来源：31 个（in_repo 10 ｜ not_in_repo 12 ｜ no_locator 9）
边：48712 条 —— 全部带 props.verification_evidence
证据对象：49572 个 —— 字段 kind/impl/detail/indep/src/src_ver/src_hash/impl_ver 各 100%
```

## 2. 数据模型（契约 → 落库 → 读取）

### 2.1 契约 v2：`contracts/evidence.schema.json`（新增）

顶层 `required: [evidence_id, claim_id, kind, impl, src, status, status_reasons]`。要点：

| 字段 | 语义 | 关键约定 |
|---|---|---|
| `evidence_id` | `evd:<16 hex>`，`sha256(claim_id\|idx\|src\|impl\|kind\|detail)[:16]` | **确定性**：同一条证据在任何机器上算出同一个 id |
| `claim_version` | `sha256(claim 文本 \| 该边全部 evidence_id 排序拼接)[:12]` | 命题版本化；证据集合变 ⇒ 版本变 |
| `input_refs[]` | `{source_id, record_id?, content_hash}` + `binding ∈ {input_source, record_level}` | ★ 记录级绑定（`record_level`）**尚未实现**，当前恒为 `input_source` |
| `reference_refs[]` | `{table_or_rule_id, version, content_hash}` + `binding ∈ {impl_declared, code_import}` | ★ 后者是**保守过近似**（见 §2.3） |
| `verifier` | `{verifier_id, code_hash, dependency_versions}` | **A04a 的修复本体** |
| `result / verification_scope / checked_at` | 结果、范围、检查时刻 | `checked_at` 只用于显示与审计，**不参与判据**（避免"时间新即有效"的假信号） |
| `status` | `valid / stale / needs_review / rejected` | 语义见 §3 |
| `status_reasons[]` | 程序化原因码 | **禁自由文本**（见 §3.2） |
| `supersedes_evidence_id` + `reverified_at` | 重验取代关系 | ★ 重验成功**生成新证据并保留旧证据** |

### 2.2 紧凑编码，以及"取值口径必须一致"的理由

落库时**不写**长键名（49572 条证据 × 长键会把图撑大）：

| 图上键 | 含义 | 取值口径 |
|---|---|---|
| `evd` | evidence_id | `evidence_id()` |
| `refs` | `{ref_id: 记录时刻内容哈希}` | **与 `reference_hashes()` 完全同一口径**（同为仓库 blob 摘要） |
| `vfr` / `vch` | verifier_id / code_hash | `verifier_identity()` |
| `dvs` | `{rel: 记录时刻文件哈希}` | 同上 |
| `chk` | checked_at | — |

★ **为什么坚持"两边同一口径"**：两边可直接比较，**少一层映射就少一类静默错位**。
本轮的 E10（§8.2）正是"取值口径一致、但**搬运**漏了一格"造成的假象。

**实测字段覆盖**（delta 落盘后）：

```
证据总数 49572 ｜ evd 49572 ｜ refs 35669 ｜ vfr 32609 ｜ vch 32609 ｜ dvs 32609
```

### 2.3 两种绑定强度**必须分列**（实测）

| 绑定 | 含义 | 数量 | 强度 |
|---|---|---|---|
| `impl_declared` | `impl` 串**显式点名**了该参考表 | **3127** | 强 |
| `code_import` | 由验证器模块**代码级 import** 推出 | **65151** | **保守过近似** |

★ `code_import` 是过近似：`verification_model.py` import 了 `dimension_table` 与 `element_reference`，
于是**每一条** `verification_model.*` 证据都被判为依赖这两张表 —— 即使某个具体函数（如 `formula_members`）
运行时并不读它们。这是任务单明确允许的「**先按整文件保守失效**」。

**处置**：两档在 `--report`、接口响应（`ref_bindings`）与前端 tooltip 里**分列报出**，
并写明「保守过近似：该模块 import 了这张表，不等于本次判定真的读了它」——
**不把过近似说成精确**。

### 2.4 ★「不可从仓库复算」≠「已变更」（铁律 #70 在 A04 语境下的落实）

A04 的状态机里这条最容易做错：

* `unverifiable_source:sid`（参考表/来源取不到仓库字节） ⇒ **进 `needs_review`**，**不进 `stale`**；
* 若把它并入 `stale`，`exclude_stale` 会退化成"几乎清空全图"（自毁开关）；
* 但它**必须始终披露**：`stats.evidence_status.needs_review` 与状态行 pill 里恒可见。

## 3. 五态 / 四态状态机

### 3.1 两种粒度的映射

| A04 状态（证据级） | → 四分类（`FIDELITY_OF_STATUS`，粗粒度） | 是否被 `exclude_stale` 排除 |
|---|---|---|
| `valid` | `verified` | 否 |
| `stale` | `changed` | **是** |
| `needs_review` | `unverifiable_no_source` | 否（★ 不可判定 ≠ 已变更） |
| `rejected` | `changed` | **是**（命题已被显式否决） |

★ 映射是**粗粒度**的：`needs_review` 不再区分 `no_locator` / `not_in_repo`
（而边级四分类**区分**）。**对外披露仍以四分类 `edge_fidelity` 为准**，本映射只用于快速对照。

### 3.2 原因码（程序化判别，禁自由文本）

```
src_changed: / ref_changed: / verifier_changed: / dep_version_changed:      ← 「已变更」类 ⇒ stale
unverifiable_source: / unverifiable_reference: / unverifiable_verifier:    ← 「不可判定」类 ⇒ needs_review
hash_rewritten_without_reverify                                            ← 「来路不明」⇒ needs_review
no_reference_declared                                                      ← 信息性（不依赖参考表）
claim_rejected / reverified                                                ← 终态标记
```

### 3.3 判定优先级（**确定性**，不依赖遍历顺序）

```
1. claim_rejected                                     ⇒ rejected
2. 有任一「已变更」类原因                              ⇒ stale
3. 有任一「不可判定」类原因（或哈希来路不明）           ⇒ needs_review
4. 否则                                                ⇒ valid
```

**多证据聚合（边级）取最坏**：`valid < needs_review < stale < rejected`。

### 3.4 排除口径合流到**一处**

```python
def edge_is_stale(e, stale_registry) -> bool:
    if edge_fidelity(e, stale_registry) in STALE_FIDELITIES:      # 边级字节层
        return True
    st = edge_evidence_status(e, stale_registry)                   # 证据级依赖层
    return bool(st) and st.get("status") in STALE_EVIDENCE_STATUSES
```

★ 为什么必须**只有一个**函数：否则「前端显示不 stale、后端却按 stale 排除」这类静默错位必然出现。
★ **无 A04 记录 ⇒ 完全回落到字节层** ⇒ A04 未落图的图（发布样例 / 干净 clone 中期图）行为与 Phase 44 **逐位一致**。

## 4. 「单纯重写哈希不能恢复 valid」的两级程序化保证

任务单禁止"原地改哈希即复活"。**一级不够**：

| 级别 | 手段 | 抓的是 |
|---|---|---|
| **图级**（主） | `detect_inplace_rewrites(old, new, ledger)` 逐条比对前后两版图记录的依赖值，凡"值变了、又没有账本条目"即报违规 | 「**绕过重验流程**」这个**动作本身** |
| **记录级**（补） | `mark_rewrites()` 把违规写进证据的 `_src_hash_rewritten=True` ⇒ `evidence_status()` 读取时判 `needs_review` | 让**单看一份图**也能发现"这条记录的哈希来路不明"，不必依赖历史版本 |

**为什么第 2 级不可省**：一份被就地改过的图，**看起来**与"正常重验后的图"**一模一样**（都是"记录值 == 当前值"）。
只有记录级记号能让孤立的图自证异常。

自检 ⑧c 用**三个分支**证明堵口有效：

* ⑧c1 新证据 + 完整账本 ⇒ `valid`；
* ⑧c2 原地改哈希 + 无账本 ⇒ `needs_review`；
* ⑧c3 把**全部 4 个值**都改成当前值 + 图级检出记号 ⇒ **仍 `needs_review`**
  （证明堵口**不依赖**"值不符"这个信号 —— 这是本条设计的关键）。

### E10（已修 · 静默错位）`dependencies_for()` 硬编码 base + `recorded_deps()` 漏透传记号

**现象 1**：`dependencies_for(ev)` 把 `base` 硬编码为模块级 `ROOT` ⇒ 在**临时仓库**里算出的
参考表哈希其实取自主仓库 —— 结果"看起来对"（自检 ⑧c 首版就是这么被骗过去的）。

**现象 2**：`recorded_deps()` 逐字段重建记录快照时，**漏了 `_src_hash_rewritten`** ⇒
记号在图上、却在裁决里消失 ⇒ 「原地改哈希即恢复 valid」的假象**重现**。

**性质**：两者都是「字段的**取值口径**一致，但**搬运**漏了一格」型静默错位。
**处方**：① base 参数**线程化**到底；② 重建快照必须透传全部判据相关字段；
③ 自检里对这两点写了断言（⑧c 三例 + 等价性契约）。

### E11（已修 · 本轮踩到）**同一把不可重入锁的自死锁**

**现象**：`viz_server.stale_registry()` 在 `with _STALE_LOCK:` 里调用
`evidence_status_registry()`，而后者也要拿**同一把** `threading.Lock()`。

**症状**：进程 **CPU ≈ 0、无子进程、永久挂起**（实测挂 10 分钟无任何输出）。
★ 这类症状极易被误判为"图太大/磁盘慢/网络不通"—— 因为**看不到异常**。

**处方**：① 计算移出锁外（锁只保护缓存读写）；② `_STALE_LOCK` 改 `threading.RLock()` 作双保险。
**推论（铁律候选 #79）**：**持锁时不得调用可能持同一把锁的函数**；
诊断"疑似卡死"时，先看 **CPU 时间与子进程数** —— 两者都低 ⇒ 是**锁/等待**，不是计算。

### E12（已修 · 本轮发现）契约校验器**静默跳过** `additionalProperties`

**现象**：A04 契约用 `additionalProperties` 约束 `evidence[].refs` 的**动态键**

**处方**：补齐实现 + 加**反例/正例**各一条（C5b2/C5b3）证其**真的被执行**（不是只加进"支持集"）。
⇒ D12（"契约校验器是子集"）的**这一项**由"已知边界"转为"已修"；其余子集限制仍存在。

### E18（本轮踩到 · 已修 · 与铁律 #76 同族）**新增断言自己崩了，会被读成"项目失败"**

### E19（性能 · 已知边界 · 本轮未改）`lineage` 全量自检是 **O(证据 × 参考表)**，单次约 **8 分钟** CPU

`_selfcheck_deps()` 对同一份图调用 `analyze()` **两次**（变异前 / 变异后），每次
48712 边 × 约 1.3 个参考表 ≈ **6.4 万次** `dependencies_for()`；`_stale_keys()` 再各来一遍。
`evidence_deps.reference_content_hash()` **没有 per-`ref_id` 缓存**（只有 5 张参考表，本可缓存到 5 次），
于是每次都要走一遍 `repo_blob()`（`source_registry._git` 有缓存，故不是 git 子进程爆炸，而是纯 Python 重复计算）。

实测：`bash sttp.sh lineage` 全量 CPU ≈ **100 s+**（单核满载，非死锁；进程 CPU 时间持续增长）。
**未在本轮优化** —— 收尾阶段引入新缓存会带来新的"失效语义"风险（正是 E4/E10 那一类），
**得不偿失**；且它不是**服务端请求路径**。

★ **对比**：`viz_server.evidence_status_registry()` 的做法是**先算一次 `current_snapshot()`，再对全部证据复用同一份 current**
⇒ 全图 48712 边只需 **1.27 s**（实测）。**这正是"两次遍历 vs 一次快照"的差别**，也说明服务端路径***设计上**规避了该问题。

**优化建议（待办，非本轮）**：给 `reference_content_hash()` 加 `(base, ref_id, byte_source)` 键的进程内缓存，
并与 `source_registry.clear_git_cache()` **联动清理**（否则 HEAD 变更后缓存会返回旧值 —— E4/E10 同类陷阱）。

### E21（本轮发现 · **真缺陷 · P1 · 未修**）发布清单 `dirty_sample` 依赖不稳定的 `git status` ⇒ **脏工作区下清单非幂等**

**现象**：连续两次 `bash sttp.sh release`（工作区文件**未变**）产出**不同**的 `manifest.json`

**根因**（`06_PoC/release/make_manifest.py:304–305, 327`）：

             if "06_PoC/release/manifest.json" not in ln]

...

（**#20/#37：缺依赖 ⇒ SKIP，不假通过也不假失败**）。危害是评审者在干净检出里看到红，
会误判成「A04 的判据本身不可用」。

**修复**：

- ⑦ 段的**输入源改为在临时仓库内可控构造**（`11_真实数据/_probe_input.json`，写固定字节并提交）
  ⇒ 与「大文件是否入库」**彻底解耦**；**干净检出与主仓库都能真跑五类变异**；
- 消除 key 不一致（统一用 `src_sid`）；
- 新增**防回退断言**：探测输入源的 blob 哈希**必须**可取，否则 **FAIL + 明确原因**（不得静默通过 / 真空通过）。

**验证（两侧都测，铁律 #75）**：

|---|---|
| 主仓库 | `evdeps --check` **七段全过**（RC=0） |
| **真·缺数据环境**（干净检出，`ls 11_真实数据/elementkg_raw.json` = No such file） | **七段全过**（RC=0）：五类变异逐一可定位 ✅×5（含 `_probe_input.json` ⇒ `src_changed`）+ 未受影响项保持原状 ✅ |

⇒ `sttp.sh evdeps` 那句注释「干净检出里可运行」**现在才是真的**。
