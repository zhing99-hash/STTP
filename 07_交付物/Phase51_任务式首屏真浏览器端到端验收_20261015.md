## §0 一句话结论

写了一个**真浏览器**端到端仪器（`bash sttp.sh taskflow`，B0–B5 共 **48** 条断言），
第一次运行就抓到 **4 个缺陷**，其中 **2 个是阻断性的**：
**四张示例卡里的第一张点下去走不通**（D47 竞态 + D48 请求发不出去）。
四者全部修复后仪器 **45/0/0** 全绿 —— **但收尾时的重负载批次又咬出两个（D53、D54）**：
一个是**产品**缺陷（跨层时间预算不匹配），一个是**仪器**缺陷（固定延时被当成等待）。
六者全部修复，仪器 **48/0/0** 全绿（含新增的 B4k / B4l / B5m）。

| 编号 | 严重度 | 一句话 | 用户可见后果 |
|---|---|---|---|
| **D47** | **P1（阻断）** | `task.js` 的请求序号与去抖计时器被 `main`/`second` 两槽**共享** | 点 path 卡 ⇒ **起点候选永不出现**、种子为空、按钮永不解锁；两个框打字互相取消搜索 |
| **D48** | **P1（阻断）** | `validateParams` 仍校验 `src`/`dst`，而发送侧 Phase 49 已改为 `seeds` | 任务卡路径查询**请求根本发不出去**，画布空白 + 状态「错误」 |
| **D49** | P2 | 卡片注释承诺「8 节点/11 边」，但那是 **3 跳**下测的，入口默认是 **2 跳** | 点第一张卡得到 `no_result`，与卡片承诺矛盾（**自己达不到的承诺**） |
| **D50** | P2 | 路径结论文案**两套**（任务卡 / 底部路径栏），且失败态不写结论 | 同一结论两种解释；`no_result` 时 `#path-status` 停留在**上一次**的结果 |
| **D53** | **P1（产品）** | `Api` 客户端等待预算**硬编码 3 s**，而请求自带的服务端 `deadline_ms` 是 **10 s** | 空闲时全过、**重负载下必现**：后端本来会给出答案，前端却显示「超时（客户端中止）」（`client_aborted`）——**表现酷似 flaky** |
| **D54** | P2（**仪器**） | 仪器点完「生成子图」只 `wait_for_timeout(600)` 就断言 —— **固定延时被当成等待** | 慢环境下读到**尚未 settle 的中间态**（`status=None` / `cyNodes=0`），把「答案还没回来」报成「图没渲染」，**把嫌疑指向产品** |

★ **这六个缺陷没有任何一个能被既有的静态自检抓到** —— 所有文件都"写对了"。
它们全在「文件写对了 → 页面点得动」这道缝里（见 §1）。

★ **D53/D54 是本轮最重要的教训**：它们的症状在空闲时完全不出现，
只有在 `release-full` + `eval` 把机器压满之后才稳定复现 ——
**「目标随机」的失败最容易被当成 flaky 放过，但它可能是两个真缺陷叠在一起**（见 §7）。
更麻烦的是其中一个是**仪器自己的**：假失败长得像"产品没反应"，
如果不是多做一次对照实验，我会把 D54 写成 D53 的"证据"。

## §1 为什么需要这台仪器（动机，不是"补个测试"）

本项目已有 `phase43_frontend_selfcheck.py`（82→**110** 条）与
`phase43_subgraph_selfcheck.py`（81→**95** 条）。前者覆盖静态面：读源码、比对常量、
`node` 里跑纯函数、HTTP MIME；后者断言**响应体**。

两者都不覆盖「**页面真的能跑通**」。这道缝在本项目已经被咬中**三次**，一次比一次贵：

| 轮次 | 症状 | 静态自检 | 真因 |
|---|---|---|---|
| Phase 47 | 页面卡死（拉 48.7 MB 全图） | 全绿 | `/api/stats` 缺 `status` ⇒ 前端判为"后端不可用" ⇒ 退 bundle |
| Phase 48 | 搜索 26/26 全 400 | 全绿 | 搜索词 `q` 被 `buildParams` 静默丢弃 |
| **Phase 51** | 第一张卡点不动 | 全绿 | `_seq` 跨槽串台 + `validateParams` 口径不同步 |

★ 共同点：**缺陷不在任何单个文件里，而在两处"各自都对"的代码之间**。
所以"再多写点静态断言"解决不了 —— 必须真的把浏览器开起来、真的点、真的按键。

指南把这层登记为 **D14（真实浏览器渲染，仅部分补齐）** 与 **D27（浏览器内「键入」未实测）**。
本轮把 **D27 直接关掉**（真键盘事件已实测），**D14 缩小到"布局/像素级"**。

### 1.1 一处需要订正的旧表述（诚实优先）

指南此前写：**「本项目零第三方依赖 ⇒ 未装 Playwright / jsdom ⇒ 真实浏览器渲染未实测」**。
这句话有**两处不准确**：

1. 「零第三方依赖」约束的是**产品**（`06_PoC/js/` 无构建链、无 npm），**不约束测试仪器** ——
   `06_PoC/tests/a4_offline_render.py` 一直在用 Playwright 做断网渲染测试。
2. 本环境 Playwright 与 Chromium **都可用**（本轮实测 `import playwright` 成功、
   `%LOCALAPPDATA%\ms-playwright\chromium-1208` 在位）。

⇒ 「未实测」的真实原因是**当时没有仪器**，不是"环境不允许"。
这条已写入 `phase43_frontend_selfcheck.py` 的 docstring 与 SKIP 段（见 §8）。

## §2 仪器设计（`06_PoC/tests/phase51_task_flow_e2e.py`）

### 2.1 覆盖的链路（正是老板指定的那条）

```
首屏：1 个文本框 + 4 张示例卡
  ↓ 点卡 / 键入关键词
候选实体（≤5 条，标注类型/来源/score）
  ↓ 用户确认实体          ← 「避免自然语言歧义直接污染结果」
生成局部图（统一信封五态）
  ↓ 点「← 修改查询」      ← 「最后生成图后，需要调整的话就返回重新更改查询信息」
改范围（可信档 / 跳数）→ 重新生成 → 结论随之改变
```

### 2.2 五条设计纪律

| # | 纪律 | 做法 |
|---|---|---|
| 1 | **真值必须来自事实源，不得手抄** | 卡片文案、`CANDIDATE_LIMIT`、`MIN_QUERY_LEN`、`TASK_SCOPE_DEFAULT` 全部在断言时**从浏览器里 `import('./js/core.js')` / `import('./js/task.js')` 现取**（B1d）。手抄一份＝把"文档写错了"变成"测试通过"（铁律 #26 可复算即证据） |
| 2 | **缺依赖 ⇒ SKIP，不计通过** | Playwright 不在零安装路径上；缺失时逐段记 SKIP 并说明原因（铁律 #20：缺依赖不得假通过） |
| 3 | **真键盘事件，不是 `el.value=`** | `page.keyboard.type()` 逐字符 dispatchKeyEvent；过短输入断言"**不发请求**"（B3d） |
| 4 | **零外部请求** | 非 localhost 一律 `route.abort()` ⇒ 同时排除 CDN 与代理干扰；断言"被拦 0 条"（B5l） |
| 5 | **仪器自身可报错但不得丢结果** | 顶层异常兜底：打印 traceback + **仍然输出已完成的断言**（见 §2.3） |

### 2.3 仪器自身的一个教训（写进代码的注释里）

第一版在 B2 抛 `TimeoutError`（候选没出现）—— 而报告是**最后统一 dump** 的，
于是**已经通过的 B1 六条断言连同整份报告一起丢了**，排查时只能另写探针重跑。

⇒ 加了模块级 `_REP/_RESULT/_JSON_OUT` + `__main__` 里的 `try/except`：
**仪器崩了也必须交出"崩溃前已完成的部分"**，并显式记一条 `B0d-仪器未捕获异常`
且 RC=1（"不可判定"绝不当成"通过"）。这是铁律 #43「审计器可报错」的延伸。

## §3 D47（P1，阻断）· `_seq` / `_timer` 跨槽共享

### 3.1 现象（真浏览器首次运行）

点第一张示例卡（`relation`，"吉布斯自由能与熵之间有什么关系？"）：

```
#task-cands 的子槽 = ["second"]        ← ★ 没有 main 槽
main 候选 = 0 条 ／ second 候选 = 5 条
state.seed = null
#task-run.disabled = true
→ 用户无法前进（除非自己在文本框里重新打一遍字）
```

### 3.2 机制

`TaskEntry` 有**两个逻辑槽**：`main`（起点/唯一实体）与 `second`（终点）。
`applyCard()` 与 `open()` **都会并发调用** `_run("main")` + `_run("second")`。
而旧实现里：

```js
this._timer = null;      // ← 一个
this._seq = 0;           // ← 一个
...
const mine = ++this._seq;
const env = await this.api.search(s, {...});
if (mine !== this._seq) return;      // ← 「过期响应丢弃」
```

`_run("main")` 同步执行到 `await` 时 `_seq = 1`；紧接着 `_run("second")` 把 `_seq` 变成 **2**。
main 的响应回来时判 `1 !== 2` ⇒ **被当成过期响应丢掉**。100% 可复现，不是偶发。

### 3.3 对照实验（唯一变量 = 是否并发）

| 实验 | 操作 | `state.lastMain` |
|---|---|---|
| A | 点 `relation` 卡（内部并发查两端） | **`null`** |
| B-并发 | `_run('main')` 与 `_run('second')` 同时发起，同查询词 `gibbs` | **`null`** |
| B-单独 | 只 `_run('main')`，**同一个查询词** | **有值** |
| C | 点 `composition` 卡（ego，只查一个槽） | 有值（5 条） |

### 3.4 第二个后果：两个框打字互相取消

`_debounced(which)` 用**同一个** `this._timer` 做 `clearTimeout` ⇒ 在一个框里打字会
**取消另一个框待发的搜索**。旧的静态断言完全看不出来（两个 `addEventListener` 都在）。

### 3.5 修法

`_timer` / `_seq` 改为**按槽独立**：

```js
this._timer = { main: null, second: null };
this._seq   = { main: 0, second: 0 };
...
const mine = ++this._seq[which];
...
if (mine !== this._seq[which]) return;   // 只丢"本槽自己"的旧响应
```

> **同族性**：这与 Phase 50 的 **D45**（一个共享计数器被当成两个不同口径的集合大小）
> 同源 —— 「**共享的可变去抖状态被当成两条独立通道用**」。
> 两轮都在同一个代码库里咬中同一个模式，值得记成一条铁律（见 §8.1 铁律候选）。

### 3.6 新增断言

| 断言 | 内容 | 旧代码下 |
|---|---|---|
| **B2g** | 两个槽**各有一份**候选（起点/终点互不吞掉） | **红**（main 0 条） |
| **B3f** | 同一轮 JS 内派发两个 `input`（零时间差）⇒ **两个槽各自的搜索都发出去** | **红**（只发得出后一个） |
| **B3g** | 两槽候选都随之更新 | 红 |

`B3f` 的构造值得说明：**不用"快速连续操作"**（那会 flaky），而是用
`page.evaluate` 在**同一个同步 turn** 内 dispatch 两个 `input` 事件 ⇒ 时间差恒为 0，
断言的是"两槽各有独立计时器"这个**结构性事实**，不受机器负载影响。

## §4 D48（P1，阻断）· 校验侧与发送侧口径不同步

### 4.1 现象（D47 修复后的下一次运行）

```
[FAIL] B4g-图实例真的渲染出节点 —— cy 节点 0 / 边 0；status=error
[FAIL] B4i-路径查询确实发到了统一信封端点 —— ★ 未捕获到 /api/subgraph 请求
```

而 `status=error`、`store.depth=0`、`pageerror=0`、`console error=0`。

**拿到了错误信封，却一条 `/api/subgraph` 请求都没有** ⇒ 说明在**本地**就被拒了。

### 4.2 根因

`SubgraphStore.run()` 的第一行：

```js
const v = validateParams(params);
if (!v.ok) return { ok: false, error: v.message, field: v.field };
```

而 `validateParams` 的 path 分支**仍在校验 `src`/`dst`**：

```js
if (mode === "path") {
  if (!nonEmpty(o.src) || !nonEmpty(o.dst)) {
    return { ok: false, field: "src", message: "请给出起点与终点（可点「取选中」）" };
  }
```

但 **Phase 49 已把发送侧从 `src`/`dst` 改成了 `seeds`**（统一端点 `/api/subgraph?mode=path`
只读 `seeds`，需 2 个）。两处口径不同步 ⇒ **任务卡的每一次路径查询都在本地被拒**。

### 4.3 为什么此前一直没被发现

**同一个功能有两条代码路径，只有一条经过校验：**

| 入口 | 路径 | 是否过 `validateParams` | 状态 |
|---|---|---|---|
| 底部「高亮路径」`runPath()` | `state.api.subgraph(...)` **直接调** | ❌ 不过 | **一直好用** |
| 任务卡 `runTask()` | `runSubgraph` → `store.run` | ✅ 过 | **一直发不出请求** |

Phase 49 的修复（P0-4）改了 `taskRequest` 与 `runPath` 两处的**发送形状**，
`validateParams` 没动 —— 而当时的验证方式是**直接 curl API**，绕过了整个前端校验层。

> 这是 **E35 家族**（"跨层口径改了 A 处、漏了 B 处"）的第 4 例
> （前三例：`q`、`hops`、`subject`↔`subjects` / `exclude_inferred`↔`exclude_model_inferred`）。

### 4.4 修法

`validateParams` 的 path 分支改为校验 **`seeds` 含 2 个非空 id**，并**明确拒绝 legacy 形状**：

```js
const n = String(o.seeds ?? "").split(",").map(s => s.trim()).filter(Boolean).length;
if (n !== 2) return { ok: false, field: "seeds", message: 说明缺几个/多了几个 };
return { ok: true };
```

**为什么不兼容 `src`/`dst`**：`src`/`dst` 属 legacy `/api/path`（该端点按 D43 甚至不做 trust 过滤）。
把 legacy 形状判为合法 ⇒ 等于放出一个后端**必然**回 `no_result` 的请求
⇒ 把「参数形状错了」伪装成「知识上不存在」。**这正是本项目最反对的那类结论。**

### 4.5 新增断言（`node` 侧，纯函数层）

新增 **F40a–F40e**（`frontend_core_check.mjs`）：

| 断言 | 内容 |
|---|---|
| **F40a** | 【链路闭合】`taskRequest` 的 path 产物**能通过** `validateParams` |
| **F40b** | 【链路闭合】ego 产物同样能通过（同一不变量，不只覆盖 path） |
| **F40c** | 【负对照】`src/dst`、零端、单端、三端 **全拒**；`"A, ,B"`（空段被忽略）⇒ 两端 ⇒ 放行 |
| **F40d** | 被拒原因**可操作**（说清缺几个端点） |
| **F40e** | 未知 `mode` 仍被拒（改造 path 分支**不得顺手放宽** mode 白名单） |

★ 为什么单列一段（F40）而不是塞进 F38：F38h 早已断言 `taskRequest` 产出 `seeds='a,b'`，
两侧**各自全绿**，合起来却是死路。
⇒ 凡"一个组件产出、另一个组件消费"的字段，都要有一条**把产物真的喂过去**的断言
（同 D31 双向求差的动机）。

## §5 D49（P2）· 卡片承诺了它默认参数达不到的结果

### 5.1 实测（`CE:pq:gibbs_energy → PB:pq:entropy`）

| trust | hops | status | nodes | edges | paths | hidden | ms |
|---|---|---|---|---|---|---|---|
| verified | **2**（入口默认） | **no_result** | 0 | 0 | 0 | 12 | 346 |
| verified | 3 / 4 / 5 | **truncated** | **8** | **11** | 5 | 28 | ~370 |
| all | 2 | **no_result** | 0 | 0 | 0 | 0 | 362 |
| all | 3 / 4 / 5 | truncated | 8 | 11 | 5 | 0 | ~370 |

对照组（用户手输时挑到同名不同源的 `TH:pq:entropy`）：2 跳 `no_result`；
**5 跳也是 `no_result`（11.9 s 到 deadline）** —— 卡片注释想说的正是这件事。

### 5.2 问题

卡片 `relation` 的注释写「`Gibbs free energy ↔ entropy(PB)` 可连通（8 节点/11 边）」，
但那份数字是 **3 跳**下测的，而任务入口的**全局默认跳数是 2**
（`BUDGET.hops = 2`，是为**ego 卡**的邻域浏览定的）。

⇒ 用户点了第一张卡、确认两端、点「生成子图」—— 得到 `no_result`。
**发布了一个自己默认参数达不到的承诺。**

### 5.3 修法（两件一起，且都**不静默**）

1. **卡片注释订正**：写明「**3 跳起**可连通（8 节点 / 11 边 / 5 条路径）」，
   并补一句「把跳数调回 2，PB 那一支也会如实变成 no_result：**通路长度是真的**」。
2. **卡片自带推荐范围** `scope: { hops: 3 }`，`applyCard()` 应用 →
   紧接着的 `_fillForm()` 把结果**回写进输入框**（用户看得见、改得动，不是静默修正）。

**为什么不提高全局默认**：`BUDGET.hops = 2` 对 ego 卡是对的 ——
把全局改成 3 会让所有 ego 邻域查询无谓变大（`has_symbol` 一条就有 24 341 条边）。
「哪张卡需要更大范围」是**卡片自己的属性**，不是入口的属性。

新增断言 **B2h**：`#task-hops` 必须等于卡片 `scope.hops`（且详情里同时报出入口全局默认值）。

## §6 D50（P2）· 路径结论文案两套 + 失败态不写结论

### 6.1 两套文案

| 入口 | 旧文案 |
|---|---|
| 任务卡 | `任务卡路径查询：无结果` —— 就这七个字 |
| 底部路径栏 | 报出被隐藏的边数 + 「通路可能正被它们连接」+ 下一步动作 |

同一个结论（"没有路径"），两个入口给的解释不一样。
而这条文案承担的是**认识论责任**：`no_result` 对**可信档**与**跳数**都敏感，
只说"确实没有路径"就是把「被过滤掉了」或「跳数不够」**报告成「不存在」**
（铁律 #52：验证的命题须＝被发布的命题）。

### 6.2 失败态不写结论

`runTask` 旧实现：

```js
const env = await runSubgraph(params, { label });
if (!env) return;        // ← no_result / 空载荷 timeout 在这里就返回了
if (params.mode === "path") { ...写 #path-status... }
```

`runSubgraph` 在 `!hasPayload` 时返回 `null` ⇒ **`#path-status` 保留上一次的结论**。
比空白更糟：用户以为那是本次结果。

### 6.3 修法（收敛到唯一来源）

抽出 `pathOutcomeText(env, paths)` 作为**唯一**文案源（五态各自的可操作说明），
`runPath()` 与 `runTask()` 都调它；并让 `runTask` 在失败时用
`state.store.lastEnvelope` **兜底**，把本次五态如实写出来。

新增断言：

| 断言 | 层 | 内容 |
|---|---|---|
| **V12** | 静态 | `pathOutcomeText` 定义 1 处、引用 ≥3 处、`低可信度边` 字面量**只许 1 份** |
| **B5i** | 真浏览器 | `no_result` 文案必须指向**真正的原因**（跳数），不只写"切可信度档试试" |

`B5i` 的依据是实测：这个组合在 `all` 档**也是** `no_result`
⇒ 「no_result 是因为低可信度边被隐藏」这个假设**已被否证**，
故文案不能只给"切档"这一条无效建议。

## §7 D53（P1）与 D54（P2，仪器侧）· 一个"酷似 flaky"的失败，其实是**两个**缺陷叠在一起

### 7.1 怎么被发现的：它**不在**前四轮里出现

D47–D50 修完、`taskflow` 单跑 **45/0/0** 全绿之后，我按惯例跑**批量回归**
（`frontend → subgraph → gatecheck → release → release-full → eval → install → taskflow`）。
`taskflow` 在这一批里 **RC=1**：

```
  [PASS] B4f-出现「← 修改查询」入口（改查询的前提）  —— taskUsed=True reopenHidden=False
  [FAIL] B4g-图实例真的渲染出节点  —— cy 节点 0 / 边 0；status=None（None）
  [FAIL] B4h-状态栏状态 ∈ {ok, truncated}  —— status=None
  ...
  phase51_task_flow_e2e: PASS 43 / FAIL 2 / SKIP 0
```

★ **这正是最危险的一种失败**：单独跑必过、批量跑才挂 ⇒ 本能反应是"环境抖动，重跑一遍"。
如果当时这么做，它会变成一条"偶发"备注 —— 而**两个**真缺陷都会留在代码里。

### 7.2 先问"是谁先放弃的"（这一问同时否证了一个归因）

第一反应（也是最自然的归因）：**"机器忙，后端来不及算"**。
要证伪它只需一个观测：**服务端到底有没有给出信封**。

重负载期间实测：

| 观测 | 空闲 | 重负载 |
|---|---|---|
| `/api/subgraph` 请求是否发出 | 是 | **是**（URL 已被捕获，参数正确） |
| 服务端是否返回信封 | 是 | **是**（约 12.0 s 后返回 `status=truncated`） |
| 前端 `Api` 是否收到 | 是 | **否**（约 3.0 s 时 `api.last = {http:0, error:"signal is aborted without reason"}`） |

⇒ 「后端来不及算」**被否证**：后端算了，也算完了。是**客户端先走了**（**E46 的第二次实例**）。

### 7.3 D53（P1）· 跨层时间预算不匹配：客户端比服务端早 7 秒放弃

```js
// 06_PoC/js/api.js（HEAD `dc08b42`，即修复前）
this.deadlineMs = opts.deadlineMs || 3000;                    // ← 实例默认 3 s
...
subgraph(opts) { ... this._get(ENDPOINTS.subgraph, p,
      { deadlineMs: opts.deadlineMs || this.deadlineMs }); }  // ← 固定回落 3 s
```

而同一个请求**自带**的服务端预算是 **10000 ms**（`deadline_ms`，来自 `core.BUDGET`；
服务端 `queries.py` 同名默认值亦为 10000）：

| 层 | 预算 | 谁定的 |
|---|---|---|
| 浏览器 `fetch` 的 AbortController | **3 000 ms**（实测 3 250 ms 触发） | `Api` 构造时硬编码 |
| 服务端查询的 deadline | **10 000 ms** | 请求参数 `deadline_ms` |

**客户端比服务端早约 7 秒放弃。** 空闲时后端 <1 s 就答，看不出问题；
重负载时后端要 ~12 s ⇒ 用户看到的是「超时（客户端中止，服务端结果未知）」，
而**后端本来会给出 8 节点 / 11 边的答案**。这不是 flaky，是**每次都错，只是平时快得看不出来**。

★ 这是**同一族的又一处**：**两处"各自都对"的代码之间**（§1 表）——
前面几处是"字段口径不一致"，这次是"**时间预算不一致**"。

### 7.4 D54（P2，**仪器侧**）· 「固定延时」不是「等待」——`status=None` 的真身

上面对照实验除了否证"后端来不及算"，还顺手否证了另一条**我原本已经写进报告的归因**：
我把 `status=None` 解释成"客户端中止时的取值"。于是做了一次**独立的受控实验**来验证它：

> 只改浏览器里的被测实例（把 `api.subgraph` 包一层，让客户端预算变成 300 ms），
> 请求参数一个字不改，另在**网络层**延迟响应 3 s，然后走真实 UI 路径。

结果（原始数据见附录 A.4）：

```
clientBudget = 300            ← 客户端预算 300 ms
apiLast      = {http:0, ms:552, error:"signal is aborted without reason"}
lastEnvStatus        = "timeout"        ← ★ 不是 None
lastEnvClientAborted = true
hasLastEnv           = true             ← ★ state.lastEnv 被写入了
statusline = "超时 … error_code GRAPH_QUERY_TIMEOUT 客户端中止（服务端结果未知）"
pathStatus = "任务卡路径查询：路径查询超时（非失败）：可降低跳数或提高超时"
```

⇒ **客户端真的中止时，`status` 是 `timeout`（带 `client_aborted=true`），且 `state.lastEnv`
一定会被写入** —— 失败路径 `onEnvError()` 里就写着 `state.lastEnv = env`。

所以 **`status=None` 不可能意味着"客户端放弃"**：它唯一的含义是
**`state.lastEnv` 从未被写入过**，即**读到的时刻状态还没有 settle**。

于是真身浮出：**仪器自己**在点完「生成子图」后只 `wait_for_timeout(600)` 就断言：

```python
page.click("#task-run")
page.wait_for_function("…task-entry.hidden === true…")   # 入口是**点下去就藏**的，立刻返回
page.wait_for_timeout(600)                               # ← ★ 只等 600 ms
e1 = page.evaluate(JS_ENV)                               #   然后就读状态
```

重负载下这一次查询要好几秒 ⇒ 600 ms 时**答案还没回来** ⇒ `lastEnv` 仍是 `null`
⇒ `status=None` / `cyNodes=0` —— **「还没回来」被读成了「图没渲染出来」**。

★ 这是**仪器比产品更不诚实**的一种失败（E44 的同族）：
**一个固定延时在快机器上全绿、在慢机器上制造假失败**，
而假失败又长得像"产品没反应"，于是它把嫌疑指向了产品。

### 7.5 修法

**(1) D53 —— 把预算变成"从请求本身派生"**

`core.js` 新增常量与纯函数；`api.js` 的 `subgraph()` 按**本次请求自己的** `deadline_ms` 派生：

```js
export const CLIENT_MARGIN_MS = 4000;

// 判据顺序：显式 deadlineMs > deadline_ms + marginMs > fallbackMs
// 非法输入（0 / 负数 / NaN / 字符串 / null）一律回落 ——
// 否则一个 NaN 会让 setTimeout(…, NaN) 等价于**立即 abort**（比 3 s 更糟）。
export function clientBudgetMs(opts = {}, defaults = {}) { ... }

// api.js
const budget = clientBudgetMs(opts, {
  fallbackMs: BUDGET.deadline_ms + this.marginMs, marginMs: this.marginMs,
});
this.lastBudgetMs = budget;      // 供真浏览器验收断言（B4k）
```

**不变量**：`客户端预算 > 请求自己的 deadline_ms`，且余量 `> 0`。

**(2) D54 —— 断言前必须等**可观测的终止条件**，不得用固定延时**

仪器新增两个小工具函数，B4 与 B5 的两处「改查询重跑」全部改用它：

```python
def wait_settled(page, timeout_ms=60000):
    """等到 `state.lastEnv` 相对**进入查询前**打的标记发生了变化。"""
    page.wait_for_function(
        "() => (window.__sttp.lastEnv || null) !== window.__sttp.__settleMark",
        timeout=timeout_ms)      # 等不到 ⇒ False ⇒ 记「不可判定」，不记「产品失败」
```

★ 注意这里判的是**「`state.lastEnv` 有没有被重写」**，而不是"等 5 秒"：
「有结论」这件事在页面上**只有一个可观测信号**（`lastEnv` 被写入），
所以等待它就等于等待"这次查询结束了"——**不依赖机器快慢**。

### 7.6 新增断言

| 断言 | 层 | 内容 | 为什么它在**空闲时也有牙** |
|---|---|---|---|
| **F41a–F41f** | `node`（纯函数） | 预算**严格大于** `deadline_ms`；显式覆盖优先；非法输入回落；`Api.subgraph` 真的派生（不是只导出一个没人用的函数） | 断言的是**不变量**，不是耗时；F41b 实测 `1000→5000 / 10000→14000 / 30000→34000` |
| **B4k** | 真浏览器 | 从**实际发出去的 URL** 里取 `deadline_ms`，与 `window.__sttp.api.lastBudgetMs` 比较 | 同上 —— 空闲时也照红/绿；**负载只决定能否复现，不决定判据** |
| **B4l** | 真浏览器 | 断言 `B4g`/`B4h` **之前**状态已 settle（`lastEnv` 已被写入）；等不到则记**不可判定** | 它把"600 ms 够不够"从一个**运气问题**变成一个**不变量** |
| **B5m** | 真浏览器 | 两次「改查询重跑」（`all` 档 / 2 跳）同样都在 settle 后才断言 | 同上 |

★ B4k 取自**实际请求 URL**（而非读源码/读常量），所以它同时守住了另一件事：
**"派生的预算"与"真正发出去的请求"是同一个数**（铁律 #85 的同族要求）。

### 7.7 因此新增的纪律

- **E46（本轮第二次实例）｜"看起来合理的归因"必须用一次对照实验证伪才可用。**
  第一处实例是 D49：「`no_result` 是因为低可信度边被隐藏」被
  「切到 `all` 档**仍然** `no_result`」一次实验否证，真因是**跳数**。
  第二处是 D53/D54：「B4g 失败是因为机器忙（后端没算完）」被
  「服务端 12.0 s 后**确实**返回了信封」否证；
  而「`status=None` 是客户端中止的取值」又被
  「把预算压到 300 ms 实测 ⇒ 拿到的是 `timeout` 且 `lastEnv` 有值」否证。
  ⇒ 凡"环境/负载导致"的归因，**必须实测到底是谁先放弃**，不得直接归给环境。
- **#94｜两层的"时间预算"必须显式对齐，且外层的必须严格大于内层的。**
  凡 A 会在 B 之上再加一层超时（HTTP 客户端 / 网关 / 重试 / 代理 / 抓取器），
  该超时**必须从 B 的预算派生**（`B + margin`），不得硬编码常量；
  且必须有一条**跨层**断言真的比较这两个数 ——
  只断言各自"在合法范围内"会给出双份绿（同 #92 同族）。
- **#95｜「固定延时」不是「等待」。**
  凡断言依赖异步结果，必须等待**可观测的终止条件**（某个状态字段被写入），
  不得用 `sleep(N)` / `wait_for_timeout(N)`。固定延时在快环境全绿、在慢环境读到**中间态**；
  更糟的是，中间态通常长得像"产品没反应"，会把嫌疑指向产品。
  （实测：600 ms 固定延时 ⇒ `status=None` / `cyNodes=0`，看起来像"图没渲染"。）

★ **#94 与 #95 是一对**：一条管"外层不得比内层先放弃"（预算），
一条管"断言前必须确认真的结束了"（等待）。两者都指向同一件事 ——
**"停止等待"这个动作必须被显式设计，不能靠常量与运气。**

### 8.1 铁律候选

- **#91**｜**共享的可变去抖状态不得被当成两条独立通道用。**
  去抖计时器与请求序号必须**按逻辑通道独立**；跨通道共享会让
  "过期响应丢弃"退化成"新通道吃掉旧通道的结果"。
  （实测：同一查询词，并发时结果被判过期丢弃、单独调用时正常。）
  —— 与 **D45/#89** 同族：**共享的可变量 + 多口径使用**。
- **#92**｜**"两侧各自正确"不等于"两者对得上"。**
  凡 A 组件产出、B 组件消费的字段，必须有一条**把 A 的产物真的喂给 B** 的断言；
  只断言各自形状，会在两处口径漂移时给出双份绿。
- **#93**｜**"环境不允许"必须先被证伪再用。**
  本项目指南曾以"零依赖环境无 Playwright"为由把真实浏览器验收长期记为未覆盖 ——
  而 Playwright 一直可用（另一个测试文件就在用）。**未覆盖的真实原因要如实写**
  （"当时没有仪器"），不得用环境当挡箭牌。
- **#94**｜**两层的"时间预算"必须显式对齐，且外层的必须严格大于内层的。**
  凡 A 会在 B 之上再加一层超时（HTTP 客户端 / 网关 / 重试 / 代理 / 抓取器），
  该超时**必须从 B 的预算派生**（`B + margin`），不得硬编码常量；
  且必须有一条**跨层**断言真的比较这两个数 ——
  只断言各自"在合法范围内"会给出双份绿（与 **#92** 同族）。
  （实测：客户端 3 000 ms vs 服务端 10 000 ms ⇒ 空闲全过、重负载必挂。）

★ **#94 与它的"表亲" #86 合起来才完整**：一个说"外层不得比内层先放弃"（**预算**问题），
另一个说"外层放弃了也必须如实区分是**它自己**放弃、还是**内层**拒绝"（**归因**问题）——
两者都在"停止等待"这件事上。本轮的 `status=None` 正是**两条都没守**：
预算比内层短（#94），且前端没有把它标成一个独立的状态码（#86）。

（教训：**编排顺序**表达因果依赖，**编号**表达"加入的先后" —— 两者不必一致，
但必须在报告里说清楚，否则下一个人会以为是接线错了。）

## §11 仍存边界（本轮**没有**收掉的）

1. **布局 / 像素级断言**：元素位置、视觉重叠、响应式断点 375/768/1024/1440 —— 无截图基线，未测。
   这是 **D14 的剩余部分**（交互链路已由 `taskflow` 收掉）。
2. **浏览器内核单一**：只有 Chromium；Firefox / WebKit 未测。
3. **`taskflow` 需要运行中的 viz 服务**：不是自包含的（不像 `subgraph` 那样自己起后端）。
   服务不在 ⇒ 全段 SKIP 并打印启动命令。
4. **未点击**：PNG / SVG / JSON 导出、「展开邻居」、「概览」、「返回上一层」、布局切换下拉。
5. **未做键盘 Tab 序全量走查**：只覆盖 Enter 提交 / Escape 关闭路径上的监听存在性。
6. **未做性能断言**：刻意不做 —— 首帧耗时随负载波动，测时间会得到 flaky 断言
   （Phase 49 的教训：`cache_builds` **计数**优于测耗时）。
7. **CDN 兜底支路未测**：本仪器刻意 abort 所有非本地请求。
   该支路由 `a4_offline_render.py --scenario cdn-fallback` 负责（但那个脚本**未接进 `sttp.sh`**）。
8. **`a4_offline_render.py` 不在标准回归里**：它存在、能用，但没有 `sttp.sh` 目标
   ⇒ 容易再被忘掉（同 E34「手写清单总会漏」的形态）。**列为下轮候选。**
9. **D43 仍未统一**：`mode=path`（应用 trust）与 legacy `/api/path`（不应用）对同一对节点给两个答案 ——
   按 **Option** 处理，不计指摘。
10. **D46 未做**：`hidden_by_trust` 的语义是"已探索范围内被排除的不同边数"，
    不是"全图隐藏总数"；后者若要做须由 `filter` 模式**另开字段**。
11. **D54 只收掉了"gate 断言的那些"固定延时**：仪器里仍有若干**短延时**用于
    "让 DOM 更新/让 Playwright 收到事件"（如点卡后 400 ms、派发 input 后 300 ms）。
    它们**不 gate 任何断言**，但严格说同样是"赌机器够快" —— 属已知残余，见 §9 的长注释。
12. **D53 只在 `subgraph` 端点修了**：`search`（3 s）/ `overview`（5 s）/ `legacy stats`（2 s）
    的预算仍是**常量**，没有从服务端预算派生。它们的服务端预算本来也没有参数可传
    （`search` 不吃 `deadline_ms`），所以"跨层不匹配"这一条对它们**不适用**；
    但"外层超时是硬编码常量"这个形态仍在，**列为下轮候选**（若要收敛，应改成从端点契约派生）。
13. **新工具 `assert_name_diff.py` 自身未被断言覆盖**：它是"给人看的差集工具"，
    输出可观察、无副作用，但没有自检。若要"仪器的仪器"，须补一个已知答案的样本对
    （同 `gatecheck` 的做法）。**列为下轮候选。**
