### 2. 未采纳的一行（请 Codex 复核，这是本次最需要答复的一点）

远端把 `_covered()` 中的

```python
if comp.get("from") != rec:      # 本地保留
    continue
```

改成

```python
if False:  # redprobe: 不再核对 from（证明可跨版本复用）   ← 远端
```

`from` 是内容等价证明的**绑定四要素之一**（起点值 / 终点值 / 对象 / HEAD 归属），
它管的是「这张证明的起点是不是当时那条记录」。改成 `if False` 后，只要对象名与终点值
对得上就放行 **⇒ 证明可跨版本复用 ⇒ 证据链可被伪造**，直接违反本项目「判据必须可红」的铁律。

**为什么判断这不是判据失灵，而是测试环境失灵**：本轮实测了同一个服务在「有 git」与
「无 git」两种环境下的判定，结果如下（同一份 `normalized.json`，sha256 `fec51bf0f201…`）：

| 环境 | verified | changed | changed_but_proven | 不可验证 |
|---|---|---|---|---|
| 有 git（本机仓库） | 831 | 703 | 703 | 47,055 |
| 无 git（发布副本实测） | **0** | **0** | 0 | **48,589** |

远端交接文档亦自陈「原工作目录没有 Git 历史」。因此在无 git 环境跑红探针失败后关掉判据，
是把**环境缺陷**记到了**判据**头上——这与此前 D107 / D134 是同一类错误处置的第三次重演。

### 3. 使用成本实测（对应「降低使用成本」这一方向）

同一台机器、同一 Python 3.11.9，实测三种运行形态：

| 形态 | 启动数据 | 常驻内存 / 峰值 | 第三方依赖 | 冷启动 |
|---|---|---|---|---|
| 工程版 `viz_server.py`（原科研辅助） | `normalized.json` **80MB** | **455MB / 510MB** | networkx | 首页 10ms；`/api/stats` 数秒（需现算判据） |
| 探索版·精选 `06_PoC/demo/serve.py` | `data.json` **27KB** + `daily_terms.json` 2.7KB | **24.9MB / 25MB** | **无**（纯标准库 + sqlite3） | 首页 39ms |
| 探索版·原图库模式 | 需先由 80MB 原图构建 SQLite | — | 无 | 构建 **5.1 秒**，产物 **111MB** |

结论：探索版精选模式相对工程版是 **20 倍内存差**（25MB vs 510MB）、**3000 倍数据量差**
（27KB vs 80MB），且**零 pip 依赖**。原图库模式把成本推到磁盘（111MB SQLite），
但不占内存、5 秒可重建。

**给降成本的三条具体建议**（供排期，未实施）：

1. **默认入口改成精选包**：干净检出不需要 80MB 原图即可完整试用；原图库作为「进阶模式」
   按需构建。这已由探索版实现，缺的是把它定为默认并写进安装说明。
2. **不把 111MB SQLite 当分发物**：它是本地快照（构建只要 5.1 秒），分发时应只给构建脚本。
3. **线上/公网形态必须解决 git 依赖**：本轮实测 `git bundle create --all` 只要 **7.3MB**
   （268 提交），容器里 `git clone --no-checkout` + `git read-tree HEAD` 即可还原索引，
   实测判定恢复为 831 / 703 / `changed_unproven=0`、`snapshot_id` 与本机**逐位一致**。
   否则线上会显示「0 条已验证」，等于自毁证据链。
