# Codex 与 WorkBuddy 协作交接

本目录是 STTP 项目的共同交接入口。项目负责人提出目标并作最终取舍；Codex 和 WorkBuddy 均可开发、测试、评估及复核，具体分工以每次任务的实际安排为准。

## 每次开始工作

1. 确认用户的最新要求，以及仓库和当前分支：`git status --short --branch`、`git log -1 --oneline`。联网核对 `main`；有未提交改动时先识别归属，不覆盖或清理他人的工作。
2. 阅读 [当前状态](当前状态.md) 和 [任务看板](任务看板.md)，再查看与任务有关的代码、数据及原始资料。文档中的数字和结论都有时间范围，实际代码和测试结果优先。
3. 在任务看板记录认领人、工作范围和起始提交；如其他助手正修改相同文件，先协调分工。**看板是人工记录，不是自动锁。**
4. 完成后更新看板，并用 [交接模板](交接模板.md) 新建独立记录，写明变更、测试、未完成项、风险和下一步。文件名示例：`20261030_Codex_主题.md`，避免多人同时改同一条记录。
5. 提交前检查差异与敏感信息；推送前重新获取远端。若远端变化，以 Git 合并或变基处理并重新测试，不强推、不静默覆盖。若没有凭据或权限，保留本地提交并说明实际阻碍。

## 约定

- GitHub 是已推送版本的共同基线；本地未提交和未推送内容不会自动同步。每次交接给出提交号及分支。
- 同一份代码最好在带 Git 的检出目录工作，不要把两个目录当作自动同步的同一工作区。本机曾使用 `F:\codex\sttp` 保存原始项目及数据，`F:\codex\sttp\github_sync` 是独立 Git 检出；具体位置由使用者确认，其他电脑不应假设这些路径存在。
- 原始数据、许可边界、数据库、个人反馈和统计记录需要分别处理。不要提交 `.env`、令牌、账户信息、私人使用记录或未经许可的数据；遵守根目录 `.gitignore` 和 [数据许可说明](../../DATA_LICENSES.md)。
- 交流记录写结论和可核验的证据，不记录密码、令牌、认证码、用户身份信息或完整私人对话。公开仓库内的文档默认任何人可见。
- 修改前了解已有实现及验收要求；不以“已评估”“已测试”“已发布”代替命令、结果、范围和限制。
- 用户提出的四项要求适用于项目评估与研发：专家还会补做什么、使用哪些最原始素材、采用哪些方法工具、有什么独立证据验证结果。必要时参照 [项目要求](../项目评估与研发四项要求_20261026.md)。
- 本目录不会自动通知另一位助手。交接时须向对方提供本目录地址、最新提交号和需要处理的任务。

## 推荐记录格式

目录中的 `README.md` 是使用规则；`当前状态.md` 是有日期的快照；`任务看板.md` 是人工维护的任务列表；各次交接记录按日期独立保存。与源码不一致时先核实并更新文档。
