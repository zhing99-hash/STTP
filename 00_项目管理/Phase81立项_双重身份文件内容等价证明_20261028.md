## 一句话

> 让「改了文件但语义没变」这件事，**有正规通道可走**，而不是只能靠「别碰这个文件」回避。

## 为什么现在必须立

2026-10-27 的三红（V16c / V18d / V18h）根因是：`11_真实数据/element_reference.py`
这个**双重身份文件**被加了一行纯注释，三族哈希同时失配 ⇒ **35040 条证据（占 70.5%）**一次翻 stale。

当时选了路线 A（回退注释 + 豁免外挂）。那是**回避**，不是解决：

| 族 | 原因码 | 影响证据条数 | 现有等价证明通道 |
|---|---|---|---|
| 来源 | `src_changed`（`Phase13.Gate.B2` 5 条 / `B5` 734 条） | 739 | **无** |
| 参考表 | `ref_changed`（`element_reference`） | 35040 | **无** |
| 验证器依赖 | `dep_version_changed`（本文件） | 32609 | **无** |
| 验证器本体 | `verifier_changed` | — | **有**（Phase 73，rva） |

（并集 35040 条证据 / 34978 条边；以上均为 2026-10-28 对 `06_PoC/etl/normalized.json` 现算，非抄旧报告。）

只要「无通道」这件事还在，下一次任何人给这类文件加一行注释、改一行缩进，就会**再来一次同样的三红**。

## ① 专家补做项

| 补做了什么 | 为什么可能改变结论 | 状态 |
|---|---|---|
| 先量影响面再谈通道 | 若影响面只有几十条，这条路不值得立（纯属自找自赦面）。实测 **70.5%** ⇒ 值得 | ✅ 35040/49673 |
| 数清「改 1 个文件要几张证明」 | 若 1 张就够，设计很简单；实测该文件同时充当 **2 个来源 locator + 1 个参考表 + 1 个验证器依赖** ⇒ **1 次改动 = 4 张 attestation**，成本不是一个数量级 | ✅ 已数 |
| 核对三族哈希的**取值口径**是否同源 | 若口径不同（一个是工作区字节、一个是仓库 blob），证明的 from/to 会对接错层，通道开着也是漏的 | ✅ 已核：src = `sha256(Σ sorted(rel+NUL+bytes+NUL))[:12]`；ref = `sha256("rel:h" 逐文件拼接)[:16]`；dep = `sha256(仓库 blob)[:12]`；三者**都取仓库字节** |
| 反向自检：这条路是不是在给「洗白」开门 | 是的，这是本立项的**主要风险** —— 证明写松就能把真变更说成没变 | ⚠️ 见下方「自赦面」与验收设计 |

**仍未补做（动工前必须先补）**：

1. **「注释不进 AST」之外的语义改动怎么办** —— 改原子量、加元素条目，AST 会变，第一档证明拒。
   也就是说本通道**只解决 D137 那类（注释/空白），不解决真改数据**。真改数据仍需另开档位 + 另配负对照。
2. **`ref` 是复合哈希**：多文件参考表（`dimension_table` 登记 2 个文件）必须**每个文件都有证明**才抵；
   少一张 ⇒ 整条 ref 仍 stale。这条 fail-closed 规则还没写进代码。
3. **读侧一旦改错，影响面是 70.5%**，而 `normalized.json` **不入库**（无 git checkout 可救）。
   动工必须在**系统临时副本**上做（D134 的教训）。

## ③ 方法与工具

| 问题 | 输入 | 步骤 | 工具及版本 | 输出 | 判定标准 |
|---|---|---|---|---|---|
| 两版字节是否**语义逐位等价** | from/to 两版 git blob（按内容哈希反查 rev，fail-closed） | 各自 `ast.parse` → `ast.dump(include_attributes=False)` → 逐字符比 | CPython 3.11.9 标准库 `ast` | 成立/拒绝 + 拒绝原因 | `dump` **逐字符相同**才成立；任一字符不同即拒 |
| 证明的 from/to 是否与图上记录对齐 | 图上 `src_hash`/`refs`/`dvs` + 当前快照 | 按族分别比对（src 用 locator 复合口径、ref 用复合口径、dep 用单文件口径） | `evidence_deps.py`（现有） | 对齐/失配 | 三者**全对齐**才生效；任一失配即不抵 |
| 证明是否**可重算** | `reverify_attestations.json` 全部条目 | 每条回到 git 历史取真 blob 重算 | `reverify_attest.py --check`（扩 kind） | 逐条 成立/不成立 | 算不出来 ⇒ 整条不成立（fail-closed） |
| 通道是否**没接错线** | 构造的假 attestation（object_id 指向别的文件） | 读侧应**不生效** | 新负对照 | 生效/不生效 | 必须不生效 |

版本锁定：Python 3.11.9 / RDKit 2026.09.1 / networkx 3.6.1（沿用既有口径，不升级）。

## ④ 独立验证

**注意：本段写的是「动工后的验收设计」，本立项文档自身尚未跑这些**（立项 ≠ 实现）。

| 级 | 线 | 证明到哪一步为止 |
|---|---|---|
| **A** | 原始字节比对：证明里的 `from_hash` / `to_hash` 与 git blob 现算值逐字符一致 | 证明到「证明对象确实是那两版字节」，**不**证明语义等价 |
| **B** | 第三方工具：CPython 标准库 `ast` 判定（与本项目无同源关系） | 证明到「AST 逐位相同」；**不**证明运行时行为相同（docstring、`__all__`、装饰器副作用等不在本通道范围内） |
| **C** | 外部审稿：通道建成后，把「证明器 + 负对照清单」交外部模型逐条挑漏（沿用 2026-10-26/27 两次 codex 复核的做法） | 证明到「第三方没找到漏」；**不**证明不存在漏 |
| **D** | 外部数据库：`element_reference.py` 的 118 元素原子量/周期/族与 PubChem（或同等外部源）逐元素对表 | 证明到「文件内容对外仍正确」—— 这是**独立于我方自证**的第三方差数，也是本通道最需要的那一级：它回答「你说没变，那对外还对不对」 |

### 验收判据（动工时落成，编号待分配）

| # | 判据 | 为什么必须有 |
|---|---|---|
| S99a | 表内**每条**证明可被 `--check` 重算 | 证明是「待复核的断言」，不是通行证 |
| S99b | **腐烂即红**：from/to 与当前快照不符的条目必须被报出 | 防止死条目挂着当装饰 |
| S99c | **越权即红**：object_id 指向别处的证明**不得**抵掉本条原因 | 防止一张证明洗白全局 |
| NEG-S99 | **负对照**：改一个原子量 / 改一个键 ⇒ 证明器**必须拒** | 证明器不拒，就等于通道全开 |
| 非真空 | 放上一张有效证明 ⇒ 必须有 N > 0 条证据被抵 | 否则通道根本没接上 |

### 反驳条件

- 若「改一个原子量」时 `ast_identical` **没有拒绝** ⇒ 证明器方法错误（AST 常量没参与比对），本通道作废。
- 若放上一张有效证明后，被抵的证据条数为 **0** ⇒ 通道没接到读侧，S2 未完成却宣称完成。
- 若 `element_reference.py` 保留注释后重跑全链闸门仍出现 V16c / V18d / V18h 任一红
  ⇒ 「三族同源」的归属判定错（推论：我对三族口径的核对写错了），需回退读侧改动重查。
- 若 D 级对表发现 118 元素里有**任何一条**原子量/周期与 PubChem 不符
  ⇒ 「内容对外仍正确」不成立，本通道即便自证通过也不得用于该文件。

## 分步与出口

**我的选择：分两步走，先证明器、后读侧。** 理由：读侧一改就牵动 70.5% 的证据，
而 `normalized.json` 不入库（改坏了没有 git checkout 可救，D134）。先把「证明器会拒真变更」
钉死（S1 + 全部负对照），再开读侧的闸（S2），这样最坏情况也只是「通道没开」，不会是「洗白了 35040 条」。

| 步 | 内容 | 出口判据 |
|---|---|---|
| **S1** 证明器 | `reverify_attest.py` 增 `--object {src,ref,dep}` + 方法 `ast_identical`；新 kind `content_equivalent` | NEG-S99 红得起来；S99a 能重算 |
| **S2** 读侧 | `evidence_status` 第 3.5 步从「只抵 `verifier_changed`」扩到按族抵；`_attestation_ok` 按 object_id + from/to 对齐 | 非真空探针 > 0；S99c 红得起来 |
| **S3** 真用例 | 把 `element_reference.py` 那行注释**加回来**，出 4 张证明（src×2 + ref×1 + dep×1），全链闸门须仍为 0 FAIL | 十步 `[FAIL]` 计数 0，且 `changed` 不回升 |
| **S4** D 级 | 118 元素对外部源 | 见「反驳条件」最后一条 |

**范围外（本立项不做）**：真改数据（改原子量/加条目）的档位；`*_raw.json` 类大体积 locator 的等价判定。

## 代价与未来问题（立项必须同时看清的两面）

**好处**：以后改这类文件不用扭曲代码（不用为了保哈希而把说明文字藏到仪器侧）；
证明是**机械可重算**的（`ast.dump` 逐字符），不是「我说没变」。

**未来的问题**：

1. **新开了一道自赦面。** Phase 73 的 `rva` 只抵 `verifier_changed`，本通道把它扩到三族，
   可抵的证据从 3.2 万量级变成**覆盖全图七成**。证明器写松 = 洗白。这是本立项**唯一的真风险**，
   缓解手段只有一条：第一档只放行 `ast_identical`（最严），更宽档位必须另配负对照才能开。
2. **覆盖面窄。** `ast_identical` 只覆盖「不进 AST 的改动」：注释、空行、行尾空白。
   docstring、类型注解、任何常量 —— 一律拒。所以它**没有彻底解决 D137**，只是把「加注释」这一类变成可走。
   真改逻辑仍要 Phase 73 同款的结构性证明（且目前 `rva` 对结构性证明的支持也只到验证器族）。
3. **证明张数随文件身份数增长。** 一个文件当 N 个身份用就要 N 张证明（本例 N=4）。
   若将来再出现「三重、四重身份」文件，`reverify_attestations.json` 的维护会变手工活 ⇒
   S1 应顺带产出「该文件当前充当哪些身份」的自动清单，否则人会漏开。
4. **闸门时间变长。** `--check` 要对每条证明回 git 历史取 blob；张数上去后需考虑缓存
   （但缓存会引入「陈旧证明仍被认」的新风险，届时另议）。
