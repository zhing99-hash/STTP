## ③ 方法与工具

| 问题 | 输入 | 步骤 | 工具及版本 | 输出 | 判定标准 |
|---|---|---|---|---|---|
| 两版字节是否**语义逐位等价** | from/to 两版 git blob（按内容哈希反查 rev，fail-closed） | 各自 `ast.parse` → `ast.dump(include_attributes=False)` → 逐字符比 | CPython 3.11.9 标准库 `ast` | 成立/拒绝 + 拒绝原因 | `dump` **逐字符相同**才成立；任一字符不同即拒 |
| 证明的 from/to 是否与图上记录对齐 | 图上 `src_hash`/`refs`/`dvs` + 当前快照 | 按族分别比对（src 用 locator 复合口径、ref 用复合口径、dep 用单文件口径） | `evidence_deps.py`（现有） | 对齐/失配 | 三者**全对齐**才生效；任一失配即不抵 |
| 证明是否**可重算** | `reverify_attestations.json` 全部条目 | 每条回到 git 历史取真 blob 重算 | `reverify_attest.py --check`（扩 kind） | 逐条 成立/不成立 | 算不出来 ⇒ 整条不成立（fail-closed） |
| 通道是否**没接错线** | 构造的假 attestation（object_id 指向别的文件） | 读侧应**不生效** | 新负对照 | 生效/不生效 | 必须不生效 |

版本锁定：Python 3.11.9 / RDKit 2026.09.1 / networkx 3.6.1（沿用既有口径，不升级）。

## 代价与未来问题（立项必须同时看清的两面）

**好处**：以后改这类文件不用扭曲代码（不用为了保哈希而把说明文字藏到仪器侧）；
证明是**机械可重算**的（`ast.dump` 逐字符），不是「我说没变」。

**未来的问题**：

1. **新开了一道自赦面。** Phase 73 的 `rva` 只抵 `verifier_changed`，本通道把它扩到三族，
   可抵的证据从 3.2 万量级变成**覆盖全图七成**。证明器写松 = 洗白。这是本立项**唯一的真风险**，
   缓解手段只有一条：第一档只放行 `ast_identical`（最严），更宽档位必须另配负对照才能开。
2. **覆盖面窄。** `ast_identical` 只覆盖「不进 AST 的改动」：注释、空行、行尾空白。
   docstring、类型注解、任何常量 —— 一律拒。所以它**没有彻底解决 D137**，只是把「加注释」这一类变成可走。
   真改逻辑仍要 Phase 73 同款的结构性证明（且目前 `rva` 对结构性证明的支持也只到验证器族）。
3. **证明张数随文件身份数增长。** 一个文件当 N 个身份用就要 N 张证明（本例 N=4）。
   若将来再出现「三重、四重身份」文件，`reverify_attestations.json` 的维护会变手工活 ⇒
   S1 应顺带产出「该文件当前充当哪些身份」的自动清单，否则人会漏开。
4. **闸门时间变长。** `--check` 要对每条证明回 git 历史取 blob；张数上去后需考虑缓存
   （但缓存会引入「陈旧证明仍被认」的新风险，届时另议）。

## 本轮踩到的坑（学费 D139）

**负对照的变异器用正则定位，会改到注释里去。**
第一版 NEG-S99b「改一个数字常量」用 `re.search(r"\d+\.\d+")`，命中的是文件头
