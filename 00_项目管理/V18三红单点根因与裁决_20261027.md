## ③ 方法与工具

- **哈希归属判定**：写一次性诊断脚本，对三族（src / refs / dvs）分别用各自的**原算法**
  （`source_registry.hash_files`、`evidence_deps.reference_content_hash`、
  `evidence_deps._repo_bytes_hash`）重算，对照记录值判定归属 `old` / `new` / `?`，
  得到「记录值 ≡ 旧版字节」的确定结论（脚本用完即删，不入库）。
- **因果消融对照**：临时把该文件换回注册时的旧字节 → 跑 `lineage_invalidation.py`，
  `ref_changed` 归零；跑 `phase79_selfcheck.py`，S94 立刻命中 `element_reference.py:234[:1]`。
  两次操作后均**逐字节还原并校验 sha256**（`251c435e…` 前后一致）。
- **修复工具**：`git cat-file blob` 取回注册时字节 + 编辑落回（再次现算校验
  `src_hash 现算 1fe029a4cdc898eb` == 登记值）。
- **仪器侧工具**：Phase 79 的 S94 从「只认内联标注」扩展为「内联 **或** 带指纹的外部豁免」，
  指纹 =（文件, 阈值, **该行逐字原文**）三联。

### 反驳条件（本结论在什么观测下会被推翻）

> 状态：第 1、2 条已在本次修复中被测过、**未触发**（⇒ 根因归属成立）；
> 第 3、4 条是随仪器常驻的哨兵，每次跑 S94 都会炸一次。

1. 若导回注册时字节后重跑 `gatecheck`，V16c / V18d / V18h **仍有任意一条红**
   ⇒ 「单点根因」结论错，说明还有第二个未定位的来源，本文作废。
   **实测：三条全绿（V18d `changed=0`、V18h `0/47055`、V16c `stale 224 → 922`）⇒ 未触发。**
2. 若 `lineage_invalidation.py` 在导回后仍报 `ref_changed > 0` 或 `dep_version_changed > 0`
   ⇒ 「三族哈希同源于该文件」的归属判定错（推论：我的复算写错了）。
   **实测：A04 层对 stale 的贡献由 34978 降到 0（valid 1100 / stale 0）⇒ 未触发。**
3. 若有人在别处**新增**一个未豁免的裸切片而 S94 仍报 0 处
   ⇒ 外部豁免通道实际是白名单，`NEG-S94b` 未真正生效，应立即回收该通道。
4. 若 `external_exempt_hits()` 对某条目报 0 而 S94b 仍判 PASS
   ⇒ 腐烂检测失效，死条目可以无限期挂着（等价于第二处的隐性赦免）。
