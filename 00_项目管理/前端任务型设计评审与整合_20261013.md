## 0. 一句话裁定

**这份规划可作为设计输入使用，但不能整体照做。** 它的**契约意识、预算纪律、状态区分**与项目现有铁律
（#62/#63/#64/#65/#66/#67）高度同频，其中**有 4 条比我们自己的方案更强，应当采纳**；但它整体是
**「产品化任务助手」的架构**（React 构建链 + FastAPI 新服务 + 任务历史/账号 + 用户试用），
**该方向已被 2026-10-13 裁决否决** ⇒ 按 §0.2 约定归为 **P2 方向建议（Option）**，不计入缺陷。

此外，规划中**有 7 处与本仓库实际数据模型不符**（§2），其中 **2 处若照字面实现会直接失败**
（关系白名单筛空、`status: valid|stale` 字段不存在）——这些是**事实性错误**，必须修正后才可引用。

**Remotion：本轮不引入**（§5）。理由不是"不好用"，而是**许可与三条既有工程约束同时冲突**。

## 2. 逐条核对表（② 需修正的 7 处 —— 均有实测证据）

> 核对方式：直接读 `06_PoC/etl/normalized.json`（9 657 / 48 712）与源码，现算分布，不引用任何旧报告数字。

### M1 ★ `type` 与 `kind` 混用（**最严重**，照字面实现会全部筛空）

规划 §5.4 给出的关系白名单是 `defines / has_symbol / has_quantity / has_unit / uses_operator /
derived_from / dimensionally_consistent / reactant_of / product_of / has_element / same_as / related_to`。

**实测结果：这 13 个全部真实存在 —— 但它们全是 `type`（语义关系），不是 `kind`。**

| 维度 | 种数 | 值域性质 | 实例 |
|---|---:|---|---|
| **`type`** | **24** | 语义关系（知识层）| `has_symbol` 24 341｜`composed_of` 7 756｜`has_quantity` 4 478｜`reactant_of` 2 753｜`product_of` 2 559｜`has_functionalgroup` 2 350｜`reagent_of` 1 807｜`defines` 115｜`has_element` 109｜`same_as` 101｜`derived_from` 80｜`related_to` 53｜`has_unit` 48｜`dimensionally_consistent` 47｜`uses_operator` 11 … |
| **`kind`** | **115** | **来源 / 管线标签**（数据层）| `real` 26 563｜`chebi_composition` 5 092｜`gnn_typed_verified` 3 324｜`real_reaction` 2 514｜`chembl_descriptor` 2 512｜`rhea_product` 2 460｜`gnn_typed_inferred` 76｜`llm_inferred` 8 … |

⇒ **修正**：过滤必须**双维度、两组 UI**。`types` = 语义关系（用户语义），`kinds` = 来源/管线
（可信度与来源追溯）。若按规划字面把关系名当 `kind` 传参，`filter_edges_by_kind("has_quantity")` 返回 **0 条**。
★ 本项目自己的原方案 §4「入口 4」也犯了同样的 UI 标注错误（把 `[composed_of][has_quantity]…` 写在
「边 kind」下），**一并修正**。

### M2 ★ `status: "valid" | "stale"` 字段不存在

规划 §8.5 的边结构含 `"status": "valid"`，§1 第 6 条与 §11 Phase UI-2 都依赖「过期证据过滤」。

**实测**：边 props 里的 `status` **只出现在 3 423 条（7.0%）** 上，取值只有 `VERIFIED` 3 350 /
`NEEDS_REVIEW` 73（GNN 产物状态），**与"过期"无关**；其余 45 289 条边**没有** `status`。

项目真实的"过期"机制是**另一套**，且**已经落地**（Phase 41）：

| 组件 | 事实 |
|---|---|
| `11_真实数据/source_registry.py` | 31 个来源登记 `version / locator / 内容哈希 / imports_from 血缘` |
| `11_真实数据/lineage_invalidation.py` | schema `sttp-lineage-invalidation/v1`；比较来源**当前内容哈希** vs 存档哈希 ⇒ `changed_direct` / `changed_with_lineage` / `n_affected_edges` / `lineage_gap_sources`；**当前 `n_affected_edges = 0`**（来源未变） |
| 边证据 | `evidence[]` **已内联** `src / src_ver / src_hash / impl_ver / indep`（Phase 41，证据绑定 49 572/49 572） |

⇒ **修正**：`stale` 不新造字段，而是**由现有数据现算**：
> **一条边 stale ⇔ 其 `evidence[]` 中存在 `e.src_hash ≠ source_registry[e.src]` 的当前内容哈希，
> 或 `e.src ∈ lineage_gap_sources`（血缘缺口，无法判定 ⇒ fail-closed 视为不可定位）。**

这个判据**天然非真空**：改动任一个被登记来源文件即变红（与铁律 #61 的负对照手法一致）。

### M3 `verification_level` 的默认档会隐藏 56.9% 的边

规划 §4.2「默认只使用 `rule_checked` 及以上」。

**实测 `verification_level` 分布（48 712 边）**：

| level | 边数 | 占比 | 所属口径 |
|---|---:|---:|---|
| `rule_checked` | 31 520 | 64.7% | verified + verified_strict |
| `source_asserted` | 13 797 | 28.3% | 均不在 |
| `cross_source` | 3 249 | 6.7% | verified + verified_strict |
| `model_inferred` | 135 | 0.3% | 均不在 |
| `by_construction` | 11 | 0.0% | **verified 在，verified_strict 不在** |
| `unverified` / `human_reviewed` | 0 | — | — |

按规划的默认 ⇒ 只剩 34 769 条（**71.4%**），**首次使用者看到的是一张被砍掉一半的图且没有任何提示**。

项目既有口径（`verification_model.py:97/107`，铁律 #19/#41）是**两档并立**：
`verified` = level ≥ `by_construction`；`verified_strict` = level ≥ `rule_checked`（**北极星口径**）。
前端投影 `graph_data_phase41.json` 的每条边**已经同时带 `verified` 与 `verified_strict` 两个布尔**。

⇒ **修正**：UI 给**两档显式预设**（默认 `verified`，可切 `verified_strict`），**任何过滤必须显示「已隐藏 N 条」**，
禁止无提示默认剔除。

### M4 等级词表不完整（漏 `by_construction` / `unverified`）

规划列的 5 个等级**名词都对**，但不是完整词表。权威词表是 `verification_model.py::LEVELS`（**7 档**，
由弱到强 `unverified / model_inferred / source_asserted / by_construction / rule_checked / cross_source / human_reviewed`），
且同文件 `LEVEL_DOC` 已为每档写好**"覆盖什么 / 不覆盖什么"**的声明性文案 ⇒ **UI tooltip 直接由该表驱动**，
不要在前端重写一份（否则又是一次"命名缺口"，#39）。

### M5 `evidence_ids` vs 真实字段 `evidence[]`

项目**没有**独立证据 id 体系；边上是 `evidence[]`（对象数组）。⇒ 统一用 `evidence[]`；
若将来要做独立证据服务（`/api/v1/evidence/{id}`），属 **P2**，且需先定义 id 语义（现无）。

### M6 `snapshot_id` 格式

规划用 `"sha256:..."`（全串前缀）。原方案用 `sha256[:12]`。⇒ 统一为 **`sha256:<前12位>`**，
并保留**现算**语义（图变则 id 变，前端缓存自动失效），加断言（V5）。

### M7 `needs_input` 状态没有对接真实拒答分类

规划的 `TaskResult.status` 含 `needs_input`，但项目侧 `12_评测/eval_runner.py:221` 的 outcome 词表
只有 **`answer` / `refuse`**（verdict：`correct / incorrect / false_answer / false_refusal`）。
好消息：项目已有 **8 个结构化拒答理由**可直接复用为 `needs_input` 的分类依据 ——
`s_refuse_missing_T` / `_missing_phase` / `_missing_unit` / `_missing_standard_state` /
`_protonation` / `_isomer` / `_log_domain` / `_dimension_ambiguous`。

⇒ **修正**：前端 `needs_input` 的**理由列表直接复用这 8 个 `reason_class`**，不另造词表。
（`stale` 同理见 M2。）

## 3. 可用·应吸收清单（① ）

### 3.1 比我们自己的方案更强的 4 条 —— **采纳**

| # | codex 的设计 | 为何更强 |
|---|---|---|
| **S1** | **会话级累计预算**（整个任务会话节点 ≤120 / 边 ≤200） | 我们的方案只有**单次请求**预算（`max_nodes=500`）。用户反复"展开一跳"可以把浏览器**累积**打爆 —— 这是真缺口，必须补 |
| **S2** | **`expandable[].token`**：展开凭证由**服务端签发**，绑定 task / snapshot / 过滤条件 / **剩余预算**；"前端不得自行构造无限查询" | 我们的方案是"重放上一组参数"，前端**可以**自行拼任意参数 ⇒ 预算可被绕过。token 把预算控制权收回服务端 |

## 5. Remotion 裁定（④ 暂不采纳）

项目：<https://github.com/remotion-dev/remotion>（React 程序化生成 MP4）。

### 5.1 裁定：**本轮不引入**，四因中任一成立即足够

| # | 理由 | 事实 |
|---|---|---|
| **R1** | **许可不是 OSI 开源许可**，与本项目 Apache-2.0 仓库共存需单列登记 | Remotion 采用 **Remotion License**：**个人 / ≤3 名员工公司 / 非营利评估** 免费（含商用）；**4 人及以上组织需购买 Company License**；自动化另计 **$0.01/render、$100/月起**。本项目刚完成 A03「许可进打包」（`DATA_LICENSES.md` 三态 + 程序化门禁），引入一个**"源码可用但不兼容"**类目会立刻打破刚刚建立的许可纪律，且**是否需付费取决于使用主体人数**——这是需用户裁决的事实，不是技术选择 |
| **R2** | **运行时栈重**，与三条既有约束冲突 | 需 Node + 打包器 + **headless Chromium 渲染**；与「**无构建链**（离线单文件）」「**推送预算 ≈4 KB/s**（单提交 pack ≲100 KB）」「**离线可复现**」同时冲突 |
| **R3** | **价值定位是"演示"**，与 §0.1 直接相悖 | §0.1 明列 ❌「把'演示/交付'当作评价标准」；Remotion 的产物是**讲解视频**，对本项目的**研究价值 ≈ 0**（不产生任何新的跨域结论或证据） |
| **R4** | **codex 自己的规划也把它排到 P2** | 其 §6.2：*"Remotion 不进入 P0/P1 主路径"*；§11：*"暂缓到 P2"*。即**规划内部对此无争议** |

### 5.2 若将来要用（前提写清，便于另裁决）

1. 先确认**使用主体的人数档位**（≤3 人 ⇒ Free License；≥4 人 ⇒ 需 Company License）⇒ **由用户裁决**；
2. 许可登记进 `DATA_LICENSES.md`，新增类目 `OPEN_SOURCE_NO / SOURCE_AVAILABLE`（不得冒充 Apache-2.0 兼容）；
3. 放**独立目录** `tools/remotion/`，**不入库渲染产物**（mp4 体积 × 推送预算 ⇒ 必然 408），`node_modules` 不入库；
4. **只读**已完成任务的 `Storyboard`（节点/边/证据快照）⇒ 渲成讲解视频；**不得进任务主路径、不得成为证据链一环**。

### 5.3 现在就能满足"可带走"需求的替代（零新依赖）

子图**导出 PNG / SVG**（Cytoscape 已具备）＋ 公式**复制 LaTeX**（MathJax 已具备）＋ **导出 JSON 快照**
（子图 + 证据 + `snapshot_id`）⇒ 覆盖"把这一小块图带出去"的真实诉求，**无需视频链路**。
